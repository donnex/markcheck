# markcheck — Project Specification

A TUI application for pilot-style Markdown checklists, aimed at sysadmin/devops repeating workflows (server upgrades, maintenance runbooks). Reads a Markdown file, displays checklist items as navigable cards, and writes completion state back to the same file using `[ ]` / `[x]` syntax.

```toml

```

`notify` powers the file watcher (`src/watcher.rs`). The update tag in the title bar is a *relative* elapsed time computed straight from `SystemTime::duration_since`, so no calendar/timezone crate is needed. `shell-words` splits `$EDITOR`/`$VISUAL`/`$BROWSER` the way a shell would. `toml`/`serde` parse the config file (below). `sha2` computes `AppState.file_content_hash`'s SHA-256 digest (see Write-time conflict detection, below) and `PendingSync.content_hash` (see Git Sync, below) via the one shared `model::hash_bytes` — a cryptographic digest is stronger than either use strictly needs, but the cost is negligible at checklist-file sizes. Git-sync (below) shells out to the system `git` binary via `std::process::Command` rather than adding a git library dependency (e.g. `git2`) — it reuses the user's existing SSH agent/credential helper for free, and needs nothing beyond `status`/`commit`/`push`.

`arboard`'s `wayland-data-control` feature pulls in `wl-clipboard-rs`, giving it a native Wayland clipboard backend selected via `WAYLAND_DISPLAY` at runtime; without it, arboard only has an X11 backend on Linux, which silently misses native-Wayland paste targets even though it reports success. The feature is target-gated to `unix, not(macos/android/emscripten)` by arboard itself, so it has no effect on macOS/Windows builds.

## Core Data Types (`src/model.rs`)

```rust
pub type LineNumber = usize; // 1-indexed

pub enum TaskState { NotStarted, Started, Done } // Started counts as not-done

pub enum ItemKind {
    Checkbox(TaskState),
    DisplayOnly,
}

// ordered body runs: plain prose, inline code, styled prose
// (emphasis/strong/strikethrough — a TextStyle), and links (text + url).
pub enum BodySpan {
    Text(String),
    Code(String),
    Styled { text: String, style: TextStyle },
    Link { text: String, url: String },
}

// a `### H3`+ sub-section label within an `## H2` list; display context
// (overview divider + card breadcrumb), not a navigable item.
pub struct SubHeading { pub level: u8, pub text: String }  // level is the raw Markdown level 3–6

pub struct Item {
    pub line_number: LineNumber,       // for write-back
    pub depth: usize,                  // nesting level: 0 = top-level, 1 = first sub-list, …
    pub ordinal: Option<String>,       // ordered-list marker as written (`3.`, `7)`); None for a bullet
    pub section: Vec<SubHeading>,      // active `### H3`+ sub-section path, outermost first; empty = directly under the H2
    pub display_text: String,          // body only; leading bold stripped
    pub body: Vec<BodySpan>,           // ordered prose/code runs for styled cards
    pub header: Option<String>,        // leading **bold** → card title
    pub code_spans: Vec<String>,       // inline `code`, in order
    pub code_blocks: Vec<String>,      // fenced blocks belonging to item
    pub kind: ItemKind,
}

pub struct List {
    pub title: String,
    pub banner: Option<String>,   // leading bold-only bullet → list banner
    pub items: Vec<Item>,
}

pub struct Document {
    pub file_path: PathBuf,
    pub title: Option<String>,    // first `# H1`, the document title
    pub has_default_list: bool,// lists[0] is the synthesized `(Default)` (no real H2)
    pub lists: Vec<List>,
    pub raw_lines: Vec<String>,   // full file, one entry per line, each keeping its own terminator
}

pub enum View {         // the base view under any overlay
    Checklist,
    ListComplete,
    AllComplete,
}

pub enum Overlay {      // a modal layer over the view; closing it is `overlay = None`
    ConfirmReset,     // modal confirmation before resetting all tasks
    ConfirmQuitReset, // offered on quit when all done: reset before quitting?
    Help,             // keybinding cheatsheet overlay
    Search,           // incremental `/` search input; cursor jumps live to the next match from `search.origin`
    ListPicker,       // `T` "go to task" overlay: filterable list of every task
}

pub struct AppState {
    pub document: Document,
    pub current_list_index: usize,
    pub current_item_index: usize,
    pub view: View,
    pub overlay: Option<Overlay>,            // drawn over `view` and given every key first
    pub status_message: Option<String>,
    pub status_expiry: Option<SystemTime>,   // when an ephemeral status auto-clears; None = sticky (failures + action feedback)
    pub status_is_error: bool,               // current message is a failure/nothing-happened; rendered red
    pub effects: Vec<Effect>,                // outward actions (copy, editor, suspend, link, git sync, quit) for the main loop's drain — see Effects below
    pub file_mtime: Option<SystemTime>,      // last known mtime; detects external edits
    pub file_size: Option<u64>,              // last known size; cross-checked with mtime (narrows a coarse-mtime-fs race)
    pub file_content_hash: Option<[u8; 32]>, // SHA-256 of the content we last confirmed on disk; guards commit_write against a lost update
    pub last_update_at: Option<SystemTime>,  // when the content last changed (our write or a reload)
    pub git_sync: GitSyncState,              // background git-sync state (--git-sync) — see below
    pub card_scroll: u16,                    // current card body scroll; reset on navigation
    pub card_max_scroll: u16,                // written back by the cards renderer each frame
    pub card_viewport_height: u16,           // card body visible rows; drives half/full-page scroll
    pub card_rect: Option<Rect>,             // current card's on-screen area, for click-to-copy hit-testing
    pub code_regions: Vec<(Rect, String)>,   // copyable code targets (on-screen one-row rect, clean full text) for click-to-copy
    pub overview_rows: Vec<(Rect, OverviewTarget)>, // per-row overview click zones (rect → navigate list/item, or toggle a task)
    pub pending_g: bool,                     // true after a lone `g`, waiting for the second `g` of `gg`
    pub pending_open_link: bool,             // true after `o` on a multi-link card, waiting for the link number
    pub pending_copy_code: bool,             // true after `y` on a multi-command card, waiting for the command number
    pub icons: IconSet,                      // nerd() default; --no-nerd-font -> unicode()
    pub clipboard_primary: bool,             // --primary: also target X11 PRIMARY
    pub auto_copy: bool,                     // --auto-copy: copy code on navigation, announce on success
    pub palette: Palette,                    // semantic UI colors resolved at startup
    pub file_gone: Option<FileGone>,         // Deleted / NotRegular once confirmed; blocks writes
    pub search: SearchState,                 // incremental `/` search state — see below
    pub picker: PickerState,                 // `T` go-to-task overlay state — see below
    pub help: HelpState,                     // `?` help overlay scroll state — see below
    pub undo_stack: Vec<StateSnapshot>,      // full checkbox-state snapshots for undo; `u` pops+applies; capped at UNDO_HISTORY_CAP; cleared on external reload
    pub redo_stack: Vec<StateSnapshot>,      // snapshots for redo; `Ctrl-R` replays; cleared by any fresh change and on external reload
    pub history_epoch: u64,                  // bumped when an external reload clears both stacks; a failed undo/redo re-pushes its entry only if unchanged
}

// Fields that arrived together for one feature are grouped into their own
// sub-struct instead of sitting flat on AppState — keeps a ~40-field struct
// from reading as one undifferentiated pile as more overlays are added.

pub struct SearchState {
    pub query: String,           // live query typed while the Search screen is active
    pub last: Option<String>,    // last committed query, reused by `n`/`N` after the prompt closes
    pub origin: (usize, usize),  // cursor (list, item) when the search began; restored on `Esc`
}

pub struct PickerState {
    pub query: String,           // live filter query typed in the ListPicker overlay
    pub selection: usize,        // highlighted row index within the picker's filtered entries
    pub viewport_height: u16,    // picker's visible row count; drives half-page selection jumps
    pub rows_area: Option<Rect>, // on-screen entry rows, written back by render_list_picker; None when none drawn
    pub scroll_offset: usize,    // entry index drawn on rows_area's top row; for click hit-testing
}

pub struct HelpState {
    pub scroll: u16,             // `?` help overlay scroll offset
    pub max_scroll: u16,         // and its viewport height, written back by render_help each frame
    pub viewport_height: u16,
}

pub struct GitSyncState {
    pub active: bool,            // --git-sync requested and GitSync::detect confirmed a git work tree at startup
    pub last_at: Option<SystemTime>, // when git-sync last committed+pushed; drives the "Synced … ago" tag; cleared by a later failure
    pub busy: bool,              // a sync or push retry is running (mirrors GitSync::is_busy each tick); drives "syncing…"
    pub problem: Option<&'static str>, // "not pushed"/"not synced"/"not tracked" after a failed attempt, until a later Synced
    pub reported_reason: Option<String>, // the push-failure reason last put in the status bar, so an identical retry failure isn't repeated
}

pub struct PendingSync {
    pub content: String,                  // exact file content expected once the change lands
    pub content_hash: [u8; 32],           // SHA-256 of `content`; feeds the staleness check
    pub previous_content: Option<String>, // content this write replaced; None if unreadable just before the write. Staged-target guard only
    pub description: String,              // e.g. `Check "Restart service"`, becomes the commit message
}

pub type StateSnapshot = Vec<(LineNumber, TaskState)>; // every checkbox's state keyed by line number; the unit of undo/redo history
pub const UNDO_HISTORY_CAP: usize = 100;               // max undo entries kept

pub struct IconSet { // done, pending, started, current, note, file, list, update glyphs
    // IconSet::nerd(): Font Awesome range glyphs (Nerd Fonts v3); update = refresh
    // IconSet::unicode(): ☑ ☐ ◐ ❯ ▪ ≡ • ↻  (done ☑ / pending ☐, started = ◐, update = ↻)
}

pub enum ColorDepth { TrueColor, Palette256, Basic, Mono }
pub struct Palette { done, started, code /* Style */, current, note, error, warning }  // semantic UI colors; error is red, warning is amber/orange (list banner). Nesting depth guides use `Palette::depth_color(slot)` — a hard-coded color cycle indexed by the sub-list's document-wide ordinal (`sublist_base` plus `List::sublist_slot`), not a field
```

**Color palette:** the UI's semantic colors (done, started, `code`, current, note) come from a `Palette` resolved once at startup to the terminal's capability — `Color::Rgb` curated hues on truecolor terminals, the nearest `Color::Indexed(n)` on 256-color terminals, or named ANSI-16 as the always-safe fallback (which also respects the user's theme). Code is styled markdown-style with a subtle gray **background** rather than a foreground hue, so it doesn't collide with the dim-foreground elements (side cards, pending dots, captions). `code` is a whole `Style`, not a background color: it always pairs that background with an **explicit light foreground** (One Dark's `#abb2bf`, index 250, or `White`), because leaving the fg to the terminal made code black-on-slate on light themes. **`NO_COLOR`:** a non-empty `NO_COLOR` (no-color.org) wins over everything and selects `ColorDepth::Mono` / `Palette::mono()` — every role is `Color::Reset`, `code` is `Modifier::REVERSED`, `depth_color`/`progress_color` carry no color (the counter keeps its bold-when-complete), the current list-tab pill is reversed instead of black-on-cyan, and `position_dots` draws a started item as `◐` so it still reads apart from a done `●`; `Palette::is_mono()` is the check for these glyph/modifier fallbacks. Capability is sniffed from `NO_COLOR`, `COLORTERM` (`truecolor`/`24bit`) and `TERM` by the pure `depth_from_env`: a `TERM` in `TRUECOLOR_TERMS` (`xterm-kitty`, `alacritty`, `foot`, `foot-extra`, `wezterm`, `contour`, `xterm-ghostty`) or ending in `-direct` is truecolor, else one containing `256color` is 256-color. The `TERM` list exists because `COLORTERM` is the signal most often lost — OpenSSH doesn't forward it without `SendEnv`/`AcceptEnv`, `sudo` strips it — so those terminals fell back to ANSI-16 over SSH. terminfo (`colors`, `RGB`/`Tc`) is not consulted: it would mean parsing compiled entries or shelling out to `tput`. `detect_color_depth` supplies the real env, and `main.rs` sets `state.palette = Palette::detect(settings.color)` at startup, where `ColorChoice` (`--color auto|truecolor|256|16`, config `color`; flag > config > `Auto`) forces a depth via `forced_depth` — over `NO_COLOR` too, which no-color.org allows for explicit configuration — and `Auto` detects (default is `Palette::basic()`, used in tests). No color-detection crate is needed. All `ui/` rendering reads colors from `state.palette` (threaded into helpers) rather than hardcoding `Color::*`.

## Header Taxonomy

markcheck recognizes five kinds of "header," each a title on a container. This vocabulary is **canonical** across the code, this document, and the README — keep them in sync:

| Level | Markdown | What it is | Code | User-facing |
| ------- | ---------- | ----------- | ------ | ------------- |
| **Document header** | `# H1` | the whole file's title | `Document.title` | shown as the title in the title bar |
| **List header** | `## H2` | a list's title | `List.title` | "list"; shown above the cards + in the overview |
| **Sub-section header** | `### H3`–`###### H6` | a labeled group of items *within* an H2 list | `Item.section` (a `Vec<SubHeading>`) | overview `── divider`; dim ` › `-joined breadcrumb above the card |
| **Card header** | leading `**bold**` on a task | a task card's title | `Item.header` | "card title"; shown inside the card (info icon, blue) |
| **Sub-list header** | a nested/indented list under an item | the parent chain of a nested item | `List::parent_chain` → `breadcrumb_line` | depth-colored breadcrumb above the nested card |

**Naming decision:** the H2-level container was renamed `Section` → **`List`** (it holds an H2 heading plus its items and banner), so "list" is used consistently in code identifiers (`lists`, `current_list_index`, `jump_to_list`, `View::ListComplete`, …), in the UI ("List Complete", "jump to list N", "next unfinished list"), and in the docs. `List.title` **is** the list header. This mirrors the other containers — `Document.title` (document header) and `Item.header` (card header) — where the container is a noun and its header is a field.

## Markdown Parsing (`src/parser.rs`)

Use `pulldown-cmark` with `Options::ENABLE_TASKLISTS` and `.into_offset_iter()` for byte offsets. Derive line numbers from offsets:

```rust
fn offset_to_line(offset: usize, src: &str) -> usize {
    src[..offset].chars().filter(|&c| c == '\n').count() + 1
}
```

**Front matter:** a leading YAML (`---` ... `---`/`...`) or TOML (`+++` ... `+++`) front-matter block is skipped. Unhandled, CommonMark reads the opening `---` as a thematic break and the closing one as a setext underline, turning the metadata into a `## H2` list title. `blank_front_matter` probes the first event of a pulldown-cmark pass with only the metadata-block options (`FRONT_MATTER_OPTIONS`); if it is a `MetadataBlock` starting at byte 0, that byte range is overwritten with spaces (line endings kept) before the `[/]` pre-pass, so offsets and line numbers still index `raw_lines` and write-back round-trips the block byte for byte. The metadata options are deliberately kept out of `PARSE_OPTIONS`: pulldown-cmark accepts a metadata block at *any* unindented block start, so enabling them for the real parse would swallow a `---` ... `---` span in the middle of a checklist. The block's contents (e.g. a `title:` key) are not read.

**Started marker pre-processing:** pulldown-cmark's task-list extension only recognizes `[ ]` and `[x]`, not the `[/]` "started" marker. Before the real parse, `extract_started_markers` runs a first pulldown-cmark pass over the same text with the same options (`PARSE_OPTIONS`) and records the byte offset of every `[/]` that opens a list item's first paragraph (the first `Text` event after `Start(Item)`, skipping only a `Start(Paragraph)`), provided it is followed by whitespace — exactly where a `[ ]` would have produced a `TaskListMarker`. Only those three-byte ranges are rewritten to `[ ]`, so byte offsets — and line numbers — are preserved. The processed string feeds the second, real parse; `raw_lines` keeps the original text. On `Event::TaskListMarker(false)`, a marker whose offset is in the recorded set becomes `Checkbox(Started)`.

Because the marker positions come from pulldown-cmark itself, the pre-pass can never disagree with the real parse about block structure: a `[/]` lookalike inside a fenced or indented code block, an HTML block, or a fence opened on a list-marker line is never rewritten, and a fence-looking line that CommonMark doesn't treat as a fence (inside an HTML comment, or indented four spaces) hides nothing after it. A blockquoted `[/]` bullet is rewritten like any other, so pulldown sees a real checkbox and the item surfaces as a non-interactive `DisplayOnly` card (the same degrade `[ ]`/`[x]` get inside a blockquote) rather than being dropped by the no-checkbox-list rule. An earlier raw-text line scan tracked fences itself and got exactly these cases wrong. `extract_started_markers_boundary_sweep_agrees_with_pulldown` sweeps indentation, blockquote nesting, list markers and all of those block contexts against that agreement property.

Walk events. `parse_source` is a short driver: everything carried between events lives in a `ParseState`, whose `handle` dispatches each event to one method per event family (`on_heading_end`, `on_list_end`, `on_item_start`/`on_item_end`, `on_task_marker`, `on_code_block_end`, `on_text`/`on_break`/`on_code`), and the per-item text, styling and link handling sits on `ItemBuilder`. The cross-cutting rules are named helpers rather than spread across arms: `is_banner_candidate` (list banner eligibility), `keeps_fence_attachment` plus `attach_trailing_fence` (the fence-after-list rule), and `finish` (the default list and the drop-lists-without-a-checkbox pass).

- `Event::End(Tag::Heading(H2))` → start new `List`; resets the "first item seen" flag (`seen_first_top_item`) for banner detection; clears the sub-section stack
- `Event::End(Tag::Heading(H1))` → first non-empty one sets `Document.title`; also clears the sub-section stack (H1 is top-level)
- `Event::End(Tag::Heading(H3..=H6))` with non-empty text → reduce the sub-section stack: pop entries at level ≥ this heading's, then push `SubHeading { level, text }`
- These heading rules apply only to a heading **outside any list item and any blockquote**. `on_heading_start` routes a heading opened inside an item (`- ## Rollback`, `1. # X`, or one in the item's later paragraphs) to that item as a bold run (`start_strong`/`end_strong`, bracketed by boundaries): a leading one becomes the card `header` (and so can be the list banner), a later one bold body text. A heading in a blockquote outside any item (`> ## Note`) is read but discarded (`heading_quoted`). Neither ever opens a list, sets the title or touches the sub-section stack — otherwise a heading item would open a new `List` mid-list and the enclosing list's items would be appended to it, emptying (and dropping) the real section.
- `Event::Start(Tag::Item)` → push an `ItemBuilder` frame onto a stack (so a nested item's interleaved Start/End doesn't clobber its parent's in-progress fields), recording the line number, nesting `depth` (`list_depth − 1`; 0 = top-level), and a **snapshot of the current sub-section stack** (`section`, stable for the whole item since a heading inside a list item is item content, never structural)
- `Event::TaskListMarker(checked)` → marks item as `Checkbox(Done/NotStarted)`; pulldown strips `[ ]`/`[x]` from text automatically (`[/]` was already rewritten to `[ ]`), and a marker at a recorded `[/]` offset becomes `Checkbox(Started)` instead of `NotStarted`. Also sets a `list_had_checkbox_syntax` flag (reset at each new top-level list) used by the has-checkbox gate below — tracked independently of the item's final `kind` so a blockquoted checkbox (forced to `DisplayOnly`) still counts as "this list had real task syntax" and doesn't vanish its own segment. That keeps a quoted example beside the live tasks of its `## H2` list; it does not keep the H2 list itself, which the final has-checkbox pass below still drops when every checkbox in it is quoted.
- `Event::Start`/`End(Tag::BlockQuote)` → tracks a `blockquote_depth` counter; an item opened while `blockquote_depth > 0` is snapshotted `in_blockquote` and, at `End(Tag::Item)`, is forced to `ItemKind::DisplayOnly` regardless of any `TaskListMarker` — a checkbox quoted inside a `>` blockquote (e.g. illustrating another runbook) reads as an example, not a live task, and is also excluded from list-banner eligibility (below) so a quoted bold-only bullet can't hijack the real banner slot.
- `Event::Start(Tag::Strong)` at the absolute start of an item → capture the bold text as the item's `header` (card title); bold appearing **mid-text** instead toggles inline strong styling on the body runs
- `Event::Start`/`End(Tag::Emphasis | Tag::Strikethrough)` → toggle the corresponding flag in the builder's active `TextStyle`; body `Text` runs read while any flag is set are emitted as `BodySpan::Styled` instead of `BodySpan::Text`. `Options::ENABLE_STRIKETHROUGH` is enabled alongside `ENABLE_TASKLISTS`.
- `Event::Start(Tag::Link { dest_url, .. })` → begin buffering the link; its text still flows into `display_text` (so search matches it) and on `End(Tag::Link)` a `BodySpan::Link { text, url }` is emitted. `Item::link_urls()` collects these for the `o` open action. **Known limitation:** a link entirely inside the leading-bold title (`capturing_header`) is gated out — its anchor text still folds into `header` as plain text, but the URL is discarded and `link_urls()` never sees it, so `o` can't open it. Put the link in the body instead if it needs to be openable.
- **Bare URLs** (GFM "extended autolinks", which pulldown-cmark doesn't implement): the event stream is wrapped in `TextMergeWithOffset` so a URL pulldown splits at `_`/`&` arrives in one `Text` event, and `find_bare_urls` scans each body text run for `http://`/`https://`/`www.` at a word boundary, ending at whitespace or `<`, requiring a dotted domain, and trimming trailing punctuation plus an unbalanced `)`. Each match becomes a `BodySpan::Link` whose text is the URL as written (a `www.` one opens as `http://`); the prose around it keeps its `Text`/`Styled` span. Text inside a link, the bold title or code is never scanned.
- `Event::Code(text)` inside item → push to `code_spans`, and append `BodySpan::Code` to `body`. Inside the leading-bold title (`capturing_header`) the code text only folds into `header` as plain text and sets `header_has_code`: it is drawn without a chip, so it is not a copy candidate either — otherwise `y` acted on a command the card didn't show (copying a title-only `make`, or refusing a card with one visible chip as ambiguous)
- `Event::Start/End(Tag::CodeBlock)` → buffer the block's content into the open item's `code_blocks` (kept out of `display_text`) — fenced and indented blocks alike, since an indented block is how older runbooks and converters such as pandoc write a command. Outside an item, only a *fenced* block can attach to the previous list's last item (`attach_fence_to_last_item`); a stray top-level indented block is discarded
- `Event::Text` → accumulate `display_text` (or the header/code-block buffer when one is active), and append `BodySpan::Text` to `body` when in an item's body
- `Event::SoftBreak | HardBreak` → a space (`push_break`). A boundary inside the item — `Start`/`End(Paragraph)`, the end of a nested code block or sub-list, or a dropped `Html`/`InlineHtml` tag — only marks a pending separator (`mark_boundary`); `flush_separator` turns it into a space (in `text` and as a `BodySpan::Text(" ")`) just before the next text, code or link, and only when text already precedes it, so a second paragraph or `a<br>b` doesn't fuse onto the first and a body after a bold-only title gets no leading space. It is flushed before a link opens so the space never becomes link text
- `Event::End(Tag::Item)` → classify and buffer item

**List banner:** when the **first** item of a list is a non-checkbox bullet whose entire content is one leading `**bold**` span, it emits no `Item` — its text becomes the list's `banner` (a non-navigable warning line, rendered below the list title). Every *other* bullet, including later bold-only ones, is a normal card (a display-only card when it has no checkbox). A banner attaches to the pre-heading `(Default)` list too. "First item" means the first top-level item of the first *kept* Markdown list under the heading: the banner candidate (`pending_banner`) and the "saw a top-level item" flag (`list_saw_top_item`) are buffered with the Markdown list they came from, and `on_list_end` commits them to the `List` (setting `seen_first_top_item`) only when that Markdown list had checkbox syntax. A checkbox-less Markdown list is dropped by the no-checkbox rule, so it neither supplies the banner nor takes the banner slot from a bold-only first bullet in a later, kept list. If the whole `List` ends up with no live checkbox, `finish` drops it and the banner with it. A bullet with its own nested children is never banner-eligible either — the banner emits no `Item`, which would otherwise leave those children with no depth-0 parent in the flat list (`items_before`, a snapshot of `current_list_items.len()` at the bullet's `Start`, detects this: any growth by the bullet's own `End` means it has children, since descendants always finish first). Nor is a bullet inside a `>` blockquote — it's excluded from banner eligibility the same way, so a quoted example can't hijack the slot. Nor is a bullet that carries code — inline code inside its bold (`header_has_code`) or a fenced block nested under it (`code_blocks`): the banner is one line of plain text, so it would silently drop a fenced command, and a bold-only bullet that names a command stays the card it always was.

**Sub-sections (`### H3`+):** headings of level 3–6 label a group of items *within* an `## H2` list rather than starting a new list. The parser keeps a **sub-section stack** (`Vec<SubHeading>`): each H3–H6 pops entries at level ≥ its own and pushes itself (so an H4 nests under an H3, a second H3 replaces the first plus any deeper level); the stack is **cleared at every H1/H2 boundary**, which begins a fresh list context. Each item snapshots the active stack into `Item.section` when it opens. Because a heading *inside* a Markdown list item is item content rather than structural, every item in one list shares the same snapshot — and a single H2 list can hold several Markdown lists separated by sub-headings, all appended to the same `List`. A sub-heading that no item references (e.g. an H3 immediately followed by another heading, with no items between) never appears in any `section`, so **empty sub-sections drop automatically**. Sub-sections are pure display context: they are **not** navigable items, not matched by the main `/` search, and never affect progress counts or write-back. They *do* surface in the `T` go-to-task picker — shown as a dim `— …` path suffix and foldable into its filter — but that is picker-only; the section text stays out of `Item::search_text`. Rendering: the overview draws a `── Text` divider before the first item of each group (diffing adjacent items' `section` paths) and, when a group's ancestor rows scroll above the panel, pins them back as a **sticky header** — the `[n] Title` list header (multi-list only) plus every active `### H3`+ level, outermost first — in reserved rows above the still-visible list, covering nothing; the card shows the path as a dim ` › `-joined breadcrumb above it (see UI Layout).

**List buffering / list invariant:** items are buffered per top-level list and only kept if the list contains at least one checkbox — a notes-only list contributes nothing. After parsing, every list (the pre-heading `(Default)` one included, and `has_default_list` with it) that holds no `ItemKind::Checkbox` item is dropped entirely, so every list in a parsed `Document` has ≥1 checkbox. That final pass checks item kinds, not `list_had_checkbox_syntax`: a list whose only checkboxes are blockquoted keeps them as `DisplayOnly` cards through the per-segment gate, so it would otherwise survive with zero tasks — a vacuously complete `0 / 0` row in the summary, a jump key with nothing to land on, and a quoted-only file that opens instead of reporting "No checklist items found in \<file\>" (`list_whose_only_checkboxes_are_blockquoted_is_dropped` pins it). Tabs, 1–9 jump keys, and the overview renumber automatically (they enumerate positionally). The empty-list UI placeholder is kept as a defensive fallback only.

**Nested / sub-lists:** nested list items are supported, not flattened. Each `Item` carries a `depth` (0 = top-level, 1 = first indented sub-list, …); items stay a **flat `Vec` in document/pre-order** (depth is metadata, not a tree). Because items are pushed at `End(Item)` — and a parent's `End` fires *after* its children's — a nested subtree arrives post-order, so each flushed top-level list is **sorted by `line_number`** to restore document order (a parent bullet always precedes its indented children). Banner detection is gated to the first *top-level* (depth-0) bullet, so a bold-only bullet inside a sub-list is a normal display-only card, never a banner. Every item — at any depth — remains a navigable card and toggles by its own line, so write-back is unaffected. The overview indents rows by depth (`item_indent`) and draws a **`│` depth guide per nesting level** in the indent, each in `Palette::depth_color(slot)` — a hard-coded color cycle (blue → purple → cyan → orange, resolved per color depth), so hierarchy reads by *which* color rather than one color fading (which the earlier single-dimming-purple failed at legibly). The `slot` is the guide's **document-wide sub-list ordinal**: the number of sub-lists in all earlier lists (`sublist_base`) plus the ancestor-at-that-level's `List::sublist_slot` (its index among *this* list's parents). The overview gets every item's parent, sub-list slot and `info_parent_state` from `List::item_links` — one linear pass per list, not a backward/forward scan per item — and builds each row's ancestor slots from the parent links (`AncestorSlots`), keeping only the levels that fit the panel (two cells per guide; deeper guides would be clipped anyway), so a frame stays linear in the item count even for a file nested thousands of levels deep. Because the ordinal is global, **every sub-list in the document gets its own color** — distinct sub-lists within a list don't blend, and a neighbouring list's guides don't look like the same list continuing — with no collision until the 4-color cycle wraps. The guides descend from each parent's marker column and keep the marker prefix's on-screen width unchanged (so the click toggle-zone is unaffected). A nested item's card shows its parent chain as a breadcrumb above the title — the **sub-list header** (`breadcrumb_line` via `List::parent_chain`) — drawn in the **depth color of the item's own sub-list** (its immediate parent's document-wide slot), matching the overview guides. Deeper nesting is carried faithfully; odd/invalid nesting is hardened separately.

**Fenced blocks after a list:** a fenced code block immediately following a kept list (only other fenced blocks in between) attaches to that list's last item; anything else between the list and the fence breaks the attachment, and a fence after a *discarded* list attaches nowhere.

Items before the first H2 go into a synthesized `List { title: "(Default)", .. }`.

Identity of duplicate items is `line_number`, not content.

## Markdown Write-Back (`src/writer.rs`)

Surgical line replacement — only the task marker changes. `set_task_marker` replaces the first `[ ]`/`[x]`/`[X]`/`[/]` found on the item's line with the target for its state (`NotStarted`→`[ ]`, `Started`→`[/]`, `Done`→`[x]`); uppercase `[X]` is recognized too (pulldown parses it as done, so it must be rewritable) and is normalized to the target's casing only when its state changes — a checkbox already in the target state is left as written, so toggling one task never rewrites an untouched `[X]` elsewhere in the file. Written atomically: a temp file is written and fsynced first, then renamed over the target, so a crash or full disk mid-write can never leave the file truncated or corrupted — the fsync (not just the temp-then-rename pattern alone) is what makes that guarantee hold on filesystems like ext4 `data=ordered`, where a rename's durability isn't otherwise assured until the write it points at is flushed.

**One line model, CommonMark-shaped.** `raw_lines` is built by `parser::split_lines_keeping_endings`, which breaks on `\r\n`, a lone `\n`, **and** a lone `\r` (CommonMark's three line endings) and keeps each line's own terminator on the end of it. `write_back` therefore rejoins by plain concatenation: every line ending, and the presence or absence of a final one, comes straight from the source rather than from a whole-file assumption. This replaced a pair of `uses_crlf`/`trailing_newline` flags, which were wrong in two ways — deep review, round 2, both reproduced. A single flag can only describe *one* ending for the whole file, so a file mixing CRLF and LF had every line rewritten to CRLF on the first toggle, turning a one-marker change into a whole-file diff (and, under git-sync, an automatically pushed whole-file commit). Worse, the flags came from `str::lines()`, which splits only on `\n` while pulldown-cmark splits on a lone `\r` too: on a CR-only file `raw_lines` was a *single* entry while pulldown saw N list items, so `LineCounter` gave every item `line_number == 1` and `write_back`'s per-item writes all landed on that one line and clobbered each other — every toggle silently discarded, the UI showing the task done and the file never changing. `LineCounter` now counts the same three endings (`count_line_endings`), so a byte offset and a `raw_lines` index always agree about which line they name, and the `[/]` pre-scan uses the same splitter so its byte-length-preservation invariant still holds.

The original file's permissions are preserved: the temp file is created with mode `0600` (never more permissive than the most restrictive plausible source, even briefly), and the source's ordinary permission bits (`mode & 0o777`) are applied through the file handle (fchmod semantics, immune to umask) before the rename. The setuid, setgid and sticky bits are never carried over: the new file belongs to whoever saved it, so copying a setuid/setgid bit would hand that user a special-bit file whose content someone else chose — exactly what the kernel prevents by clearing those bits when anyone but the owner writes a file — and none of them has a legitimate use on a Markdown checklist. If the source file's metadata can't be read — **including when it has been deleted externally** — the write aborts with an error and nothing is written, so a deletion is never silently overwritten or recreated. The app layer detects the deletion first and blocks the toggle before `write_back` is even called (see "Reload From Disk"); this abort is the writer's own backstop.

**Documented limitations:** the rename gives the path a new inode, so hard links are severed (other links keep the old content) and another user's ownership is not preserved — the same trade-off every atomic-save editor makes. The same goes for anything else inode-associated that `write_temp` doesn't explicitly carry forward: POSIX ACLs, extended attributes (xattrs), and any filesystem-specific security label — `write_temp` only ever calls `set_permissions` (plain Unix mode bits, via `fchmod`), never any ACL/xattr API, so a file with an ACL granting another user access, or xattrs with operational meaning, loses that extra metadata on the very first toggle, even though the ordinary mode bits come through unchanged. Worth calling out explicitly for this project's stated audience (sysadmin/devops runbooks, more likely than average to live in ACL-managed shared directories) rather than leaving "permissions are preserved" (README) to imply a broader guarantee than the code actually gives.

**Write-protected checklists are refused, not overwritten.** A rename only needs write permission on the *directory*, so temp-then-rename would happily replace a file the user made read-only (`chmod a-w`) — and then copy the `0444` mode onto the new content, so the result looks untouched. Read-only is the tool-agnostic way to say "don't change this", and editors honour it (vim's `E45`), so `write_back` checks `metadata.permissions().readonly()` (all write bits clear) right after reading the source metadata and returns `PermissionDenied` with nothing written. `commit_write` rolls the toggle back and, when `writer::is_read_only` confirms the cause, shows a sticky "File is read-only — change not saved (chmod u+w to allow saving)" instead of the generic write failure; nothing reaches git-sync. `main.rs` also passes `is_read_only` to `launch::startup_warning`, so the condition is announced before the first keypress. Only the mode bits are consulted: a file writable by its owner but not by the runner is the foreign-owner case below, not this one.

**Hard-linked checklists are warned about, not refused.** `write_back`'s temp-then-rename gives the path a *new inode*, so any other name hard-linked to the checklist keeps the old one and silently stops tracking it — one logical file quietly becomes two, and neither the content fingerprint nor the write lock notices, because both reason about paths while this is about inodes. External review of `5c51d81` raised it and preferred refusing the write outright.

markcheck warns instead, at startup, before anything has been written and while quitting is still free: `writer::hard_link_count` reports the link count and `launch::startup_warning` turns anything above one into a sticky, error-coloured status message. Refusing would make markcheck stricter than the editors these files are already edited with — vim with `backupcopy=no`, emacs and VS Code all break hard links exactly the same way — and with no override flag the checklist would simply be unusable. No data is lost either; the aliases diverge, but both keep valid content. The defect the review names is that it happens *silently*, and the warning is what removes the silence. A PTY test asserts the warning actually reaches the terminal, since a warning nobody sees would make the whole trade-off worthless.

**Ownership: the group is kept, another user's UID is warned about.** A plain temp-then-rename hands the checklist to the saver: their UID, and their primary group unless the directory is setgid. In a shared runbook directory (files `0664` in a common group, each operator with their own primary group) the first toggle would lock the rest of the group out of the file. `write_temp` therefore `fchown`s the temp file to the source's UID and GID before applying the mode, falling back to the GID alone when the UID can't be kept — any group the saver belongs to may be set without privilege, which covers the shared-group case, and root keeps both. Both calls are best effort: a group the saver isn't in simply isn't kept. Keeping another user's UID needs root, so that case is flagged rather than fixed: `writer::foreign_owner` compares the file's owner with the UID a newly created file gets (read off a throwaway probe file in the temp directory, as std has no `geteuid`; this predates the `libc` dependency, which could replace it), and `main.rs` adds "this file belongs to user N — saving makes it yours" to the startup warning alongside the hard-link one. An in-place write would keep the owner but give up the atomic-rename guarantee, so it was not taken. A sticky directory additionally refuses the rename over another user's file outright (`EPERM`), which surfaces as an ordinary write failure.

**Symlinks:** the CLI path is resolved with `fs::canonicalize` once at startup (`main.rs`), so a file opened through a symlink is written through to the real target, the link stays intact, and the file watcher watches the *target's* parent directory (a cross-directory symlink would otherwise never produce watch events). Consequences: the title bar shows the resolved target's filename, and a symlink retargeted mid-session keeps writing to the startup-resolved target.

```rust
pub fn write_back(document: &Document) -> io::Result<()> {
    // 1. Flip [ ]/[x] on the recorded line numbers in raw_lines.
    // 2. Read source metadata: any error (incl. NotFound) => abort, file
    //    untouched, so a deleted file is never recreated. A read-only file
    //    (all write bits clear) => PermissionDenied, file untouched.
    // 3. write_temp(): create ".{name}.markcheck-tmp-{pid}-{random:x}" with
    //    mode 0600 (create_new; on AlreadyExists, retry once at a freshly
    //    -suffixed name instead of deleting the colliding file -- it could
    //    belong to another live process; random_suffix() adds
    //    process-random entropy beyond the PID alone so a genuine name
    //    collision is vanishingly unlikely, not just unlikely), write
    //    contents, fchown to the source's uid+gid (best effort; on EPERM
    //    retry with the gid alone, which a member of that group may set),
    //    file.set_permissions(source mode & 0o777 — never setuid/setgid/
    //    sticky) (fchmod, umask-immune), then
    //    file.sync_all() to flush the data to disk.
    // 4. fs::rename over the target; remove the temp on any failure.
    // 5. unix only, best-effort: fsync the parent directory too, so the
    //    rename's directory entry itself survives a crash.
}
```

Called synchronously on every toggle. Guarantees persistence if the terminal crashes mid-session, and rename's atomicity (same filesystem) means the file is never observed half-written.

## App State & Navigation (`src/app.rs`)

Key methods on `AppState`:

- `current_item() -> Option<&Item>` / `current_item_mut() -> Option<&mut Item>` — `None` when the current list has zero items (e.g. an H2 heading with only prose underneath, no checklist). Every call site handles this instead of assuming an item always exists; the UI shows a "No checklist items in \<list\>" placeholder card in that case.
- `first_undone_index(list)` (free fn) — position of the first `Checkbox` whose state ≠ `Done` (a `Started` task still counts as not-done), or `None`. Drives startup/jump/advance landing on the first not-done item.
- `AppState::new` — starts the cursor on the first not-done item: the first list's first undone, else the first undone anywhere, else item 0 when everything is done. **Precondition:** the document must hold ≥1 list — `current_list()` indexes `lists[current_list_index]` with no fallback, so a list-less document would panic. This is upheld at both entry points (startup rejects a list-less file in `main.rs`; reload keeps the last good document when the new one has no lists) and is made explicit by a `debug_assert!` in the constructor plus a clear `.expect` message in `current_list()` for release builds.
- `focus_item(list, item, CursorMove)` — the **single cursor-move primitive** every motion goes through: set both indices (clamping the item, ignoring an out-of-range or empty list), set `view = Checklist` (it never touches `overlay`; a caller that closes one, like `picker_commit`, does so itself), reset `card_scroll`, and — for `CursorMove::Navigate` — `maybe_auto_copy()`. `CursorMove::Quiet` is for moves that aren't the user navigating to a card (undo focusing the changed item, `Esc` restoring the pre-search cursor). Before it existed each motion re-implemented those steps by hand and `Tab`, `gg`, `G` and the all-complete screen's `h`/`k` all forgot the auto-copy (#30); a new motion should call it rather than set the indices itself. The copy itself only runs when the main loop drains the effect queue (see Effects), after the handler has set its own status, so `report_auto_copy` appends a copy confirmation to whatever the motion reported (`Match 1/5 · wrapped to top · Copied to clipboard`), never replaces an error, and a sticky hidden-characters refusal replaces the motion's message; neither the motion's notice nor the copy outcome is lost. `n`/`N` and `Tab` report through `focus_and_report`, which clears the status, moves, then sets the motion's message.
- `navigate_next()` / `navigate_prev()` — the clamping primitives: `focus_item` one item along in the current list, which clamps at list boundaries. Cursor stops on **all** item kinds including `DisplayOnly`. `l`/`j` and `h`/`k` (and `→`/`↓` / `←`/`↑`) are bound to `navigate_forward`/`navigate_backward`, which call these but **cross** into the adjacent list at a list edge (see "Advancing between lists"); toggle-advance uses the clamping primitives directly.
- `scroll_card_down_by(n)` / `scroll_card_up_by(n)` (bound to `Ctrl-E`/`Ctrl-Y` with `n=1`, `Ctrl-D`/`Ctrl-U` with `n=half_page()`, `PageDown`/`PageUp` with `n=page()`) — move `card_scroll` by `n` wrapped lines, clamped to `[0, card_max_scroll]` (which the renderer recomputes each frame). `scroll_card_down()`/`scroll_card_up()` are the `n=1` shorthands the mouse wheel uses. `half_page()`/`page()` derive their distance from `card_viewport_height`.
- `handle_scroll_down()` / `handle_scroll_up()` (mouse wheel) — routed by overlay, then view: with no overlay on the `Checklist` view, scroll an overflowing card, otherwise `navigate_forward`/`navigate_backward` (crossing list edges like `j`/`k`); over `Help`, `scroll_help_*_by(1)`; over `ListPicker`, `picker_move(±1)`; ignored elsewhere. The wheel isn't hit-tested, so wheeling over the overview panel moves the task cursor too.
- `maybe_auto_copy()` — with `--auto-copy`, queue a copy (`Effect::Copy` with `CopyKind::Auto`) of the current item's code when it has exactly one candidate; announces a **successful** copy with the same status message as manual `y`, and stays silent for no-code / ambiguous / failure so passive navigation isn't spammed. A hidden-characters refusal is always reported. Called from `focus_item` for every `CursorMove::Navigate`, and directly by `commit_search`. A reload never calls it: it isn't navigation, and an external change to the file (another instance toggling a task, a sync tool) used to overwrite the clipboard with the current card's command (#60).
- `toggle_current()` (Space/Enter) — on a `DisplayOnly` card, which has nothing to toggle, it **advances** via `navigate_forward` (crossing into the next list at a list edge) instead of doing nothing; a `None` current is still a no-op. Otherwise toggles *done*: `Done` → `NotStarted`, anything else (including `Started`) → `Done`. Writes back via `set_current_state` and confirms with `Marked done` / `Marked not done`, then `maybe_transition_screen()` on completion. When the list isn't complete, that advances via `advance_to_next_open`: the next item after the cursor that isn't a `Done` task (notes still stop the cursor), else the list's first open task — never onto a done task, where the next `Space` would silently uncheck it.
- `start_current()` (bound to `s`) — toggles *started*: `Started` → `NotStarted`, anything else (including `Done`) → `Started`. Writes back but **never** completes or auto-advances (stays on `Checklist`), so a started task is marked in place.
- `set_current_state(state)` — shared write path for both: sets the current `Checkbox` state, `write_back`, and on success refreshes `file_mtime` (self-write guard) and `last_update_at` (the "Updated" tag), via the shared `commit_write` helper (which also queues an `Effect::GitSync` with the change description — see Git Sync below). Returns `bool`: on a write failure it **rolls the mutation back** (restores the pre-mutation checkbox snapshot via `apply_snapshot`, so memory never diverges from what's actually on disk), sets a sticky error (`Write failed — change not saved to disk`), and returns `false`; both callers skip their screen transition in that case rather than acting as if the toggle had succeeded.
- `maybe_transition_screen()` — after completing, check if all checkboxes in list done → `ListComplete`; all lists done → `AllComplete`; otherwise `navigate_next()`
- `jump_to_list(n)` — set `current_list_index`, land `current_item_index` on the list's first undone item (else item 0), set `View::Checklist`
- `advance_to_next_incomplete_list()` — from a complete list, skip fully-complete lists to the next with remaining work, landing on its first undone item; **wrapping back to an earlier incomplete list** when nothing follows, and reaching `AllComplete` only when no list anywhere still has unfinished work. Wired to the `ListComplete` screen's `l`/`Enter`. Deep review, round 3: the search used to run forward only, so completing the *last* list while an earlier one was untouched fell straight through to `AllComplete` — a screen headed "All Tasks Complete" over a body that contradicted it (`List 1  0 / 1`, then `Total: 1 / 2 tasks`). Confirming nothing was missed is the whole point of a pilot-style checklist, so this is the one claim the screen must never make falsely. Wrapping matches `Tab`'s document-wide behaviour; the sibling `Shift-L` path (`jump_to_next_incomplete_list`) already got this right via `no_further_incomplete_list_message`. `render_all_complete` additionally derives each row's marker from that list's own `done == total` rather than a hardcoded done icon, so the summary can never again rubber-stamp a green check over its own numbers.
- `request_reset()` / `reset_all()` — the `R` confirmation flow. `finish_editor(...)` / `finish_suspend(outcome)` — the post-editor and post-resume reload/feedback, called by the main loop after it carries out `Effect::OpenEditor` / `Effect::Suspend` (see Editor integration and Suspend).
- `apply_copy_outcome(kind, text, outcome)` — the one place a copy's `CopyOutcome` becomes a status message, chosen by its `CopyKind` (see Effects).

**The fingerprint is derived from the document, never from a second read.** Deep rounds 3, round 2 — the same defect the reload path was fixed for in the first deep review, recurring as a race between two reads rather than between two branches. Both `AppState::new` and `reload_from_disk` parsed the file and then called `current_content_hash`, which reads it *again*. If the file changed in between, the fingerprint described content the in-memory document was not: `disk_content_diverged` then reported "unchanged" and the next toggle silently overwrote the newer content — precisely the outcome the fingerprint exists to prevent. Reachable with any editor that saves in stages. The cure is to stop reading twice: `Document.raw_lines` concatenates to exactly the bytes it was parsed from (the invariant `write_back` already relies on), so the fingerprint is taken from `writer::document_contents` and the two cannot describe different revisions by construction. `current_content_hash` survives only in `disk_content_diverged`, where reading the file is the entire point.

**Write-time conflict detection.** Before any of the actions above actually writes, `commit_write` calls `disk_content_diverged()`, which re-hashes the file's current on-disk bytes (SHA-256, via the `sha2` crate — a cryptographic digest is stronger than this check strictly needs, since nothing here is adversarial, but costs nothing once the fingerprint abstraction exists) and compares against `AppState.file_content_hash` — the hash of the content we last confirmed was there, refreshed at load and after every write or reload. A mismatch means something else (another `markcheck` instance, an external editor) changed the file since we last saw it: overwriting now would silently discard that change (the classic lost-update problem for two writers sharing one file). In that case the in-memory mutation is rolled back (`apply_snapshot(pre_state)`), the file is force-reloaded (`force_reload()` — the same body as `reload_if_changed()` but bypassing its mtime/size "unchanged" short-circuit, since the hash can catch a change that mtime/size miss within one coarse-mtime tick), and a sticky error is shown (`File changed on disk — reloaded; change not saved, please retry`) instead of writing. On its own this is only a **pre-write content check** — external review, round 4: there's a gap between this check returning "unchanged" and `write_back`'s own rename actually landing, in which another writer could still save a change that gets silently overwritten. Between two markcheck instances that gap is now closed by the advisory write lock held across both steps (next paragraph); against any other writer — an editor, a script — it remains, since nothing else takes that lock. The check is layered on top of the mtime/size check `reload_if_changed()` already does for *detecting* external changes on a watcher event or the 2-second recheck — this one specifically protects the moment of *writing*, which mtime/size alone can't, since two writes landing within the same timestamp resolution window can otherwise look identical.

**An advisory lock makes that check-then-write a real compare-and-swap.** Deep round 4, closing the gap the paragraph above documented as accepted. `commit_write` hashes the file on disk and *then* replaces it; two markcheck instances could both pass the hash check and both rename, and the second silently discarded the first's toggle. `writer::WriteLock` is held across both, so only one instance is ever inside that sequence. A blocked instance reports `Another markcheck is saving this file — change not saved, please retry`, rolls its in-memory toggle back, and queues no git-sync request — the same shape as the existing diverged-on-disk refusal, which is already a well-trodden path. **The lock file lives in a directory private to the user, keyed by the digest of the checklist's canonical path — not beside the checklist.** `lock_path` canonicalizes the path itself before hashing it, so a symlink to the checklist, a `..` component, or a relative spelling all resolve to one lock; mutual exclusion keyed on an unresolved path would let two spellings of one file each take their own lock and both enter the section that exists to hold one. `main.rs` canonicalizes at startup too, so this is defence in depth rather than the only guard — but an invariant maintained in another module is one refactor from being dropped, and the lock is the wrong place to find that out. A sibling lock file lands inside the user's repository, where a `git add -A` pre-commit hook can sweep it into a commit, which `verify_commit_scope` would then correctly abort the sync over; keeping it elsewhere keeps it entirely out of git's way. The directory is `$XDG_RUNTIME_DIR` when it is a real directory owned by the user and closed to everyone else, otherwise `<temp>/markcheck-<uid>`, created `0700` and checked the same way before use (`lock_dir_in`; a squatted, symlinked or widened directory makes the lock `Unavailable`). It used to be the shared temp directory itself, at a name anyone could compute, so another local user could plant a lock naming an always-running PID and block every save, which the victim couldn't even remove from sticky `/tmp`; they could also plant a symlink to a FIFO, whose `open` froze the UI (#1). An existing lock is read through `open_regular` (the `O_NOFOLLOW | O_NONBLOCK` open `read_checklist` uses, #123) and capped at 256 bytes, and one that isn't a regular file is `Unavailable` rather than `Busy`. The trade is that it serialises only one user's instances on one machine. Two machines writing one checklist over a network share are not covered — and were not before either. An abandoned lock (a crash while holding it) is recovered by asking whether its owner is still running, not by how old it is, or one crash would wedge every future write. The lock file holds the writing process's pid, and `token_owner_is_gone` (through `pid_is_gone`) recovers the lock only when that process is *proven* absent. On Linux the proof is `/proc/<pid>` missing while `/proc/self` exists, with no subprocess, so a system without `ps` (slim and distroless images) can still recover a lock left by a killed instance. Elsewhere, or with `/proc` unmounted, it runs `ps -p <pid> -o pid=` and counts the owner gone only on an empty listing with nothing on stderr and an exit of 0 or 1: an exit code alone is not evidence, because BusyBox `ps` has no `-p` and exits 1 with a usage message for every PID, which read as "no such process" would steal every live lock. Anything else — an unreadable file, a malformed token, a usage error or other stderr output, an unexpected exit code, `ps` failing to run — leaves the lock **live**, so uncertainty never licenses stealing one somebody holds. **Age is deliberately not a signal.** External review of `d885c88` caught the earlier age-based version displacing a writer that legitimately held the lock longer than the threshold — a slow disk, a stopped process, a debugger — which is precisely the concurrent-write race the lock exists to prevent, reintroduced by the recovery path. `/proc` and `ps -p` are the liveness tests rather than `kill -0` because `kill` cannot distinguish "no such process" from "exists but not yours". `create_new` is atomic, so when two instances both decide to recover exactly one wins; the winner keeps the lock only if a re-read still finds its own token, and the loser correctly reports busy. If the lock itself is unusable (no writable temp directory) the write proceeds **unlocked**: this is a safety net over an existing check, not a gate that may deny saving. `acquire` returns those three cases as `LockOutcome::{Acquired, Busy, Unavailable}`, so the caller has to distinguish "someone else is writing" from "locking is not available here" rather than collapsing them into one failure.

**Lock recovery is by proven death, never by elapsed time.** External review of `d885c88`, and a correction to what this paragraph previously claimed was an acceptable residual. Recovery used to treat any lock older than 30 seconds as abandoned, which meant a **live** holder could be displaced simply for being slow — a stalled `sync_all`, a FUSE or network filesystem, storage under recovery. Both instances then entered the critical section, both passed the content check against the same pre-write hash, and the second rename silently won: exactly the lost update this lock was introduced to prevent. The unique token stopped one instance deleting the other's file; it never stopped both from writing, and the earlier framing of the residual as "two takeovers of the same *abandoned* lock" understated it. Age is no longer consulted at all. A lock is recovered only when its recorded owner is *demonstrably* gone, and anything short of proof — owner alive, `ps` unavailable, file unreadable or unparseable — honours it. Liveness is checked with `/proc` or `ps -p`, not `kill -0`: `kill` cannot distinguish "no such process" from "not permitted to signal it", so a lock held by another user's markcheck would look dead and be stolen. The token and the ownership-checked `Drop` remain, since recovery still removes then re-creates and a guard must never delete a file it no longer owns. The cost is honest and stated in the refusal: if the owning process died and its PID was recycled by an unrelated live process, the lock is honoured indefinitely and saving stays blocked, so the message names the file to remove. That is strictly better than the alternative it replaces, where the same uncertainty silently permitted two writers.

Uncompleting an item always sets `View::Checklist`.

Lists with no checkboxes are dropped at parse time, so this case no longer arises in normal use; the empty-list handling in `current_item()`/the UI remains only as a defensive fallback.

## Effects (`src/effect.rs`)

`AppState` never touches the clipboard, a process, git or the terminal. A handler that needs one of them pushes an `Effect` onto `AppState.effects`:

```rust
pub enum Effect {
    Copy { text: String, primary: bool, kind: CopyKind }, // y, click, y+digit, --auto-copy, o's no-browser fallback
    OpenEditor { line: Option<LineNumber> },              // e, at the current task's line
    Suspend,                                              // Ctrl-Z
    OpenLink(String),                                     // o
    GitSync(PendingSync),                                 // every successful write-back, and an edit made in `e`
    Quit,                                                 // q / Esc, or the quit-reset prompt's y (after a successful reset) / n
}
```

The main loop calls `effect::drain(state, host)` once per iteration, after the input event. It pops effects in order, including any queued while draining (a link with no browser falls back to a copy; an `e` edit queues a sync), through one exhaustive `match`, so a new kind of effect does not compile until it is handled there. Copies run in `drain` itself (`clipboard::copy`, then `AppState::apply_copy_outcome`); everything that owns the terminal or a worker goes through the `effect::Host` trait, which `main.rs`'s `TerminalHost` implements against the real terminal, processes and `GitSync`. Tests drain against `test_support::RecordingHost` and the per-thread fake clipboard instead, so they assert on the effects a key produced without touching anything outside the process. `Drained { ran_any, quit }` tells the loop whether to redraw and whether to stop; a sync queued alongside `Quit` has already been handed to the worker by then, so the exit wait covers it.

`CopyKind` decides how an outcome is reported: `Command` (`y`, a click on a command, `y` + digit) reports every outcome; `Auto` announces only a success, appended to the motion's own message, or a hidden-characters refusal; `LinkFallback` words each outcome around the link (`No browser here — link copied to clipboard`).

`GitSync` is the one effect with slot semantics: `queue_git_sync` replaces one still in the queue, since only the latest content needs committing, and an external reload removes it (`cancel_git_sync`; see Git Sync).

Before this, each outward action had its own request field (`editor_requested`, `link_open_request`, `git_sync.pending`, `should_quit`) with a `take_*` method the main loop had to remember to poll, in an order that was implicit in `run`, while copies ran directly inside `AppState` (#138).

## Reload From Disk (`src/watcher.rs`, `src/app.rs`)

Detects external edits to the open file (e.g. editing the runbook in another terminal while `markcheck` is running) and reloads it live.

**Watching, plus a slow poll:** `FileWatcher` (`src/watcher.rs`, using the `notify` crate) watches the file's **parent directory**, non-recursive — not the file path directly. Watching the path directly can silently lose the watch when the file is replaced via a temp-file-then-rename save, which both `write_back` and most editors (vim, VS Code) use. Events are filtered to the target filename since the directory watch also sees unrelated siblings; a watcher error or a `Rescan`-flagged event (the kernel's inotify queue overflowed) also counts as a possible change, since it means events were lost. The watcher is only the fast path. `ReloadTrigger` wraps it and `main.rs`'s event loop calls `ReloadTrigger::check` every tick, which runs `AppState::reload_if_changed()` on a watcher event **or** every `RECHECK_INTERVAL` (2 s) regardless — one `stat` per interval. The timer covers the cases a watch alone can't: the watch failed to start (inotify instance/watch limits are the usual cause), the file is on a network or FUSE filesystem that never reports edits made elsewhere, or the watched directory was removed and recreated (inotify drops the watch, and without the timer a `file_deleted` state would never clear). When the timer finds a change no event reported, it sets the watch up afresh, restoring the fast path where it can. `check` returns whether anything on screen may have changed (a reload, or `file_mtime`/`file_size`/`file_deleted` moved, which is when the skipped/failed/deleted messages are set), so the idle recheck never forces a redraw.

**Self-write filtering:** a directory watch sees our own writes too (the temp-file creation and the rename both generate events), so `AppState.file_mtime`/`file_size` still track the last known mtime and size and are updated immediately after every write we make ourselves. `reload_if_changed()` compares the file's current mtime *and* size against those; both matching means nothing external happened, regardless of what triggered the check. The size cross-check narrows (but doesn't eliminate) the window where a same-instant external edit could be missed on a coarse-mtime filesystem (whole-second resolution is common): an edit landing in the same resolution window that also happens to leave the size unchanged is still missed, but that's a much narrower coincidence than mtime alone. This residual window matters for *detecting* a change to reload it; the equivalent problem at the moment of *writing* is closed separately by the content-hash check in `commit_write` — see "Write-time conflict detection" above.

```rust
pub fn reload_if_changed(&mut self) {
    // symlink_metadata, never followed: NotFound -> FileGone::Deleted,
    // anything but a regular file -> FileGone::NotRegular, other errors ->
    // transient, try again next tick. Each sets its sticky error once.
    if let Some(gone) = classify(&self.document.file_path) {
        if self.file_gone != Some(gone) {
            self.file_gone = Some(gone);
            self.set_error(gone.message().to_string());
        }
        return;
    }
    let (modified, size) = current_stat(&self.document.file_path)?; // one lstat() call
    // A regular file again: clear the flag and force a reload so the
    // restored content is always picked up, even if mtime/size look unchanged.
    let was_deleted = self.file_gone.take().is_some();
    let unchanged = self.file_mtime == Some(modified) && self.file_size == Some(size);
    if !was_deleted && unchanged { return; }

    match parser::parse_document(self.document.file_path.clone()) {
        Ok(new_document) if !new_document.lists.is_empty() => {
            let task_lost = self.remap_position(&new_document);
            self.document = new_document;
            self.keep_overlay_across_reload(search_origin); // view = Checklist; see below
            let reloaded = if was_deleted { "File restored — reloaded" }
                           else { "Reloaded: file changed on disk" };
            self.set_status(if task_lost { format!("{reloaded} — task not found, cursor moved") }
                            else { reloaded.to_string() });
            self.last_update_at = Some(SystemTime::now());
        }
        Ok(_) => {  // new content has zero lists; keep the last good document
            self.set_status("Reload skipped: file has no checklist items".to_string());
        }
        Err(err) => {  // e.g. non-UTF8 content; keep the last good document
            self.set_status(format!("Reload failed: {err}"));
        }
    }
    self.file_mtime = Some(modified);
    self.file_size = Some(size);
}
```

**File deletion:** a plain "unreadable" (`current_stat` returns `None`) is ambiguous — the file may be mid-rename by another writer or genuinely gone. `reload_if_changed` only treats it as a deletion when `fs::symlink_metadata` returns `NotFound`, and then sets a **sticky error** status (`File was deleted — changes cannot be saved until it exists again`, via `set_error`) exactly once and sets `AppState.file_gone` to `FileGone::Deleted`. While that flag is set, every mutating action (`set_current_state`/`toggle_item`/`reset_all`/`undo`/`redo`) refuses to write, repeating that same message — so we never recreate the file behind the user's back (the `write_back` metadata-abort above is the second line of defense). The five identical guard blocks this used to be were consolidated into one `blocked_by_deletion()` helper (sets the error and returns `true`; call sites read as `if self.blocked_by_deletion() { return ...; }`) — no behavior change. When a regular file reappears the flag clears and the content is reloaded unconditionally (`File restored — reloaded`), regardless of mtime/size. These file-deleted messages are rendered `palette.error` (red) like every other failure message via the `status_is_error` flag — see `ui/statusbar.rs`.

**A path swapped for a symlink or special file (#123).** Startup canonicalization pins the path, but nothing stopped someone with write access to the directory from replacing the checklist afterwards. Every later read followed whatever was there: a symlink to the operator's private file was reloaded, then written back into the shared checklist (and committed by git sync) on the next toggle, and a FIFO blocked the UI thread forever on the next tick. Every read of the checklist now goes through `writer::read_checklist`, which opens with `O_NOFOLLOW | O_NONBLOCK` (from the `libc` dependency) and checks the *open handle* is a regular file, so the check and the read can't disagree: `parse_document` (startup and reload), `current_content_hash` and `commit_write`'s pre-write content (the pre-write checks), and git sync's staleness read in `run_sync`. A refusal is the `writer::NotRegularFile` error (`writer::is_not_regular`), which names what it found (`not a regular file: it is a named pipe`; also a symlink, a directory, a device or socket), so starting markcheck on such a path explains itself too. `reload_if_changed` classifies the path with `symlink_metadata` first; anything but a regular file sets `FileGone::NotRegular` and its own sticky message (`File was replaced by a symlink or special file — not loaded; changes cannot be saved until it is a regular file again`), and it then blocks writes and git sync through the same `blocked_by_deletion` guard as a deletion. `write_back` takes its metadata with `symlink_metadata` too and refuses a non-regular path, so a swap landing between two ticks is caught by the write itself, which `commit_write` turns into the same `FileGone::NotRegular` state. Putting a regular file back reloads it as `File restored — reloaded`.

**Cursor remapping:** `remap_position()` keeps the cursor on the same list (matched by title) and task after a reload. The task is found by **content** — the same `header`, `display_text` and `depth` — choosing the candidate nearest the old line number when several match, because inserting or deleting a single line above the cursor shifts every following line number. It used to match by exact line number only, so adding a step with `e` or a `git pull` dropped the cursor to the list's first item without a word (#60). With no content match it takes the item on the old line (a task edited in place), and failing that the item nearest the old line number; that last case, and a list that can no longer be found (which falls back to the start of the document), return `true` so the reload status reads `Reloaded: file changed on disk — task not found, cursor moved` instead of moving the cursor silently. Title alone doesn't identify a list — nothing in the Markdown format forbids two `## H2`s sharing a title — so matching is disambiguated by *occurrence*: the old list's rank among same-titled lists in the old document (how many earlier lists shared its title) is computed once, and the new document's list at that same rank among its own same-titled lists is the target, rather than always the first same-titled match. This handles the common case (the duplicate lists' relative order is unchanged across the reload) without needing a real stable list identity; a rank that no longer exists (e.g. a duplicate was removed) falls back to the first list overall, the same as a title that vanished entirely.

**A reload keeps an open overlay open.** Found in review; the same class as the chord disarming above. `reload_from_disk` used to set `screen = Checklist` unconditionally, so a reload arriving while `/` search or the `T` picker was taking text silently turned every following keystroke into a command — `s` marked a task started and wrote the file. `keep_overlay_across_reload` now sets the view to `Checklist` and decides per overlay, after the new document is adopted: `Search` stays open, re-runs `update_search` against the new content, and gets its `Esc` origin remapped through the same `remapped` helper `remap_position` uses (the raw indices could point past the end of the new document); `ListPicker` and `Help` stay open, the picker with its selection clamped; `ConfirmReset`/`ConfirmQuitReset` are dropped, since they were asked about the old content, with a sticky `File changed on disk — reset cancelled` (or `quit cancelled`) error so the dialog never vanishes unexplained; a `ListComplete`/`AllComplete` view still returns to `Checklist` as before, under whatever overlay stays open. Since #66 split the state into a view and an overlay, a reload only has to leave `overlay` alone; before that, one `screen` field held both and every view change clobbered whatever overlay was open. A reload never auto-copies, on any screen (see `maybe_auto_copy`).

**Graceful degradation:** if the watch can't be set up (e.g. inotify limits reached) reload falls back to the 2-second recheck alone, and `main.rs` says so with a sticky startup warning built by `launch::watch_warning` (`Live reload slowed: can't watch the file (<error>) — checking every 2 s instead`); if reloaded content has zero lists or fails to parse, the reload is skipped and the last good document is kept, with a status-bar message explaining why (`Reload skipped: file has no checklist items` / `Reload failed: {err}`) — this is a convenience feature, not core functionality, so it never crashes or blanks the screen.

## Recurring defect classes

Every deep review of this project has found new bugs, and by round three of
the third pass a pattern was unmistakable: the same *shapes* keep coming
back, usually in code written to fix an earlier instance of the same shape.
This list is the audit trail turned into a checklist, so a future review
starts from what has already bitten us instead of rediscovering it. Each
entry names the shape, what it cost, and what to grep for.

1. **Symbolic identity re-derived instead of captured.** Asking git the same
   question twice — `HEAD` for a check and `HEAD` again for the action — is
   asking about two different commits. Cost: the fast path and the startup
   catch-up published commits they had never validated. Cure: resolve once,
   name that SHA everywhere. *Look for:* the same query issued twice, a
   literal `"HEAD"` anywhere but a capture.

2. **Two reads of one file assumed to describe each other.** The same shape
   for the filesystem. Cost: the content fingerprint described a revision
   the in-memory document wasn't, so the next write silently overwrote a
   newer edit; and a stat taken after a parse made an external change look
   already seen. Cure: derive from the bytes you already have
   (`Document.raw_lines` concatenates to its own source), or cross-check.

3. **Failure collapsed into a verdict.** `unwrap_or`, `.ok()`, and an
   ambiguous `None` turn "couldn't tell" into "fine". Cost: an unanswerable
   history check read as "nothing unrelated here" and published; an empty
   `rev-list` read as a root commit, whose undo path *deletes the branch*.
   Cure: three states, not two — and pick the fail direction per caller,
   since refusing is the consequential action for some and pushing is for
   others. *Look for:* every `unwrap_or`/`.ok()` on a fallible git call.

4. **One question answered from two sources.** Cost: `push` read the
   *config* for "is there an upstream?" while the guard resolved `@{u}`;
   when they disagreed the guard stood down and the push published unrelated
   work. Cure: one authority per question.

5. **Acting on something no longer yours.** Cost: a group kill aimed at a
   reaped (possibly recycled) PID; a rollback that rewound commits markcheck
   never made; a lock guard deleting another instance's lock; a realignment
   overwriting a version the user had staged. Cure: check ownership
   immediately before the destructive step, and prefer leaving a mess you
   can report over destroying something you can't restore.

6. **Unbounded waits.** Cost: `join()` on a pipe thread that a lingering
   descendant kept alive forever, defeating the timeout on every subprocess.
   Cure: bound every wait, and spend one budget across a teardown rather
   than one per step. *Look for:* `join()`, `recv()`, `read_to_end`.

7. **Superseded state left live.** Cost: a stale retry timestamp firing
   every frame; a queued sync request describing content that no longer
   existed; an armed input chord pointed at a card the user never chose.
   Cure: whatever a reload invalidates, clear it in the same place.

8. **Ambient environment trusted.** Cost: an inherited `GIT_DIR` made
   git-sync read one repository and commit into another. Cure: neutralise
   what redirects the target; leave what is the user's to set.

9. **Tools asked questions they cannot answer.** Cost: `git status` was the
   untracked oracle, and it says nothing at all for a gitignored file or
   under `status.showUntrackedFiles=no` — so git-sync sat silent forever.
   Cure: ask the component that actually knows (here, the index).

10. **Superseded prose left in present tense.** Not a runtime bug, but the
    same failure mode in documentation, and it caused real confusion: this
    document described a bare `git push` for several rounds after the code
    had stopped doing that. Cure: when behaviour changes, rewrite the
    paragraph that described it rather than appending a newer one below.

11. **A test that pins an outcome but not its cause.** Cost: both
    `undo_commit` compare-and-swap tests asserted only `result.is_err()`
    alongside an unchanged `HEAD`. That pair is satisfied by *any* failure,
    so an `undo_commit` gutted to return `Err` unconditionally passed both —
    they proved the branch was intact without proving the CAS is what kept it
    intact. Cure: assert on the reason (here, that the message came from
    `update-ref`), not just the outcome. See "Verifying the guards" below for
    how these were found.

### Verifying the guards

The safety guards in `git_sync/guards.rs` and `writer.rs` are the code most likely
to rot silently: they only run on paths that normal use never reaches, so a
guard that stopped working would not show up in ordinary testing. Class 11
above is what that rot looks like from the test side.

The check is mutation testing, and it needs no tooling beyond a script that
edits one function, runs `cargo test`, and restores the file. Disable a guard
so it permits everything — `verify_commit_scope` returning `Ok(())`,
`unpushed_history_blocks` returning `None`, `git_command` skipping its
`env_remove` loop, `token_owner_is_gone` returning `true` — and the suite *must*
fail. A mutant that survives is a guard nothing actually pins, which is the
same as not having the guard at all.

Ten such mutations were run in the fourth pass, covering every git-sync guard
and every `WriteLock` invariant, including subtle ones that model real
regressions rather than wholesale deletion (reverting `parse_first_parent` to
the ambiguity that let an unreadable listing read as a root commit and delete
the branch). All ten were caught, by 2–8 tests each. Re-run this after
changing a guard, and prefer it to a coverage number: coverage proves a line
executed, a surviving mutant proves nothing was checking what it did.

## Git Sync (`src/git_sync/`)

**Split by concern, in one direction only.** This started as a single 7,000-line file and grew that way because every review round added another guard to it. It is now a module directory whose parts depend on each other in a strict order, so a change can be reasoned about without holding the whole subsystem in mind:

```text
process  ->  inspect  ->  guards  ->  commit  ->  sync  ->  mod (GitSync)
                            |           |          |
                            +---------> push ------+

shared: imported by any of them, imports none of them
```

`shared.rs` is the leaf beneath all of them: `SyncOutcome`, the request-hash lock (`lock_hash`) and the test race points (`race_point`), with no imports from its siblings. `process.rs` runs git and depends on nothing else in the module but that leaf. `inspect.rs` asks the repository questions. `guards.rs` decides what must not happen. `commit.rs` builds the commit (and re-checks guards around it), `push.rs` publishes one, and `sync.rs` sequences the whole request; `mod.rs` holds `GitSync`, which drives `sync` and `push` from its worker thread. Nothing calls upward — these three items used to live in `mod.rs`, so the lower layers reached back up into it — and and only `GitSync` and `SyncOutcome` are visible outside the module — everything else is `pub(super)`, so the layering cannot leak into the rest of the crate. The split was a pure move: coverage was identical before and after (97.78% region), and all twelve guard mutations were still caught.

Auto-commits and pushes the checklist file after a write-back, when it lives in a git repo — so a list stays in sync across hosts that already share it via git. Off by default; activated per-file by `--git-sync` (forces it for this invocation) or a `git_sync_paths` prefix list in the config file (below). "After a write-back," not "after every one": requests that arrive while a sync is already running coalesce into a single commit rather than one apiece — see "Background thread, not the UI thread" below.

**Detection, once at startup:** `GitSync::detect(file_path)` runs `git rev-parse --is-inside-work-tree` in the file's parent directory. `Err(reason)` (no `GitSync` constructed, feature inert for the session) when that fails — not inside a repository, inside the `.git` directory (rev-parse succeeds but prints `false`), `git` not on `PATH`, a timeout, or git refusing the repository (e.g. "dubious ownership" without a `safe.directory` exception) — the same fails-open convenience-feature stance as the file watcher, but not a silent one: `main.rs` shows the reason as a sticky startup message (`Git sync off: <reason>`, built by `launch::git_sync_warning`). For a git refusal the reason is git's whole stderr joined onto one line, not just its first `fatal:` line, because git follows that line with the exact `git config --global --add safe.directory <path>` command that fixes it. This is a single blocking call at startup, not re-checked per toggle.

**Kept out of `AppState`, driven from `main.rs`:** mirrors `FileWatcher` — `main.rs` owns an `Option<GitSync>` and polls it once per loop tick, alongside the existing watcher poll:

```rust
if let Some(sync) = git_sync.as_mut() {
    if let Some(outcome) = sync.poll() {
        state.apply_git_sync_outcome(&outcome);
    }
    sync.retry_push_if_due(Instant::now());
}
if let Some(sync) = git_sync.as_ref() {
    state.git_sync.busy = sync.is_busy(); // redraws only when it changes
}
```

`AppState::apply_git_sync_outcome` is the one place an outcome reaches the UI: it updates the title-bar indicator state (`last_at`, `problem`) and calls `set_error` with the outcome's status message, so it's unit tested headlessly rather than living in `main.rs`.

`git_sync::status_message` maps each outcome to the sticky message the user sees (`None` for `Synced`, `Skipped` and `RetryAbandoned`), next to `exit_report`, which does the same for the line printed after quitting; both are unit tested per variant rather than only through the PTY tests.

`AppState` never touches git/process directly — it just queues an `Effect::GitSync(PendingSync)` in `commit_write`, the same shared tail every mutating action (toggle/start/reset/undo/redo) already goes through, and the main loop's effect drain hands it to `GitSync::request` (see Effects). `PendingSync { content, content_hash, previous_content, description }` carries not just the change description (e.g. `Check "Restart service"`) but the *exact file content* `write_back` just wrote, plus its hash — see "Isolated commits, not working-tree reads" below for why — and the content that write replaced, which only the staged-checklist guard reads (see "A staged checklist is not overwritten either" below). This is unconditional: `AppState` has no notion of whether git-sync is even enabled, like every other effect: app state asks for an external action, `main.rs` performs it.

**The editor (`e`) queues a request too, separately:** an edit made in `$EDITOR` never goes through `write_back`/`commit_write` (the change already landed on disk before markcheck sees it), so it used to sit uncommitted until some later markcheck-driven write happened to piggyback on — or, if the user only edited and quit, was silently never synced at all despite `--git-sync` being active. `AppState::reload_if_changed()` returns whether it actually loaded new content (as opposed to nothing changing, or a skipped/failed reload), so `AppState::finish_editor` (called by `open_in_editor` in `main.rs` once the terminal is restored) checks that after its `reload_if_changed()` call and, when true and the editor exited successfully, calls `AppState::request_external_edit_sync(program)` — a second, narrower `Effect::GitSync`, with `content` from `writer::document_contents(&self.document)` (the just-reloaded document, reconstructed with its original line endings/trailing-newline state — see Markdown Write-Back) and a description built from the file name of `program`, the *resolved* editor binary (e.g. `Edited in vim`, never `Edited in /home/example-user/bin/vim`: a directory from the user's environment is not theirs to publish to a shared remote), not the literal `$EDITOR`/`$VISUAL` env var name (there's no structured diff for a free-form edit the way a toggle has, so this is as specific as the description gets). A non-zero exit is the editor's conventional abort signal (vim's `:cq`, which git itself uses to cancel a commit message), so an edit the editor exited with an error on is reloaded but never queued; the status bar says so (`… — not synced`). This is deliberately scoped to the editor-return call site only, not the generic watcher-driven `reload_if_changed()` call in the main loop: a change *we* just caused by spawning the editor is analogous to a toggle and should sync promptly, but a change picked up from *elsewhere* (another host, another process) isn't necessarily ours to re-commit.

**Commit messages are capped at 80 characters:** `commit_message` (`git_sync/sync.rs`) builds `{file_name}: {change_desc}`; when a change description is long enough to push the whole line past 80 chars — the usual cause is a long task title landing in a `Check "…"` description — the file-name prefix is kept intact and only the description is cut, with a trailing `…` marking the cut, so `git log` stays readable even for a long checklist item. Since the cut point is a plain character count, it can land inside that `"…"` item-title quoting; `commit_message` counts `"` in the truncated text and, if odd (an opening quote with no matching close), shortens the cut by one more character and appends a closing `"` after the `…` so the message never ends with a dangling open quote.

**Background thread, not the UI thread:** `GitSync::request` spawns a `std::thread` that runs the commit+push sequence and sends a `SyncOutcome` back over an `mpsc::channel` — the same non-blocking shape as `FileWatcher` (background worker → channel → `poll()` drains it via `try_recv` once per frame), so a slow or offline `git push` can never freeze the TUI. A `request` that arrives while a sync is already running is coalesced into a single `pending: Option<PendingSync>` slot rather than spawning a second concurrent thread (two `git commit`/`push` runs on the same repo could race on the index/HEAD); `poll()` spawns the queued request once the in-flight one reports back. Only the latest pending request matters — its `content` already reflects everything the dropped one would have committed, since both were captured from the same, ever-more-current document.

**Every git subprocess also runs with the ambient git environment neutralised.** Deep rounds 2, round 2, confirmed against real git. markcheck inherits its environment, and several git variables redirect which *repository* a command acts on. With `GIT_DIR` exported, `git log -1` run inside repository *a* reports *b*'s HEAD — refs and the object database come from the other repository while the work tree stays *a*, so markcheck would resolve its tip from one repository and commit and push into another. With `GIT_INDEX_FILE` exported, `ls-files --stage` for a perfectly tracked checklist returns nothing (reported untracked) while `status` shows a `D`/`??` status, which the `??` prefix check does not even catch, and `align_real_index_entry` would write into the stray index. None of this is exotic: git hooks set both, `git rebase --exec` and `git bisect run` inherit them, and exporting `GIT_DIR`/`GIT_WORK_TREE` for a bare dotfiles repository is a widely-used pattern. `git_command(repo_root)` is now the only way this module builds a `git` invocation; it sets the working directory and removes `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE` and `GIT_PREFIX`, leaving repository discovery to `current_dir` alone. The temp-index commit path still sets `GIT_INDEX_FILE` deliberately, applied *after* the removal so it wins. Only variables that would make git act on a different repository are removed: `GIT_CEILING_DIRECTORIES` is left alone because at worst it stops discovery and git-sync simply doesn't activate, and author/committer identity and config overrides are the user's to set and don't change which repository is written.

**A pathspec naming the checklist is matched literally.** #70, reproduced against real git: git reads every path after `--` as a glob, so a checklist named `notes[1].md` also matched a tracked `notes1.md`, which `ls-files` lists first. `index_entry` took that first record as `relpath`, so the sync staged the checklist's content as `notes1.md`, passed `verify_commit_scope` (the commit touched only the wrong `relpath`), pushed it and reported `Synced`. The three invocations that take the checklist's path as a pathspec (`status --porcelain` in `run_sync`, and the `ls-files --stage` in `index_entry` and `index_blob`) are built with `literal_pathspec_command`, which is `git_command` plus `GIT_LITERAL_PATHSPECS=1` and the removal of `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS` and `GIT_ICASE_PATHSPECS` (an ambient one would widen the match again, and git refuses to combine any of them with the literal setting). It is deliberately not folded into `git_command` itself: `git commit` runs the repository's hooks with markcheck's environment, and a hook's own glob pathspecs must keep their usual meaning. As defence in depth, `index_entry` returns an error when `ls-files` prints more than one record, since exactly one path was asked for.

**A checklist path that isn't valid UTF-8 is refused, not converted.** #8: `index_entry` used to read `relpath` from the `ls-files -z` record with `String::from_utf8_lossy`, so a file name containing non-UTF-8 bytes became a different path with U+FFFD in it. Every later step used that mangled path consistently — `update-index --cacheinfo` staged the content there, `verify_commit_scope` found the commit touched only `relpath`, and `blob_at`/`index_blob` found nothing to conflict with — so the sync committed and pushed a new junk file on every toggle while the real checklist was never updated. `relpath` flows through the module as `&str` (it is formatted into `<commit>:<relpath>` revision arguments too), so rather than carry raw bytes end to end, `index_entry` decodes the record strictly and returns an error naming the file when it isn't UTF-8; `run_sync` and the push-retry path report it as `SyncOutcome::Failed` before anything is staged.

**Every git subprocess is bounded, not just kept off the UI thread.** "Never freezes the TUI" only holds if the *background* thread itself can't get stuck forever — external review: `Command::output()` has no timeout, so a hung subprocess (broken SSH, a stuck credential helper, a hanging commit hook, a wedged network transport) would block the worker thread indefinitely, and quitting markcheck while one was hung would orphan the child process entirely (Rust neither kills children on drop nor joins/kills detached threads on exit). Every one of `git_sync/`'s ~30 `git` invocations now runs through `run_with_timeout` (or `run_with_timeout_and_stdin`, for `hash_object`'s one stdin-writing call), which `spawn`s manually and polls `try_wait` against a deadline rather than blocking on `Command::output()`. Three tiers: `PLUMBING_TIMEOUT` (10s) for every local, normally-instant command (`status`, `ls-files`, `hash-object`, `rev-parse`, `read-tree`, `update-index`, `symbolic-ref`, `update-ref`, `diff`, `show`), `PUSH_TIMEOUT` (60s) for the network-bound commands, `git push` and the `git ls-remote` that checks the remote branch, and `COMMIT_TIMEOUT` (300s) for `git commit` alone (#53): it runs the repository's `pre-commit`/`commit-msg`/`post-commit` hooks and `commit.gpgsign`, and a hook framework's first-run environment setup, a slow linter, or a signing key waiting for a hardware touch or a pinentry can all take far longer than 10s. The sync runs on the background worker, so the longer cap never blocks the UI; it only bounds how long a quit waits for nothing (quitting waits at most 5s regardless). A timeout maps to `CommittedNotPushed` for `push` (feeding the existing retry machinery — see above) and `Failed` for a plumbing command — except `commit_temp_index`, which reconciles a timeout against `HEAD` first (external review, round 4): a `git commit`'s mutation — the ref update — is already durable by the time any `post-commit` hook runs, since that hook is the *last* step before the process exits; if `run_with_timeout`'s kill lands while such a hook is still running past the deadline, the commit itself already succeeded, and reporting it as a plain failure would be wrong. `commit_temp_index` takes `parent`, `relpath`, `blob` and an explicit `timeout` (mirroring `run_with_timeout`'s own explicit-timeout design, and letting tests inject a short one rather than waiting out the real `COMMIT_TIMEOUT`) and, only on a `TimedOut` error specifically, re-resolves `HEAD` and confirms markcheck actually *owns* the commit it found there before adopting it. Ref movement alone is not that proof — external review, round 9: another process can commit something else entirely during the same window (most plausibly while our own commit is still blocked in a slow hook), and adopting *that* commit as `created_commit` would be worse than a false failure, since `verify_commit_scope` would correctly flag it as out-of-scope and `undo_commit`'s compare-and-swap would then succeed — the right SHA for the wrong reason — rewinding a real, unrelated commit off the branch. Ownership therefore takes **three** checks, each catching a case the others miss: `HEAD` moved past `parent` at all; `relpath` at the new `HEAD` is exactly `blob` (`blob_at`, `git rev-parse <commit>:<relpath>` — catches an unrelated commit made directly on `parent`, which never touched the checklist so the old blob is still there); and the new `HEAD` is a *direct child* of `parent` (`descends_directly_from`, `git rev-list --parents -n 1` — catches the mirror case a content check cannot, where our commit landed **and** an unrelated commit landed on top of it without touching `relpath`, leaving our blob in place at `HEAD`). All three passing returns that new `HEAD` exactly as the success path would, so `verify_commit_scope` still runs against it normally (a hook that also misbehaved during that same timed-out run is still caught and undone). Any of them failing reports the original timeout — including the "our commit landed but got raced" case, which is a deliberate false negative: the commit really is there, but refusing is the safe direction, since `run_sync` returns `Failed`, the next request retries from fresh state, and nothing is rewound. Both content and lineage checks are proven independently load-bearing by their own regression tests (`commit_temp_index_does_not_adopt_an_unrelated_commit_after_a_timeout` and `commit_temp_index_does_not_adopt_a_commit_that_landed_on_top_of_its_own`), each verified to fail when *its* check alone is removed. stdout, stderr and (for `hash_object`) stdin are redirected to **scratch files** in the temp directory, not pipes — see "Scratch files, not pipes" below for why that choice replaced an elaborate threaded drain. On timeout, the child is stopped via its whole **process group** (`spawn_in_new_session` + `terminate_and_reap`'s `kill -TERM -- -<pid>`, then `kill -KILL -- -<pid>` if the child is still running after `KILL_GRACE` (1s)) rather than just the direct child — `git` itself can spawn subprocesses (`ssh`, a credential helper, a hook's own children), and killing only the immediate `git` process would leave those grandchildren running, still doing whatever wedged the command. **`SIGTERM` comes first** (#119): an uncatchable `SIGKILL` leaves `.git/index.lock` or a ref lock behind in the user's real repository, and every index-writing git command then fails until the file is deleted by hand, whereas git's own signal handlers remove its lock files on `SIGTERM`. The group is only signalled while the child is still unreaped — once reaped, its PID (and so the group ID) can be recycled — so a descendant that ignores `SIGTERM` after `git` itself exited is left alone, the same as a descendant of a successful command. When `SIGKILL` was needed, the timeout message says so and tells the user to remove `.git/index.lock` if git reports it exists. Separately, `git_command` sets **`GIT_OPTIONAL_LOCKS=0`** on every invocation, as git's documentation recommends for background processes: without it, the `git status` run on every toggle takes `.git/index.lock` to refresh the stat cache, so the user's own `git add`/`commit`/`checkout` in another terminal could fail with "index.lock: File exists" while a sync was running. It disables only optional locking; `update-index`, `commit` and `update-ref` still take the locks they need. A `kill`-group call isn't exposed by `std::process::Child`, so the group kill shells out to the `kill` utility; that predates the `libc` dependency added for the session (see below), which could replace it.

**No controlling terminal for git sync's children.** Stdin is nulled, but git, ssh and gpg don't prompt on stdin: they open `/dev/tty` directly. A child that merely sat in its own process group could still write a "Username for ..." prompt, an unknown-host-key question or a curses pinentry straight over the TUI, then stop on `SIGTTIN` reading an answer nobody could type, until `PUSH_TIMEOUT` killed it (and every push retry did it again). `spawn_in_new_session` therefore calls `setsid()` in `pre_exec`. That makes the child a session leader with no controlling terminal, so every terminal prompt fails at once and is reported as an ordinary sync error, while graphical askpass and pinentry prompts keep working. `git_command` also sets `GIT_TERMINAL_PROMPT=0`, so git's own HTTPS prompt fails with a clear message instead of an open error. The session leader also leads its own process group, so the timeout's group kill is unchanged. `setsid` comes from a direct `libc` dependency (already in the build through crossterm and notify), and the `pre_exec` closure is the crate's only `unsafe` block: `setsid` is async-signal-safe and touches no parent memory, which is what `pre_exec` requires. `git_sync_children_cannot_reach_markcheck_s_terminal` (tests/pty.rs) runs a hook that tries `/dev/tty` while markcheck itself has a terminal.

**Scratch files, not pipes — and that removed a whole class of defect.** Output used to be piped, with stdout and stderr each drained by its own detached thread and a third thread writing stdin. Threads were unavoidable there, because a pipe has a small fixed buffer: a child that outproduces it blocks mid-write, `try_wait` never returns, and nothing arrives to unblock it unless something drains concurrently — the classic pipe deadlock.

That design produced three separate defects across successive reviews, every one the same shape. `git` hands its descriptors to whatever it spawns, so a descendant outliving `git` itself keeps the pipes open, and a thread blocked in `read_to_end` waits for an EOF only that descendant can send. Round 8 fixed the stdout/stderr hang (an unconditional `.join()` that hung well past the timeout) by moving the buffers onto channels bounded by a fixed `PIPE_DRAIN_GRACE`; deep round 2 fixed the mirror-image hang on stdin; deep round 2 also had to stop the drain from killing the process group when that grace expired, because by then the child is reaped and its PID may have been recycled onto something unrelated. Pass 5 then measured what all that left behind: two threads and two descriptors leaked per call, held for as long as the descendant lives — +44 threads over 20 calls, climbing toward the descriptor limit in a session against a repository whose hooks daemonise anything.

Redirecting all three streams to files in the temp directory dissolves the premise. A file has no buffer to fill, so the child never blocks on a write and nothing has to drain concurrently: no reader threads, no writer thread, no drain budget, no `PIPE_DRAIN_GRACE`, and a lingering descendant is simply harmless — it goes on writing to an unlinked inode the OS reclaims when it exits. The three fixes above are all subsumed rather than stacked on. Output is read back after the child is known gone; a descendant appending after that point is missed, exactly as it was missed when the drain budget expired, but now missing it costs nothing.

The files live in the temp directory, never beside the checklist, for the same reason `writer::WriteLock`'s does: anything written inside the user's repository can be swept into a commit by a `git add -A` hook, which `verify_commit_scope` would then correctly abort the sync over. They are created `create_new` with mode 0600 (git's output routinely names branches and absolute paths) and removed by a `Drop` guard on every path — success, failure, timeout, or an early return. A scratch file that cannot be created returns the error rather than falling back to pipes or discarding output, which is the same fail-closed stance the rest of the module takes.

**Isolated commits, not working-tree reads:** the sync sequence starts with `git status --porcelain -- <file>` (scoped to the one file, so there's at most one porcelain line to read) purely to classify untracked/unchanged/dirty — absent → `SyncOutcome::Skipped`; a leading `??` → `SyncOutcome::SkippedUntracked` (reported, see Failure reporting below, but still never `git add`ed — there's no `git add` step anywhere in this flow, so a new file is never staged); anything else → proceed. Untracked and unchanged used to collapse into the same silent `Skipped`, via a single `--untracked-files=no` check — which meant git-sync could be permanently, silently unable to do anything for an untracked file, indistinguishable from it simply working with nothing to do yet.

**`git status` is not the authority on whether the checklist is tracked.** Deep round 2, both cases confirmed against real git. `run_sync` asked `git status --porcelain -- <file>` and read a leading `??` as untracked and empty output as "nothing to do". But status prints nothing at all for an untracked file under `status.showUntrackedFiles=no`, and equally nothing when the checklist matches a `.gitignore` rule — so both reported `Skipped`, and git-sync sat silent forever while being structurally unable to commit anything. That is precisely the "looks exactly like a bug" case `SkippedUntracked` was introduced to surface. The index is the authority, so `index_entry` now returns three answers — `Ok(Some(entry))` tracked, `Ok(None)` no index entry (untracked), `Err` the lookup itself failed — and `run_sync` settles trackedness from it *before* the empty-status short-circuit, leaving `status` to answer only what it reliably can: whether anything changed. `an_untracked_checklist_is_reported_even_when_git_status_stays_silent` covers both configurations and was verified to fail with the old ordering.

**A queued request can go stale, and now refuses rather than publishing anyway.** `run_sync` builds its commit entirely from `expected_content`, captured whenever the request was queued — possibly well before this function actually runs (coalesced behind a slow push, a busy worker). External review, round 5: nothing confirmed that snapshot was still accounted for by the file's current state before committing it. A naive "disk must equal `expected_content`" check would be too strict, though: several of markcheck's own toggles can legitimately land on disk in quick succession (each queuing its own request) before the *first* one's background thread is even scheduled — by the time it runs, disk already reflects a *later*, already-queued request, not an unrelated external change, and that's fine (the later request's own sync commits it momentarily). `GitSync.latest_requested_hash` (`Arc<Mutex<[u8; 32]>>`) is the distinguishing signal: updated on every `request()` call — including ones that only coalesce into `pending` — so it always holds the hash of the newest content git-sync has ever been asked to sync, and is shared (not snapshotted at spawn time) with the background thread. `run_sync` hashes the file's current bytes and compares against it: a match means whatever's on disk is already accounted for by *some* known request (this one, or a newer one already queued to run next); a mismatch — including the file no longer existing at all, the deletion variant — means the current state is unaccounted for by anything git-sync knows about, and the sync is refused (`SyncOutcome::Failed`) rather than committing (and publishing) a snapshot already known to be behind. The passive file-watcher reload deliberately never calls `request()` (see `AppState::request_external_edit_sync`'s doc comment: a change "picked up from elsewhere isn't necessarily ours to re-commit"), so without this check nothing would ever correct the record for an external edit or deletion landing in the gap.

Once past that check, the commit is built entirely from `PendingSync.content` — never by re-reading the working-tree file — which is what makes a concurrent, unrelated write to the file safe rather than a silent correctness hazard. The original implementation used `git commit --only -m <message> -- <file>`, which reads *whatever the working tree currently holds* for that path (despite `--only`'s name, this is true of a plain pathspec-commit too — neither form sources from a manually staged index entry). If some other change — another markcheck write, an external editor, anything — landed on disk between a request being queued and the background thread actually reaching this line, that commit would silently absorb it under a message describing only the *original* request; a second coalesced request for the same intervening change could then find nothing left to commit (`git status` already clean) and vanish with no record of its own. Building the commit from `PendingSync.content` instead closes that: `index_entry` (`git ls-files --stage --full-name`) reads the file's tracked mode and repo-root-relative path; `hash_object` (`git hash-object -w --path <relpath> --stdin`) writes the expected content into the object database — **`--path` is what makes the blob identical to the one `git add` would store**, since it applies whatever clean filter that path is configured for; without it markcheck hashed the bytes verbatim and published un-normalised content that git itself would never have written; if the blob `HEAD` holds for that path (`blob_at`, `git rev-parse HEAD:<relpath>`) already equals the content's filtered SHA (`blob_sha_for`, the same `hash-object --path` without `-w`), the request was already satisfied by an earlier sync and this one is `Skipped` too (covers a coalesced request whose content a prior commit already carried). **That comparison is made in git's terms, never on raw bytes** (#127): under a line-ending filter (`core.autocrlf`, or a `.gitattributes` rule such as `*.md text eol=crlf`) the checklist is CRLF on disk and LF in the blob, so a byte comparison never matched, the request fell through to building a commit whose tree equalled `HEAD`'s, and `git commit` refused with "nothing to commit" — reported as a false sync failure, and the push the fast path would have retried was skipped. `run_sync_recognises_already_committed_content_under_an_eol_filter` is the regression test.

**A temporary index, not the real one, and `git commit`, not `commit-tree`.** The commit is actually created via `commit_via_temp_index`: a fresh temp index file (`GIT_INDEX_FILE`, under the git-dir, named with the file's PID and `writer::random_suffix()` like `write_back`'s own temp files) is populated with `parent`'s tree (`git read-tree <parent>`, skipped for a repo with no commits yet), the expected blob is staged into *that* index at `relpath`/`mode` (`git update-index --add --cacheinfo`), and it's committed with a plain `git commit -m <message>` run with that `GIT_INDEX_FILE` — never `write-tree`/`commit-tree`/`update-ref` by hand. An earlier version of this function did exactly that manual plumbing, run against the repository's *real* index: `write-tree` serializes the *entire* current index, so anything else the user had `git add`ed but not yet committed rode along into markcheck's commit under a message describing only the checklist change, and `update-ref HEAD <new>` (no compare-and-swap) could silently make a concurrently-created commit unreachable from the branch. The temporary index sidesteps the first problem outright (the real index is never read or written *during* the commit — confirmed by `run_sync_never_includes_an_unrelated_staged_file`), and a normal `git commit` sidesteps the second (it performs its own `HEAD` read as part of one internally-locked operation, not a separate read-then-blindly-overwrite step on markcheck's side) while — for free — running the repository's normal commit hooks and honoring `commit.gpgsign`, neither of which `commit-tree` ever did. The temp index file is removed after the attempt regardless of outcome.

**`align_real_index_entry` fixes up the real index's own entry for `relpath` afterward — the one write this flow does make.** External review, round 9: committing entirely through a *separate* index, as above, has a consequence beyond keeping unrelated staged content out — the real index's entry for `relpath` itself is never advanced either, since nothing ever `git add`s it there. Reproduced empirically against a freshly cloned repo with no staged content of any kind: before any sync, the real index matches `HEAD` for `relpath` (clean). The temp-index commit moves `HEAD` forward for that path without touching the real index, so the real index is left holding the *old* blob — permanently, starting with the very first toggle. From then on `git status` shows the file as both staged (the stale index vs. the new `HEAD`) and not staged (the current working tree vs. that same stale index), recurring on every subsequent sync, since nothing else ever corrects it. Once `commit_via_temp_index` has committed and `verify_commit_scope` has confirmed the commit's scope, `align_real_index_entry` runs one `git update-index --add --cacheinfo <mode> <blob> <relpath>` against the *real* index (no `GIT_INDEX_FILE` override) — the same one-path realignment a normal `git commit -- <path>` would naturally leave behind. It touches only `relpath`; every other real-index entry, staged or not, is left exactly as it was, so `run_sync_never_includes_an_unrelated_staged_file`'s guarantee is unaffected. It's best-effort (its own failure is ignored): the commit — and any push it enables — has already succeeded by the time this runs, so this is local bookkeeping, not part of the commit's correctness. `run_sync_leaves_the_real_index_matching_head_after_a_commit` is the regression test. **It is also conditional, not unconditional** — external review, round 10: this is the one place the flow writes the real index, and it used to do so without checking that the entry still belonged to markcheck. If the user stages a *newer* version of the checklist while the background sync is running (`git add` from another terminal, or an IDE doing it for them), overwriting the entry silently discards their staged version. The working tree is untouched either way, so this is staging loss rather than content loss — but it is precisely the unrelated state the temporary-index design exists to protect, and the target path shouldn't be the one exception that ignores it. `commit_via_temp_index` therefore captures the real index's blob for `relpath` (`index_blob`) *before* any of its work runs, and `align_real_index_entry` realigns only if the index still holds exactly that: matching means markcheck is advancing its own entry, and any mismatch means someone else staged something since and it is theirs to keep. `align_real_index_entry_leaves_a_newer_staged_version_alone` pins the refusal and `align_real_index_entry_still_realigns_its_own_untouched_entry` pins that the ordinary case still works; the first was verified to fail with the guard removed.

**A staged checklist is not overwritten either: sync refuses rather than dropping it.** External review, round 11, reproduced end-to-end. The commit is built from the working tree and the realignment above then points the real index at it, so if the index was holding a *different* version of the checklist, that version is neither committed nor still staged — it survives only as a dangling blob, reachable through no ordinary git workflow. Verified against a real repository: a staged blob's unique content was absent from the resulting commit and unreferenced by anything afterwards. `staged_target_would_be_lost` refuses before any commit is built, reported as `SyncOutcome::Failed` like the unrelated-history refusal. **This is deliberately narrower than "refuse whenever the target is staged."** Staged content equal to what markcheck loaded is wholly contained in the content about to be committed — the toggle is the only difference — so nothing is lost, and refusing there would break two ordinary workflows for no safety gain: staging the checklist before running markcheck, and `git add`ing a brand-new checklist that has never been committed (the root-commit path, which `run_sync_undoes_a_hook_violated_root_commit_by_deleting_the_branch_ref` exercises). The discriminator is `PendingSync.previous_content` — the content this write replaced, read in `commit_write` under the write lock, immediately after the divergence check confirmed the file still held it. Both sides of the comparison are **blob SHAs git computed for that path** (`hash-object --path` against the staged entry's SHA), which is what makes the comparison valid under a content filter. It carries the content rather than a digest of it for exactly that reason: an earlier version hashed the pre-write bytes itself and compared that to the raw staged bytes, and under `core.autocrlf` (or a `.gitattributes` `text` setting) those differ by precisely the normalisation — measured at 22 bytes on disk against 20 in the blob for the same two lines — so they could never match and the guard refused a sync that was in fact safe, in exactly the two workflows this paragraph says must keep working. It fails **closed**: a request carrying no pre-write content, or a blob SHA that cannot be computed, both refuse, the same rule `unpushed_history` follows. **The realignment guard above does not cover this**, and the two are easy to confuse: that one compares the index against a baseline taken at the *start of the sync*, so it catches a stage landing *during* a sync, while this one catches a stage that was already there before markcheck ran.

**`resolve_parent`, not `current_head`, establishes the parent for a possible new commit.** Self-review finding: `current_head`'s `None` is ambiguous — `git rev-parse HEAD` fails identically (`output.status.success() == false`) whether the repository genuinely has no commits yet or the command failed for any other reason (a timeout, a spawn failure, a corrupted ref; confirmed empirically that a real empty repo exits 128 with "unknown revision", the same failure shape a timeout produces). That ambiguity is harmless everywhere `current_head` is used *except* here: `run_sync` treats `parent: None` as "build a root commit," which skips seeding the temporary index from any existing tree at all — if `current_head` merely failed transiently on an otherwise non-empty repository, the resulting commit's tree would contain only the checklist path, silently dropping every other tracked file, and `verify_commit_scope` wouldn't catch it (its own baseline is equally wrong under the same bad assumption). `resolve_parent` uses `git rev-parse --verify -q HEAD` instead, which exits with status **1** specifically for "no commits yet" (confirmed empirically, silent thanks to `-q`) — distinctly from 128 or a timeout for any other failure — so only that exact exit code becomes `Ok(None)`; anything else is `Err`, surfaced as a normal sync failure rather than silently assumed to be an empty repository. Every other `current_head` call site is unaffected (traced through each: a transient failure there only ever causes an unnecessary refusal or retry, never a silent wrong action), so this is a narrow fix at the one genuinely dangerous call site, not a signature change across the module.

**Running the repository's hooks at all is a trust decision, not just a scope one.** The paragraph below bounds what a hook can get *committed*; nothing bounds what a hook can *run*. Committing with a real `git commit` means opening a checklist with `--git-sync` inside an untrusted repository executes that repository's `pre-commit`/`commit-msg`/`post-commit` hooks, exactly as running `git commit` there by hand would. That's the accepted cost of hook and `commit.gpgsign` support — the alternative (`commit-tree`, which runs neither) was what this design deliberately moved away from — and it's called out in README.md's git-sync section so it isn't a surprise, rather than being mitigated in code.

**Hooks run against the temporary index too, but the commit's scope is verified and enforced afterward.** Restoring hook support was the whole point of moving off `commit-tree`, so a hook that runs `git add` inherits the same `GIT_INDEX_FILE` and can stage more into the temporary index, same as it could against the real one. An earlier version of this design left that as a documented tradeoff rather than enforcing it — reasoning that verifying post-hook and refusing on a violation would silence a hook's own intentional file-expanding behavior, a stranger failure mode than the one it prevents. A second external review pushed back on that: with `--git-sync` active, a hook silently expanding the commit isn't just "a locally messy commit" the user might notice — it becomes an automatically *pushed* commit, which is a materially different risk than the "considered and rejected" reasoning weighed. `verify_commit_scope` now runs immediately after `commit_temp_index` succeeds: it checks `parent` against `created_commit` — the exact SHA `commit_temp_index` resolved via one `current_head` call right after `git commit` returned, threaded through as an argument, never re-resolved later by `verify_commit_scope` itself — via `range_has_unrelated_commits` (shared with `unpushed_history` above; see its own paragraph for why this is a per-commit check, not a single net diff between `parent` and `created_commit` — a hook that made two nested commits where the second reverts the first's unrelated change would otherwise net out to zero and pass). A violation calls `undo_commit`, which moves the branch ref back to `created_commit`'s own first parent (read with `git rev-list --parents -n 1`, never the `parent` captured before the commit, since a concurrent commit can land between that capture and `git commit`) or, for a root commit, resolves the branch's symref (`git symbolic-ref -q HEAD` — resolvable even before any commit exists, since `git init` makes `HEAD` a symref immediately) and deletes it, to return to the pre-commit unborn-branch state. Both forms pass `created_commit` as `update-ref`'s expected-old-value argument (`git update-ref HEAD <first-parent> <created_commit>`, or `git update-ref -d <ref> <created_commit>`) rather than an unconditional move/delete — external review, round 4: an earlier version had no such guard, so a commit landing on top of `created_commit` (another markcheck instance, a human, an IDE) between the commit and the undo would have been silently rewound out of the branch's history along with the one actually being undone; the CAS makes that update-ref fail instead. The undo rewinds exactly one commit, `created_commit`, to its own first parent; it does not discard a whole chain of hook-made commits, and any earlier commit in the range stays on the branch. If the undo itself fails — whether from an ordinary error or the CAS guard refusing — the error is deliberately more alarming than an ordinary sync failure (it names the stray commit's SHA) rather than reading like a routine problem, since a commit with unrelated files now exists with no automatic rollback.

**A scope check that cannot be *performed* is reported differently from one that fails.** Deep rounds 2, round 3. `verify_commit_scope` propagated a `range_has_unrelated_commits` error with a bare `?`, so when git itself failed the user saw only the raw message ("git rev-list: fatal: …") — with nothing to say that a commit had already been made and was still sitting on the branch, which the neighbouring undo-failed arm is careful to spell out. The commit is deliberately **not** undone in that case: whether it is in scope is precisely what could not be established, and rewinding a possibly-fine commit is the worse guess. The error now names the commit and says it was left in place. Contained either way — the next sync's unpushed-history guard sees it and refuses if it touches anything beyond the checklist.

**The captured `created_commit` narrows this race further but doesn't eliminate it.** Threading one SHA through scope verification and rollback (rather than each step re-resolving `HEAD` independently, at a later point in time than the last) closes the window in which an *externally* timed concurrent commit could be misattributed to markcheck's own. What remains is a much narrower case: something committing *during* `commit_temp_index`'s own `git commit` invocation, before it returns and `current_head` is resolved — realistically, only a hook running as part of that same commit (e.g. a `post-commit` hook that itself commits) can land in that specific window, and if it touches anything beyond `relpath` it's still caught by the scope check above. Not reaching for a repository-wide lock here is the same tradeoff already accepted for `commit_via_temp_index`'s own pre-commit `parent` check, below (see "No repository-level lock" at the end of this section for why git-sync, unlike the file write, takes no lock).

**The rollback rewinds exactly markcheck's own commit, never the captured parent.** Deep round 3, found with the new race harness and reproduced deterministically. `undo_commit` used to reset the branch straight back to `parent`, discarding *everything* in between. Its compare-and-swap only guards against the branch moving **past** `created_commit`; a commit landing in the window between `commit_via_temp_index`'s `HEAD == parent` re-check and `git commit` itself becomes an **ancestor** of `created_commit` instead, so the CAS still passes and the reset dropped that commit off the branch. Observed directly: a concurrent `unrelated` commit left the branch reading `init` alone, surviving only as a dangling object — the precise violation of "markcheck must never move `HEAD` across a commit it did not create" that the rest of this section is built around. The commit graph cannot tell that apart from a `pre-commit` hook making nested commits of its own, and it does not need to: markcheck did not create those either, so sweeping them away was never right. `undo_commit` now resolves `created_commit`'s **own first parent** and resets to that, so exactly one commit is ever rewound. Hook-made commits consequently survive an aborted sync rather than going with it; that is the deliberate trade, the reported error names the commit, and the next sync's unpushed-history guard refuses with a clear message until the user deals with them. `a_commit_landing_before_ours_is_detected_rather_than_built_on_stale_state` pins the concurrent case, and `verify_commit_scope_catches_a_revert_cancelled_unrelated_change` was updated from asserting the old whole-chain reset.

**And it refuses to rewind at all when it cannot read the commit's parents.** Deep rounds 3, round 1 — the same ambiguous `None` that `resolve_parent` exists to eliminate for `current_head`, recurring in the rewind added above. `undo_commit` parsed `rev-list --parents` with `.lines().next().unwrap_or_default()`, so an **empty** listing produced no parent, which is indistinguishable from a genuine root commit — and the root-commit path *deletes the branch ref* rather than moving it back one commit. Reachable, not theoretical: when output was piped, a drain that timed out against a lingering descendant returned empty output while the command's own exit status was still success. Scratch files removed that particular route, but not the premise — a scratch file that cannot be read back yields the same empty output beside a successful status. `parse_first_parent` now returns `None` for "said nothing" and `Some(None)` only for a real root commit, and unreadable output refuses the rewind — the commit stays and the next sync reports on it.

`repo_sync_blocked` runs first, before even `status` — a normal `git commit` doesn't refuse on its own to commit while the repository is mid-merge (a fresh temp index has nothing conflicted in it), so this is a genuinely separate check: it looks for `MERGE_HEAD`/`CHERRY_PICK_HEAD`/`REVERT_HEAD`/`BISECT_LOG` or a `sequencer`/`rebase-merge`/`rebase-apply` directory under the git-dir (`sequencer/` because a multi-commit cherry-pick or revert whose step the user concluded with a plain `git commit` instead of `--continue` has no `CHERRY_PICK_HEAD` any more, yet is still mid-sequence) (`git_dir`, resolved to an absolute path regardless of whether `git rev-parse --git-dir` itself returns one), a detached `HEAD` (`git symbolic-ref -q HEAD` failing — a commit made there is one `git checkout` away from becoming unreachable), and unresolved conflicts *anywhere* in the repository, not just the target path (`git ls-files -u`, non-empty). Any of these refuses the whole sync with `SyncOutcome::Failed`. So does any check that can't be answered (#9) — the git-dir not resolving, a marker whose existence can't be determined, `symbolic-ref` failing with anything but exit 1 (its "not a symbolic ref" answer) or timing out, `ls-files -u` failing or timing out — each with a "could not check …; not syncing" message, since the guard fails closed like the rest of `guards.rs`: it used to treat each of these as "not blocked" and let the commit through. Without this, a genuine unresolved merge conflict on the checklist file used to be silently "resolved": the conflicted index entry (`git ls-files --stage` emits three lines — stages 1/2/3 — for a conflicted path) got collapsed to markcheck's own expected content by the old `update-index --cacheinfo`, and the plumbing sequence happily committed and advanced `HEAD` past the in-progress merge, leaving `MERGE_HEAD` still present (only `git commit`, not a raw `update-ref`, clears it) and the working tree's conflict markers now shown as "modified" relative to the new `HEAD` — a thoroughly confused repository state. `run_sync_refuses_during_an_unresolved_merge_conflict` is the regression test.

**A narrower residual race, accepted rather than eliminated:** `commit_via_temp_index` re-reads `current_head` immediately before committing and refuses (rather than committing) if it no longer matches `parent` — `commit_via_temp_index_refuses_when_head_moved_since_parent_was_read` covers this. It also re-runs `repo_sync_blocked` at that same point (`commit_via_temp_index_refuses_when_repo_becomes_blocked_after_the_head_check`), narrowing the separate window in which a merge/rebase/etc. could start after `run_sync`'s own top-of-function check but before the commit actually happens. Neither re-check closes its window entirely (a commit — or a merge starting — could still land in the instant between the check and the `git commit` call actually running), but a normal `git commit`'s own HEAD update is never at risk of corruption either way; what a still-possible stale `parent` would produce is a tree that's correct for `relpath` but reverts every *other* path back to `parent`'s content for that one commit — a narrow, self-correcting-on-the-next-sync risk, accepted rather than reaching for a repository lock (see "No repository-level lock" below). **The safety property is therefore "optimistic commit, then verify", not "the commit is built on the history that was validated"** — external review of `8a405dd` rightly warned that a future contributor could read the pre-check as the latter. It is not. What makes the residual acceptable is not the check but what happens after it: `verify_commit_scope` inspects every commit in the range the commit actually landed on, so a foreign commit that raced in is *detected*, and `undo_commit`'s compare-and-swap rewinds only markcheck's own commit, leaving the racer on the branch untouched. The result is a reported failure and a repository nobody has damaged, not a silently wrong commit. `a_commit_landing_before_ours_is_detected_rather_than_built_on_stale_state` drives exactly that interleaving through `RacePoint::BeforeCommit` and asserts the foreign commit survives and `HEAD` is not rewound past it; it should be treated as a permanent regression test, since this is precisely the property a refactor could quietly drop.

None of the above touches the working tree, so the commit's content always matches its message exactly regardless of what else is happening to the file concurrently; a later, unrelated change still gets synced, just as its own, separately labeled commit the next time `request` runs. Every git-sync command runs from the repository root, which `GitSync::detect` resolves once (`git rev-parse --show-toplevel`) and stores as `GitSync::repo_root`; the checklist is named by its absolute path or a root-relative one (`ls-files --full-name`). Whether a command ran from the checklist's directory or the root used to be decided per call, and `push` resolved `@{u}` from one while `unpushed_history` resolved it from the other (#141); `a_checklist_in_a_subdirectory_syncs_from_the_repository_root` covers a checklist below the top level.

**Publishing, end to end — the current contract, before the reasoning.** Stated here first because the paragraphs that follow record how it was arrived at, in the order the problems were found. markcheck publishes exactly **one explicitly named commit**: the branch tip it captured and validated at the start of this sync, pushed as `git push <remote> <sha>:<upstream-branch>` — never a bare `git push`, and never a `HEAD` re-resolved after the checks ran. Before pushing it requires an upstream to exist, requires the unpushed range ending at that exact commit to touch nothing but the checklist file, and refuses outright if it cannot *determine* that. A failed push leaves the commit safely local and arms a retry; nothing is ever committed in order to make a push possible, including at startup. Where a paragraph below describes an earlier design, it says so — this summary is the one to trust if they ever disagree again.

**The push is scoped too, not just the commit: sync refuses rather than publishing unrelated work.** `run_sync` checks `unpushed_history` before *either* of its two paths that can push — the fast path (below) and building a new commit — and refuses outright (`SyncOutcome::Failed`, not retried) if the branch is already ahead of upstream with anything other than the checklist file. The reason this guard has to exist at all is that pushing any commit publishes its whole ancestry: even the explicit-SHA refspec below cannot narrow a push to markcheck's own commit alone, so the guard — not the refspec — is what keeps unrelated work unpublished. A second external review is what forced the point: for a feature that goes to considerable lengths to keep the *commit* scoped to exactly the checklist file (temp index, hook-scope enforcement — see above), letting the *push* silently publish whatever else happens to be sitting on the branch is an inconsistent safety story, especially once `--git-sync` makes the push automatic rather than something the user reviews first. This is deliberately *not* a plain ahead-of-upstream check: several of markcheck's own commits can legitimately stack up while offline (see `repeated_requests_against_an_unreachable_remote_never_deadlock_or_lose_edits`), so the check looks at each commit in the ahead range and refuses only at one that isn't publishable (see "Which unpushed commits are markcheck's" below). External review, round 7: the check originally ran only immediately before building a new commit, on the assumption that the fast path's `HEAD` is always "markcheck's own prior commit, always legitimate to push" — false whenever an unrelated commit lands on top of that prior commit without touching the checklist file at all, since the checklist's blob at `HEAD` is then unchanged and the fast path's equality check still passes. Reproduced concretely: a request queued earlier (content already matching `HEAD`) processed after both a newer uncommitted edit lands on disk (so `git status` stays non-empty, reaching this far) and an unrelated commit lands on the branch — the fast path would otherwise push `HEAD`, publishing the unrelated commit alongside it. What this check does when it *cannot* be answered changed later, and is described under "Couldn't check" below rather than here.

**Checked per commit, not as one net tree diff.** External review, round 8, confirmed empirically: an earlier version of this check ran a single `git diff --name-only @{u} HEAD` and flagged anything other than `relpath` in that *net* result. A commit that touches an unrelated path followed by a later commit that reverts that exact change nets out to zero in that comparison — the diff shows nothing wrong — but both commits are still in the unpushed range and still get published, since an explicit-SHA push (see below) sends a commit's whole ancestry regardless of what any single commit's net effect on the tree looks like. `unpushed_history` and `range_has_unrelated_commits` (the latter `verify_commit_scope`'s, above — the same blind spot existed there too, for a hook that makes two nested commits where the second reverts the first's unrelated change) check each commit individually instead: `git rev-list --parents <range>` lists every commit in range plus its parent count in one call; a commit with more than one parent (a merge) is treated as unrelated unconditionally — refusing outright rather than attempting a combined-diff interpretation of what a merge itself touched, which has genuine edge cases (conflict resolutions, content changed only during the merge) that could misjudge it either way. Every other commit is checked with `git diff-tree --root --no-commit-id --name-only -r -z <sha>` — `--root` is required for a root (zero-parent) commit to show anything at all (confirmed empirically: without it, `diff-tree` prints nothing for one) and is a no-op for an ordinary commit, which still diffs against its own first parent.

**Which unpushed commits are markcheck's: a commit trailer (#62, #99).** Every commit markcheck makes ends with a `Synced-by: markcheck` trailer (`guards::OWN_COMMIT_TRAILER`, a second `-m` to `git commit`), and a commit counts as markcheck's own when it carries that trailer (read with `%(trailers:key=Synced-by,valueonly)`) and changes exactly one `.md` path. `unpushed_history` walks `@{u}..tip` oldest first under a `Publishable` rule. A toggle's sync (`OwnOrThisChecklist`) may publish markcheck's own commits for *any* checklist, so one checklist's commit stranded while offline no longer blocks a second checklist in the same repository, plus any commit touching only this checklist, as before. The startup catch-up (`OwnOnly`), which the user did nothing to start, publishes only markcheck's own commits, so a commit the user made to the checklist and kept local is never pushed by opening the file. The first commit that fails the rule (a merge always does) comes back as `UnpushedHistory::Blocked` with its SHA and subject, and the refusal names it (`commit abc1234 "WIP: reorder" is not pushed yet and isn't markcheck's; push or drop it first`); at startup it is `SyncOutcome::NotCaughtUp`, a sticky message saying to push it by hand. A catch-up that pushes reports `SyncOutcome::CaughtUp { pushed }` (`Pushed N earlier markcheck commits`). A message-shape match was rejected as too easy to collide with, and a state file in `.git` as more state than the question needs. Commits made before the trailer existed count as the user's, which errs on the side of not publishing.

**"Couldn't check" is not "safe": the unrelated-history guard fails closed.** External review, round 10. The guard was a `bool` produced with `.unwrap_or(false)`, so *any* git failure — a `rev-list` timeout on a large history, a transiently unhealthy object database — was indistinguishable from "verified safe", and the caller went on to push. The asymmetry is what makes that the wrong default: a false refusal costs the user one retry, while a false clearance publishes someone else's commits. The original reasoning was sound, though, and is why this isn't simply a `Result<bool, _>`: `@{u}` is legitimately unresolvable when a branch has no upstream, and failing closed on *that* would block every first-ever commit to a fresh repository. `unpushed_history` therefore returns three answers — `Safe`, `ContainsUnrelated`, `NoUpstream` — with `Err` reserved for a genuinely unanswerable check; `NoUpstream` proceeds (committing is fine, and `push` declines separately with its own specific message), while `ContainsUnrelated` and `Err` both refuse. The no-upstream case is detected by resolving `@{u}` itself (`resolve_upstream`, exit **1** for "doesn't resolve", confirmed empirically, the same exit-code trick `resolve_parent` uses), **not** by reading `branch.<name>.remote`/`.merge` config via `upstream_parts`: config can claim an upstream exists while the tracking ref still doesn't resolve — a remote added but never fetched, or those keys set by hand — and an earlier attempt at this fix used `upstream_parts` and turned three passing tests into hard sync failures for exactly that reason. `a_configured_but_unfetched_upstream_still_counts_as_no_upstream` is the regression test for that mistake. Resolving to a concrete SHA also means the range walk names two real commits rather than a symbolic ref, matching the captured-tip rule below.

**`push` targets `expected_commit` explicitly, not a bare `git push`.** External review, round 5: `push_if_head_unchanged` and `retry_commit` both verify `HEAD == expected_commit` immediately before calling `push`, but that check and the push itself used to be two separate steps regardless — a bare `git push` sends whatever the local branch tip has become by the time it actually runs, so a commit landing in the gap between the check and the push would still ride along and get published, unnoticed. `push` now resolves `(remote, upstream-branch-ref)` via `upstream_parts` — `current_branch_ref` (stripped of its `refs/heads/` prefix) plus the branch's `branch.<name>.remote`/`branch.<name>.merge` config, rather than parsing `@{u}`'s abbreviated form, which would need guessing where the remote name ends and a branch name that itself contains `/` begins — and runs `git push <remote> <expected_commit>:<branch-ref>` instead. This closes the gap rather than merely re-narrowing it: the push can never publish more than `expected_commit`'s own ancestry, no matter what the local branch has become by push-time. **When `upstream_parts` can't resolve a remote/branch at all (no upstream tracking configured for the branch), the push is refused rather than falling back to a bare `git push`.** It used to fall back, justified on the premise that "a bare push already reports a clear git-native error for it" — deep review, reproduced empirically: that premise is false for an ordinary configuration. With a remote added but `-u` never used and `push.default = current`, a bare push resolves a destination and *succeeds*, publishing the whole branch tip rather than `expected_commit` alone. Worse, it composed with the unrelated-history guard, which declines to refuse in exactly the same configuration (its `@{u}..<tip>` range is equally unresolvable, and a branch with no upstream must not be blocked from making its first commit — see `unpushed_history`'s `NoUpstream` answer): both guards were off simultaneously, so an unrelated local commit is published by a checklist toggle — the precise scenario that guard exists to prevent. `push` now returns `CommittedNotPushed` naming the cause ("this branch has no upstream yet; run `git push -u` once"), which keeps the commit safely local, reuses the existing retry machinery, and gives the user a single one-off action. This is a behavior change for repositories that relied on the bare-push fallback: they now need `git push -u` once before git-sync will push. `run_sync_never_publishes_unrelated_work_when_no_upstream_is_configured` is the regression test. `run_sync`'s own already-committed fast path (see "Isolated commits" above) still checks `ahead_of_upstream` (`git rev-list --count @{u}..<tip>`, failing open — assume "yes, ahead" — when there's no upstream configured at all, so a real push attempt still runs and reports why rather than the sync going silently quiet) before returning `Skipped`; if the matching commit hasn't actually reached the remote yet, it pushes instead of skipping — this is content-based (it's driven by a normal `request`, not the SHA-based retry), but it's still markcheck's own prior commit being pushed, so replaying is safe here specifically because nothing new is being *committed*, only pushed. **That fast path resolves `HEAD` as a hard failure, never a default.** Deep review, reproduced empirically: it used to read `current_head(&repo_root).unwrap_or_default()`, and `current_head`'s `None` covers *any* failure (a timeout, a spawn failure, a corrupted ref — see `resolve_parent` for the same ambiguity at the other dangerous call site), while `String`'s default is `""`. That empty SHA formats into the refspec below as `<remote> :<branch>` — git's **delete a remote ref** form, which succeeds, exits 0, and so gets reported as `Synced` while the branch is gone from the remote. A bare remote refuses to delete its own `HEAD` branch (`receive.denyDeleteCurrent`), so only branches other than the remote's default were ever exposed — which is every topic branch, and is precisely why every git-sync test running on `main` never saw it. `run_sync` now returns `Failed` when `HEAD` won't resolve, and `push` independently rejects an empty `expected_commit` as `Failed` before building any refspec, so a future caller can't reintroduce it from another direction. `push_refuses_an_empty_commit_instead_of_deleting_the_remote_branch` and `run_sync_commits_and_pushes_on_a_non_default_branch` (both on a topic branch, via `init_repo_with_remote_on_a_topic_branch`) are the regression tests. Between that fast-path retry (triggered by any new request, including the periodic one below) and `retry_push_if_due`'s time-based one, a commit that only failed to push can't get permanently stranded local-only just because the user never happens to touch the file again. One more gap remains even so — quitting (or crashing) before either retry path gets a turn leaves the commit unpushed until the *next* launch — closed by `main.rs` calling `GitSync::request_catch_up_push()` right after `GitSync::detect` at startup, before the event loop even begins, giving a leftover unpushed commit one more chance to go out immediately rather than waiting on the first edit of the new session.

**`push` and the unpushed-history guard resolve the upstream the same way.** Deep rounds 3, round 3, confirmed against real git. They used to answer "is there an upstream?" from different sources: `push` read the *config* (`branch.<name>.remote`/`.merge`, via `upstream_parts`) while `unpushed_history` resolves `@{u}`. Those disagree whenever the config names an upstream whose remote-tracking ref does not exist — set by hand, or pruned, or a clone that never fetched it. The guard then reported `NoUpstream` and stood down, while `push` built a refspec and published anyway, *creating* the branch on the remote. That reopened the exact hazard the refuse-without-an-upstream rule closed, by a different door: the unrelated-commits check never ran, so a checklist toggle published unrelated local work. Reproduced end to end — the sync reported `Synced` with the unrelated commit on the remote. The resolvable ref is now the authority for both. A branch whose upstream has never been created still commits locally; only publishing waits for the one-off `git push -u`, which is what the message says.

**And the remote itself is asked whether the branch is still there.** External review of `8a405dd` — a third door into the same "creating the branch on the remote" hazard as the two above, and the one neither of them watches. `refs/remotes/<remote>/<branch>` is a *cache*, refreshed only by a fetch, so once somebody deletes the branch upstream this clone keeps pointing at the last commit it saw and `@{u}` keeps resolving. Every guard in the paragraphs above is satisfied: there is an upstream, both resolvers agree it exists, the refspec is explicit. The push then finds nothing to be non-fast-forward *against* and simply creates the branch again — confirmed against a real remote, which reports `* [new branch]`. Ticking a checkbox silently republishes history somebody deliberately removed, unattended. `push` now consults the remote (`git ls-remote --heads <remote> <branch-ref>`) before publishing and returns `CommittedNotPushed` if the branch is gone, so the work stays committed locally while the user decides where it belongs. The answer is three-way (`RemoteBranch::{Present, Absent, Unknown}`), because "could not ask" is not "not there" — the ambiguity this module keeps relearning — and an unreachable remote also refuses, which gives up little in practice since `ls-remote` and `push` share a transport and credentials. `ls-remote` matches its pattern against ref *tails*, so `refs/heads/main` also lists `refs/heads/a/refs/heads/main` (sorted first); `remote_branch_state` therefore takes only the line whose ref name equals the branch ref exactly, and treats no exact match as `Absent` (#120). It costs one extra round trip on the push path, which already spends one. `a_branch_deleted_on_the_remote_is_not_recreated_by_a_sync` is the regression test, verified to fail with the check removed.

**The check and the push are then made atomic with a lease.** External review of `2322436`: asking the remote and pushing are two round trips, so a deletion landing between them recreates the branch anyway — the check narrowed the window rather than closing it. The push now carries `--force-with-lease=<branch-ref>:<sha>`, the SHA being exactly what `ls-remote` reported, so git itself rejects with `stale info` if the ref is no longer that commit — missing included. `command_error` reports that rejection as `the remote branch changed while pushing (stale info)` (#127), since git's bare ref-rejection line means nothing to someone who never ran the push. Confirmed against real git for both the deleted and the moved case.

**The destination is the one `git push` would use, at the URL it would use.** Issue #98. `upstream_parts` names where the branch is *fetched* from; `git push` decides separately, from `branch.<name>.pushRemote`, `remote.pushDefault`, `push.default` and push refspecs. A branch made with `git switch -c notes origin/main` tracks `main`, and under the default `push.default = simple` a plain `git push` refuses it, yet git-sync published straight to `main`; a triangular setup (`remote.pushDefault = fork`) had its checklist commits pushed into the fetch remote instead of the fork. `push` now requires `push_goes_to_upstream`: `@{push}` must resolve to the same tracking ref as `@{u}`, and `%(push:remotename)` must be the upstream's remote. `@{push}` is git's own resolution of those settings and fails wherever `git push` has no single destination, so this refuses (`CommittedNotPushed`, "push it yourself") rather than reimplementing `push.default`. Requiring `@{push} == @{u}` keeps the unpushed-history guard and `ahead_of_upstream`, which both range over `@{u}`, describing exactly what is published. A triangular `simple` setup is refused rather than pushed to the fork, since `@{push}` itself does not resolve there. Separately, `ls-remote <remote>` asks the fetch `url`, while the push goes to `remote.<name>.pushurl` when one is set, so the lease and the fast-forward check could describe a different repository than the one written to; `push` now runs `ls-remote` against `git remote get-url --push <remote>`. The push itself still names the remote, so a remote's other settings keep applying. Tests in `push.rs` cover a differently named upstream (refused under `simple`, pushed under `upstream`), `remote.pushDefault` and `branch.<name>.pushRemote`, and a `pushurl` pointing at a second repository.

**A local upstream is not a remote.** Issue #71. `git checkout -b <name> --track main` (or `branch.autoSetupMerge = always`) sets `branch.<name>.remote = .`, and `@{u}` resolves to the local `main`. Under `push.default = upstream`, `ls-remote .` and `git push . <sha>:refs/heads/main` both work against the repository itself, so a sync would fast-forward another local branch and report it synced. `push` now refuses a remote of `.` before anything else is asked of it, with `CommittedNotPushed` ("this branch tracks the local branch main, not a remote; push it yourself"). A remote name with no configured URL is already refused by the `push_url` lookup.

**A lease permits a non-fast-forward whenever it matches**, which is precisely what an ordinary `git push` refuses, and that is why an earlier round rejected `--force-with-lease` as a blanket answer. Confirmed: with the lease satisfied, pushing a commit that does not descend from the remote tip reports `(forced update)` and rewrites the branch. So `push` establishes the fast-forward itself first — `is_ancestor(remote_tip, expected_commit)`, which answers `false` when it cannot tell, including when the remote tip is a commit this clone has never fetched. With that established the lease can only ever *reject*, never force, and the two together give a compare-and-swap without turning git-sync into an automatic force-pusher.

`a_branch_deleted_between_the_check_and_the_push_is_not_recreated` drives the deletion through `RacePoint::BeforePush`, which sits after the existence check, and fails with the lease removed. `a_commit_not_based_on_the_remote_tip_is_refused_rather_than_forced` fails with the ancestry check removed. `a_branch_that_moves_between_the_check_and_the_push_is_not_clobbered` is honest about pinning less: it still passes without the lease, because a plain push already refuses a moved tip as a non-fast-forward — the lease's unique contribution is the deleted case, where there is no tip to be non-fast-forward against.

**One captured tip, named at every step — never the symbolic `HEAD` twice.** External review, round 10. Both push-capable paths used to re-resolve `HEAD` independently at each step: `run_sync`'s fast path ran the unrelated-history guard against the range ending at `HEAD`, read the checklist blob at `HEAD`, then separately called `current_head()` for the SHA it handed to `push`; `catch_up_push` did the same thing at startup. Those are different subprocesses, so they are not guaranteed to be talking about the same commit. A commit landing in that window was published having never been checked — the fresh-commit path was already protected by `push_if_head_unchanged`, but neither of these two was. Both now resolve the tip **once** (`resolve_parent`, so "no commits yet" stays distinguishable from a failed lookup) and pass that SHA explicitly to the guard, the blob read, the push, and — in `run_sync` — as the parent the new commit is built on. This *closes* the race rather than narrowing it, and needs no re-check or retry path: because `push` targets an explicit SHA, the ancestry it can publish is exactly the range that was validated, no matter what `HEAD` does afterwards. The predicates took a `tip` parameter rather than growing a `CheckedCommit` wrapper type — the invariant needed is "every question names the same commit", which threading one SHA already enforces at the type level by leaving no symbolic `HEAD` for a caller to reach for. `a_head_that_moves_after_the_tip_is_captured_cannot_broaden_the_push` pins it, moving `HEAD` inside the window deterministically rather than racing a thread.

**The unrelated-history guard is only a snapshot taken before the commit — `push_if_head_unchanged` closes the window after it.** External review, round 4: the unrelated-history guard (`unpushed_history`) runs once, before `commit_via_temp_index`; a commit landing on the branch *after* markcheck's own commit was made and scope-verified, but before the push actually runs, would previously have been pushed right alongside it, unnoticed — the same risk the check above exists to prevent, just at a later point in the same `run_sync` call it doesn't reach. `run_sync` now calls `push_if_head_unchanged(repo_root, created_commit)` instead of `push` directly for a freshly-made commit: it re-resolves `current_head` and only proceeds to `push` if it still equals `created_commit`, otherwise reporting `CommittedNotPushed` without pushing anything. This deliberately doesn't reuse `retry_commit`'s silent `Skipped` on the same mismatch (below) — that's correct for abandoning a *retry* of an already-reported failure, but a first attempt at a commit nobody has been told about yet must surface something rather than going quiet. Nothing is lost either way: the commit stays local and safe, and `CommittedNotPushed` feeds the same automatic retry machinery described next, which re-runs this exact check once due.

**Commit succeeding and push succeeding are tracked separately, and a failed push retries on its own:** a push failure (offline, auth, no upstream) never rolls back or discards the commit that already landed — but it also can't be conflated with a genuinely failed sync, because the two need different recovery. `SyncOutcome::CommittedNotPushed { message, commit }` is the distinct outcome for exactly this case; `SyncOutcome::Failed` covers everything else that stops a sync: a failed git command or one of markcheck's own refusals (a blocked repo state, unrelated unpushed commits, a staged checklist). Usually nothing was committed; the exception is a commit whose scope couldn't be verified or whose undo failed, which is left on the branch and named in the message. This distinction is what makes automatic retry possible: `GitSync` remembers the **commit SHA** (not the file content) of the last attempt that ended in `CommittedNotPushed` — `push` embeds the exact `expected_commit` it was targeting directly (it always knows this now — see below — rather than needing to re-resolve `current_head` on a failure branch), so `poll()` can promote it straight into `retry: Option<(String, Instant)>`, cleared on the next `Synced` — and `retry_push_if_due` — called every main-loop tick alongside `poll` — calls `retry_commit(repo_root, expected_commit)` once `retry_interval` has passed — `PUSH_RETRY_INTERVAL` (30s) at first, doubled by every further `CommittedNotPushed` for the *same* commit or `RetryFailed`, capped at `PUSH_RETRY_MAX_INTERVAL` (5 min), and reset by `Synced`, `RetryAbandoned` or a new commit, so a laptop offline for hours isn't running `ls-remote` every 30 seconds (#64) — without waiting for another checklist edit to come along and trigger a fresh `request`. `retry_commit` checks `current_head == expected_commit` before pushing; if something else has moved `HEAD` in the meantime (most plausibly a concurrent markcheck/git-sync process against the same repo, since an ordinary external commit resyncs the real index and would already have made `run_sync` return `Skipped` before ever reaching this point — see "Isolated commits" above), it abandons the retry silently (`RetryAbandoned`, see below) rather than rebuilding a commit from the stale content, which could otherwise revert whatever superseded it. This is a deliberate design choice over the simpler content-replay approach an earlier version of this mechanism used: retrying *a specific commit* rather than *a piece of content* is what makes the retry safe regardless of what else has happened to the repo since the failure. Abandoning also **clears** `GitSync.retry` itself, not just that one attempt — external review, round 7: `poll()` previously only updated `retry` for `Synced`/`CommittedNotPushed`, leaving an abandoned retry's `(commit, last_attempt)` tuple in place with its now-stale `Instant` untouched; since that timestamp never advances, `retry_push_if_due`'s backoff check stays permanently elapsed once abandonment starts, re-spawning an equally-doomed retry attempt on *every* subsequent tick rather than every `PUSH_RETRY_INTERVAL`. `retry_commit` now returns a dedicated `SyncOutcome::RetryAbandoned` rather than a bare `Skipped`, and `apply_outcome` — the single, deliberately **total** `match` that is the only writer of `retry` — clears the retry for it. Carrying the distinction in the *outcome* is what replaced an earlier out-of-band `last_spawn_was_retry` flag read at `poll` time: an ordinary sync's `Skipped` (nothing to do) must never clear an unrelated, still-valid armed retry for an earlier commit, and making the two genuinely different values means adding a variant is a compile error rather than a silent fall-through into a catch-all — which is precisely how the `Failed` retry storm survived until deep review round 2.

**A retry's own failure and a content sync's failure are different outcomes.** Deep round 1. `apply_outcome`'s `Failed` arm restarted the armed retry's backoff for *any* failure, but only a failure of the retry itself says anything about the retry. A content sync that keeps failing for its own reasons — an unrelated-commits refusal on every toggle, say — pushed the retry's clock forward each time, so a perfectly pushable commit never got its turn. That arm exists because of the opposite bug (round 2's storm: a permanently failing retry whose stale timestamp left the backoff always elapsed, firing on every ~100ms frame), so neither "always restart" nor "never restart" is right — the two cases genuinely differ. `SyncOutcome::RetryFailed` carries the distinction: `spawn_retry` maps `retry_commit`'s `Failed` to it in one place, so `apply_outcome` never has to ask where an outcome came from. `RetryFailed` restarts the backoff; `Failed` leaves it untouched. This is the same reasoning that made `RetryAbandoned` its own variant rather than an out-of-band `last_spawn_was_retry` flag, and it keeps `apply_outcome` a total match. `an_unrelated_content_failure_does_not_starve_an_armed_retry` pins both directions.

**An external reload drops a queued sync request, for the same reason it drops undo history.** Deep rounds 2, round 1. A write queues a `PendingSync` carrying the exact content it just put on disk, drained by the main loop after the key that caused it. If an external edit is reloaded while the request is still queued, that content is no longer what the file holds. `run_sync` does refuse it — the `latest_requested_hash` staleness check catches it and reports "the file changed after this sync was queued" — but that surfaces to the user as a git-sync *failure* for a situation where nothing actually went wrong: their toggle was written, somebody else edited the file, and both facts are fine. `reload_from_disk`'s adopting branch already clears `undo_stack`/`redo_stack` because state captured against the old revision no longer applies; a queued request describing that revision's content is exactly the same thing, so it is removed from the effect queue alongside them (`cancel_git_sync`). Nothing takes its place: an external edit markcheck did not make deliberately queues no sync of its own (only `e` does, via `request_external_edit_sync`, which runs *after* the reload and so re-queues correctly).

**It disarms any half-finished input chord too.** Deep rounds 3, round 4, the same class again. `clear_pending_chords` exists because a mouse click landing between the two halves of a chord left it armed against whatever the click had just selected; a reload reaches the same state by a different route, since `remap_position` can move the cursor to a different card. An armed `o` prompt would then read the user's next digit as a choice from a numbered link list that is no longer on screen, opening a link belonging to a card they never chose from — and a pending `gg` is the same shape. Both are cleared alongside the undo history and the queued sync request.

**The startup catch-up pushes and can never commit.** Deep review, round 3, reproduced end-to-end. This used to be expressed as an ordinary `GitSync::request` carrying the file's *current on-disk content*, described as `Catch up a pending push` and justified as "commit-wise a no-op in the common case (content already matches `HEAD`)". In the uncommon case it was not a no-op, and every guard `run_sync` has was satisfied *by construction*: `status` is non-empty, `HEAD`'s blob differs, and the staleness check compares disk against `latest_requested_hash` — which that very request had just set to that same content. So a checklist carrying ordinary uncommitted edits (made in an editor, with no markcheck involvement) was committed **and pushed** purely by opening the file and quitting, under a message describing a push catch-up rather than the change it actually published. Publishing is not undoable the way a local commit is, and opening a viewer must publish nothing. `catch_up_push` replaces it: a dedicated path that resolves the repo root, refuses via `repo_sync_blocked`, requires a *positively known* unpushed commit, applies `unpushed_history` with the stricter `OwnOnly` rule, and then pushes `HEAD` — with no code path that can build a commit. Where it can't tell whether there is anything to push, it fails **closed**, the opposite of `run_sync`: `run_sync` runs after a change the user just made, where silence would hide a problem, whereas nothing has happened here, so every unanswerable question (no upstream, no commits, an unreadable count) means "do nothing, quietly" rather than nagging on every launch. `commits_ahead_of_upstream` was split out of `ahead_of_upstream` so both callers get their opposite failure direction from the same one subprocess. Two *known* states are still reported at startup even with nothing to push, because each means git-sync can't work for this file right now and the title bar's `⇅ git` would otherwise suggest it can: a blocked repository (`repo_sync_blocked`'s refusal — a merge, rebase, cherry-pick, revert or bisect in progress, unresolved conflicts, a detached `HEAD`, or that guard being unable to check one of these, which it treats the same way here as in `run_sync`) is returned as `Failed`, and an untracked checklist as `SkippedUntracked`, preserving what the old startup request surfaced. The trackedness lookup therefore runs *before* the ahead-count short-circuit — it used to run after it, so an untracked checklist on a fully pushed branch went unreported until the first toggle (`catch_up_push_reports_an_untracked_checklist_on_a_fully_pushed_branch`). Only a definite "not tracked" answer is reported early; an index lookup that errors is held back and only becomes `Failed` once there is something to push, so it stays quiet like the other unanswerable questions. `git_sync_does_not_commit_uncommitted_changes_just_because_the_file_was_opened` (PTY, driving the real binary — the only level that reaches this wiring) is the regression test, verified to fail against the pre-fix code with exactly the original signature.

**Quitting waits for a sync in flight, says so, and never orphans it (#5).** A sync is a dozen or more `git` subprocesses plus hooks and network round trips, and every thread dies the instant `main` returns, so quitting mid-sync used to leave `markcheck-index-*` in the git dir, an orphaned `git commit` that could still move `HEAD` with the real index never aligned, and scratch and lock files behind. Three layers now cover it:

- **`q` while a sync runs.** When a drain reports `Effect::Quit` and `GitSync::is_busy()`, the loop doesn't exit: it sets `quitting` and shows the sticky notice `Waiting for git sync… press q again to abandon` (`AppState::set_notice`, sticky but not error-colored), and the loop goes on polling. It breaks as soon as the sync settles, recording the outcome for the exit report. While `quitting`, every key but `q` re-shows the notice and mouse and paste are ignored, so nothing queues another sync; a second `q` abandons (`abandon_git_sync`).
- **Signals.** `stop_on_signals` (via `signal-hook`) sets a flag on `SIGTERM`, `SIGHUP` and `SIGINT` (raw mode keeps Ctrl-C a key, so `SIGINT` only comes from `kill`); a second `SIGTERM`/`SIGINT` exits at once (`register_conditional_shutdown`). The loop checks the flag every tick (`event::poll` returns within 100ms) and returns without drawing anything, since after `SIGHUP` the terminal is gone: it waits up to `QUIT_WAIT` (5s) for the sync, then abandons whatever is left, and `main` restores the terminal and writes the exit report with errors ignored.
- **Abandoning** (`GitSync::abandon`) works through `process::Children`, a registry each `GitSync` owns and its worker threads install in a thread-local (`track_children_on_this_thread`; code outside a worker gets a private registry nothing abandons, which keeps tests isolated). A child is spawned, reaped and signalled only under the registry's lock, so an abandon can't signal a reaped child's recycled PID or miss one spawned meanwhile, and once abandoned the registry refuses to start another git. `abandon_git_sync` sends `SIGTERM` to the running group (git's handlers remove its locks; the hook shares the group), gives the worker `ABANDON_GRACE` (2s) to unwind through `commit_via_temp_index`'s cleanup and the `ScratchFiles` drops, then repeats with `SIGKILL` if it's still busy.
- **The startup sweep** covers what no handler can catch (`SIGKILL`, the OOM killer, a power loss): `writer::sweep_interrupted_saves` removes `.<name>.markcheck-tmp-*` and `.<name>.markcheck-new-*` beside the checklist, and `GitSync::sweep_interrupted_syncs` removes `markcheck-index-*` (and `.lock`) in the git dir, both through `writer::remove_leftovers`: only regular files whose name parses as `<pid>-<hex>…` and whose PID is provably gone (`pid_is_gone`, the same `/proc`/`ps` proof as the write lock, never this process). The count joins the startup message (`removed N files left by an interrupted markcheck`).

What quitting deliberately does *not* wait for is a pending retry's backoff: after `CommittedNotPushed` the commit is safely local, `busy` is already clear, and the startup catch-up push picks it up next launch. **The exit wait's result is reported, not discarded.** The outcome the quit waited for, or the last one seen while abandoning, goes to `git_sync::exit_report`, which turns anything other than `Synced`/`Skipped`/`RetryAbandoned` (and a sync still running) into one line that `main` prints to stderr after dropping `TerminalGuard`. The exit status is unchanged (0). `tests/pty.rs` covers each path: `quitting_during_a_sync_says_it_waits_and_quits_once_it_lands`, `a_second_q_abandons_the_sync_and_leaves_nothing_behind`, `sigterm_mid_sync_quits_cleanly_and_leaves_nothing_behind` and `quitting_right_after_a_toggle_whose_sync_fails_says_so_after_the_tui_closes`.

**Commit message:** `<file name>: <change description>`, e.g. `checklist.md: Check "Restart service"`. The change description names the actual transition (`Check`/`Uncheck`/`Start` + the toggled item's `header`/`display_text`; `Reset all tasks to not done`; `Undo: N items`/`Redo: N items`) rather than a generic "updated by markcheck" — these commits accumulate across hosts, so a message naming what changed is more useful in `git log`/`git blame` later than a constant string would be.

**Failure reporting:** a failed `status`/`commit` becomes `SyncOutcome::Failed(message)` (the failing command's name plus the line that says why, chosen by `process::failure_reason` from stderr — or from stdout when stderr gives no reason, since a refused `git commit` such as "nothing to commit" explains itself only there (#127), so `unknown error` appears only when neither stream says anything: blank, `hint:` and `To <url>` lines are skipped; a push's `! [...]` ref-rejection line wins — or, for a `[remote rejected]` one, the remote hook's own first `remote:` message — then git's first `fatal:`/`error:` line, and otherwise the **last** line, since hook frameworks print banners such as `[INFO] Initializing environment` first and the actual failure last (#53)) and is surfaced via the existing `set_error` sticky-red-status convention — no new UI channel. A failed push after a successful commit instead becomes `SyncOutcome::CommittedNotPushed { message, commit }`, reported the same way but with wording that says the commit is safe and a retry is coming (`Committed, not pushed: {message} (will keep retrying)`; a retry that fails again reads `Push retry failed: {message} (will keep retrying)`) rather than the flatter "Git sync failed", since silently retrying without saying so would look exactly like the sync had gone quiet again — `commit` isn't shown to the user, it's what `GitSync` remembers internally to retry the *push*, not the commit (see "Commit succeeding and push succeeding are tracked separately" above). `SyncOutcome::SkippedUntracked` goes through the same `set_error` call with a fixed message ("Git sync skipped: file is not tracked in git…") rather than a per-attempt one, since there's nothing per-attempt to say — it fires on every sync attempt for as long as the file stays untracked, the same as a real `Failed` would, rather than only once, since there's no persistent "this file is untracked" flag to gate it on (unlike the file-deletion notice, which does track `AppState.file_deleted` to fire exactly once). A successful sync is *not* echoed to the status bar (that channel is reserved for problems and deliberate-keypress responses); instead it drives the title-bar "Synced … ago" tag — see Title bar, below. The exception is the first success after a failure, which says `Git sync caught up: committed and pushed` (an ephemeral `set_status`), since that is the moment the earlier red message stops being true. **A push failing again for the same reason is not re-reported** (#64): `retry_push_if_due` fires for the whole session while a push keeps failing, and every `set_error` replaces whatever message is showing — a lock-refusal path, a reload notice, `Match 2/5`. So `apply_git_sync_outcome` remembers the reason last reported for `CommittedNotPushed`/`RetryFailed` in `git_sync.reported_reason` and skips the status bar when the next push failure carries the same one; the title bar's `not pushed` state carries it in the meantime. A new reason is reported, and content-sync `Failed`/`SkippedUntracked` outcomes, which follow the user's own edits, are reported every time.

**The status bar reports, the title bar remembers:** the title-bar icon (see Title bar, below) is *persistent* — whether the feature is active *at all* this session, never expiring — and the state text after it says where the file stands right now: `syncing…`, `Synced … ago` (*ephemeral*, fading after 2 minutes), or an error-colored `not pushed`/`not synced`/`not tracked` that stays until a later sync lands. A failure's detailed message still goes to the status bar, but a sticky status message is cleared by the next keypress — usually within a second, mid-procedure — so before #64 the only lasting signal was a green `⇅ git`, often with an *earlier* success's `Synced 40s ago` still beside it, while every push of the session was failing. The failed state also clears `last_at`, so an old success can never vouch for newer changes.

**A worker that dies must not take git-sync down with it.** `GitSync.busy` is cleared in exactly one place — `poll`, on receiving an outcome — and the channel never reports `Disconnected`, because `GitSync` holds its own clone of the sender. A worker thread that ends without sending therefore leaves `busy` stuck `true` for the rest of the session: every later `request` coalesces into `pending` and never spawns, `retry_push_if_due` returns immediately, and quitting burns the full `wait_for_git_sync` budget — git-sync permanently dead, with nothing on screen saying so. Two guards, both deep-review findings. `run_reporting_panics` wraps each worker body so a panic becomes an ordinary `SyncOutcome::Failed` rather than a lost outcome; it's a backstop for unknown paths, deliberately untested (forcing a panic through it would mean adding one to production code just to observe it). `lock_hash` recovers a poisoned `latest_requested_hash` instead of unwrapping it: that mutex guards a plain `[u8; 32]` digest, overwritten wholesale, so there's no half-updated invariant for poisoning to warn about — and one of its two lock sites is `GitSync::request`, on the **main** thread, where an `unwrap` would convert a background panic into a TUI crash several frames later, disconnected from anything the user did.

**Races are tested by interleaving, not by pre-arranging state.** Deep round 3. Every review of this module made the same observation: its concurrency tests construct the repository state *before* calling the function, which pins the resulting invariant but never exercises the actual check → race → use ordering. `RacePoint`/`race_point` are named points inside a sync — after history validation, before the commit, before index alignment, before the push — where a test can run a real concurrent git process at exactly the moment that matters. Outside `cfg(test)` `race_point` has an empty body, so the shipped binary carries nothing. Hooks are **thread-local**: tests run in parallel in one process and drive `run_sync`/`catch_up_push` on their own thread, so a global registry would have them firing each other's hooks. This is what found the `undo_commit` defect above, which no amount of pre-arranged state would have surfaced — the window it exploits only exists *during* a commit.

**No repository-level lock across multiple `markcheck` processes — a known, accepted limitation, not a broken invariant.** External review, round 5: `GitSync.busy`/`pending` only serialize requests *within one process* — two independent `markcheck` processes (or `--git-sync` invocations) against the same repository and the same checklist file share no lock at all. This is deliberately not treated as a bug: the individual races that scenario can produce are already covered by the checks each involved piece already makes on its own — `commit_via_temp_index`'s `parent` re-check, `verify_commit_scope`'s exact-SHA diff, `undo_commit`'s CAS-guarded rollback, `push_if_head_unchanged`/`retry_commit`'s `HEAD` check, and `push`'s explicit-commit targeting (all above) — each of which fails safely (refuses, retries, or narrows the window) rather than corrupting anything, regardless of which process the interference comes from. What this lacks is a *single* transaction boundary tying those checks together: each new git-sync feature has to independently remember to add its own guard against concurrent movement, rather than inheriting one for free from a shared lock. That's a maintainability concern for future changes, not a correctness gap in the current code. The file-write side *did* get an advisory lock (`writer::WriteLock`, see "An advisory lock makes that check-then-write a real compare-and-swap" above), because there the two writers that race are realistically two markcheck instances and the lost update is silent. Here a lock would only ever serialize *cooperating* `markcheck` processes, not a human or another tool running `git` concurrently — which the existing checks already have to tolerate regardless, and do, by failing safely. Not implemented for that reason.

On **narrow** terminals (overview hidden, `<60` cols) the tabs move to a **dedicated row** directly below the title bar (and only when there's more than one list). The **status-bar legend** is `KEYBIND_LEGEND` (`ui/statusbar.rs`), truncated to the terminal width: `hjkl:nav  space:toggle  /:search  y:copy  ?:help  q:quit` — trimmed to essentials, with `?` as the full keybinding reference. The two completion screens get their own legends listing only keys that work there: `LIST_COMPLETE_LEGEND` (`l/enter:next list  h:review  ?:help  q:quit`) and `ALL_COMPLETE_LEGEND` (`h:review  R:reset  ?:help  q:quit`).

Layout tree:

- **Width cap:** before anything else, `render` centers the working area at `Max(120)` columns via a horizontal `Flex::Center`; wider terminals get blank side margins, narrower ones use their full width. Everything below (title/main/status) lives inside this capped area.
- `Layout::vertical` → title (1 line), **list-tab row (1 line, narrow multi-list only)**, progress bar (1 line), main (fill), statusbar (1 line, or more for a long status message — see Status bar below). The tab row is inserted between the title and the progress bar only when the overview is hidden (`!overview_shown`) and there's more than one list; the constraints are built conditionally.
- Main → `Layout::horizontal` → cards (`Min(0)`), a 2-column gap, overview (`Length(30)`) — the gap keeps the "next" side card off the overview list.
- **Card row:** sized to the current item's content — `desired_card_height` measures the wrapped body (at the width the card will actually render, `current_card_width`) plus borders and clamps it to `[MIN_CARD_HEIGHT, ~60% of the main area]`. The card is vertically centered via `Flex::Center` with the rest empty — but when the list heading/banner rows are shown, the heading rows and the card are centered **together as one block** so the heading hugs the card instead of floating at the top; see List header. Short tasks get a compact card (removing the old empty-body void); long tasks get more room before scrolling. The completion/confirm modal cards size to their own content instead (`modal_card`, below).
- **List header:** on the `Checklist` screen, `render_checklist` renders reserved rows for the current list's `## H2` title (`render_list_heading` — ` {list icon} {title} ` centered, `palette.current` bold, matching the overview's current-list row; kept to one row and cut with `…` via `ui::truncate` when wider than the area). The heading rows sit just above the card, separated from it by a **single blank spacer row** — mirroring the one-row gap below the card before the link panel, so the card sits symmetrically between them. The `[reserved rows + card]` group is centered together as a single block via `Flex::Center`, so the heading stays visually tied to the card rather than pinned to the top of the area. It's shown only when the current list has a real H2 — suppressed for the synthesized `(Default)` list (`current_list_index == 0 && document.has_default_list`). Sits above the card row in the cards column only (never the overview).
- **List banner:** when `list.banner` is set (a leading bold-only bullet), the block gains one row per wrapped line of the banner (`banner_rows` word-wraps `{info icon} {banner}` with `wrap_text` to `current_card_width`, so a long warning is shown in full rather than clipped at the edge — it carries the precondition, and a cut one reads as complete), rendered **directly below the H2 title with no blank line between them** (the title and banner read as a heading + sub-header pair); the single blank spacer then sits below the banner, above the card. For a title-less default list the banner takes the top row, still one blank spacer above the card. `render_list_banner` centers each wrapped row in `palette.warning` (amber/orange) bold. It's a warning line, not a card, and is skipped by all navigation (it's not an `Item`). The reserved rows (title/banner + the one spacer) are only taken when there's room for both them and the card (`area.height > content_h + reserved`); otherwise the heading/banner are dropped and just the card is centered.
- **Sub-section breadcrumb:** when the current item has a non-empty `section` (`### H3`+ sub-section path), the reserved block gains one more row — **directly above the blank spacer, nearest the card** — showing the path as a dim, centered ` › `-joined breadcrumb (`render_section_breadcrumb`, e.g. `Outer › Inner`), **clamped to the card width with an ellipsis** (`ui::truncate`, the same helper the list tabs use) so a deep or long path can't overflow the card on a narrow terminal. It keeps the single-card view (narrow terminals, where the overview and its dividers are hidden) oriented about which sub-section it's in. Absent when the item sits directly under its H2. Stacking order top→bottom is thus: H2 title, banner, breadcrumb, blank spacer, card.
- **Card stack:** manual `Rect` math — the center card is full height and `CENTER_CARD_PCT` (72%) of the row width; the side cards fill the remainder, tucked 1 row down, 2 rows shorter, and extend ~4 columns (`STACK_OVERLAP`) underneath the center card. Both side cards are anchored to the center card's own edges (not the row's edges), each starting `STACK_OVERLAP` columns under it, so an odd leftover width can't open a 1-column gap between the center card and the next (right) card. The same `CENTER_CARD_PCT` drives both `current_card_width` (height measurement) and `center_width` (the rendered Rect). Render order: prev, next, `Clear` on the center rect (ratatui doesn't blank covered cells), then the center card on top.

**Card anatomy:** display-only note cards use a **rounded** border while task cards use a **thick** border (thick replaced the old double border for a bolder, cleaner "actionable step" frame), so a note reads as information rather than a step. The top border carries a state icon (done/pending/started/note from `IconSet`) on the left and the position status ` n/m ` on the right. **Card title:** the item's leading `**bold**` (`Item.header`) is shown *inside* the card — not in the border — as the first body lines via `card_title_lines`: `{info icon} {header}` word-wrapped to the card's inner width (`card_title_rows`, `wrap_text`) with each row centered, followed by a blank separator, then the body. The **title text is bold in the terminal's default foreground** so it always contrasts with the background and stays legible (it was previously `palette.note` blue, which could wash out on some backgrounds); the leading info icon keeps `palette.note` (blue) as a small accent (shared with the list banner, but blue rather than the banner's amber). Items with no leading bold show no title line. **Step numbers:** an ordered-list item's `ordinal` (the marker as written, read from the source at the item's start by `ordered_marker` in the parser, so non-sequential author numbering survives) leads the title (`{info icon} 3. {header}`), or, with no title, the body as a bold first token (`body_tokens`); side cards, the overview, the `T` picker, the parent breadcrumb and git-sync commit descriptions all name an item through `Item::label()`, which carries the same prefix. The ` n/m ` position is unchanged and still counts every card. The title's wrapped rows count toward `desired_card_height` (through the same `card_title_rows`, so the card grows by exactly what is drawn) and scroll/center with the body. The bottom border carries a left-aligned pilot-style position dot strip for the list's items (`position_dots` — current `◉` cyan, done `●` green, started `●` yellow (`◐` under `NO_COLOR`), pending `·` dim, and a display-only item a `·` in `palette.note` blue so the strip stays a faithful item map while reading as information, not a pending task), and a right-aligned dim ` first–last/total ` scroll indicator when the body overflows, alongside a **scrollbar** on the right border (`render_scrollbar`). **Budgeted together:** whether the dots fit and whether the indicator is needed (`max_scroll > 0`) are both known before either title is added, so their widths are checked jointly against the card width — the two used to be decided independently, letting ratatui's title truncation silently eat the dots' current-item marker (`◉`) to make room for the indicator on a long list with a wide card. When both can't fit, the indicator (the harder functional need once the body overflows) wins and the dots are dropped entirely rather than truncated. The body has no `[ ]`/`[x]` prefix and sits inside `BODY_PAD` columns of horizontal padding so text isn't flush to the border; it's vertically centered when it fits, top-anchored and scrollable (`card_scroll`) when it overflows. The current card renders the item's ordered `body` spans as styled, word-wrapped `Line`s via `body_lines()`/`wrap_tokens()`. Prose is in the base style and **centered when it fits in ≤`PROSE_CENTER_MAX_LINES` lines, else left-aligned** (set per-`Line`). Inline `` `code` `` is drawn in the palette's `code` style (light fg on a subtle gray background, markdown-style, rather than a loud foreground hue; keeps yellow meaning only `started`). **Inline styling:** `body_tokens` carries a per-token `SpanStyle` (widened from the old code/not-code bool) that `wrap_tokens` maps to modifiers — emphasis→italic, strong→bold, strikethrough→crossed-out; a `Link` renders as just its underlined text — the URL is **not** shown inline, because a long URL wrapped ugly mid-token on narrow cards; it's shown in a panel **below the card** instead (see below). When a card has **two or more** links, each link text is followed by a dim `[N]` marker (1-based, document order) that keys it to the numbered list below the card; a lone link gets no marker. Colour isn't used for these, keeping the `code` style exclusive to commands. Commands are numbered the same way for `y`'s digit prompt (see Clipboard), but only among `y`'s candidates and only when there are two or more: each inline chip — the trailing command included — gets a dim `[N]` glued right after it (`inline_command_number`), and each fenced box carries its number in its top border, `┌─[N]──┐` (`code_block_lines`'s `marker`; a card too narrow for a box puts `[N]` on its own row above the code instead). **Trailing command:** when the item's *last* meaningful body span is inline code (`body_tokens` — trailing whitespace-only text ignored), that command is split onto its own line below a blank separator, so a lead-in and its command read as two tidy blocks; inline code followed by any text stays in the flow, and a body that is only a command has no leading blank. Fenced `code_blocks` are appended below, **left-aligned inside a light box in the `code` style** (`code_block_lines`) preserving their own line breaks (hard-wrapped; falls back to plain left-aligned lines when the card is too narrow for a box). **Continuation marker:** every row a source line wraps onto the next ends in a dim `↩` (`CONTINUATION`, `continuation_style`) — in the box's right padding column (`soft_wrapped` flags each piece but a line's last), or in a cell reserved at the row's end in the unboxed fallback (none at width 1) — and `wrap_tokens` does the same for a code chip it hard-splits, splitting at `width − 1` so the marker fits. Without it a wrapped command was indistinguishable from a real line break, so a delete command split mid-path read as two commands. **Tabs:** ratatui never draws a control character, so a tab in a command used to vanish while still being counted as one cell — tab indentation was lost and the box's closing `│` shifted left on every tabbed row. `expand_tabs` (`ui/mod.rs`, `TAB_WIDTH` = 4) expands tabs to spaces for display only: per source line in `soft_wrapped` (before `hard_wrap`, so stops count from the line's start) and per code token in `wrap_tokens` (stops count from the chip's start). `Item::code_blocks`/`code_spans` and the copy targets keep the original text, so `y` and click-to-copy still yield the real tabs. Row counts are unchanged, so `code_rows` stays index-aligned and scroll clamping exact; the marker is never part of copied text. The box **always spans the full card-body width** — `box_w` is the full content width, not the longest content line — so the code background reaches both edges even for a short one-line block and successive blocks align, matching a rendered Markdown block. Margins (bounded by the cell grid — whole cells only): the inline chip is padded a space each side, and the box keeps a one-space left/right margin and a blank code-styled row just inside the top and bottom borders. Per-`Line` alignment lets prose and code differ within one body while `body_lines` keeps exact line counts for scroll clamping. Items with an empty `body` fall back to `display_text`. Side cards stay plain text (`side_card_lines`): the bold title (`Item.header`, no icon) when present, a blank separator, then `display_text`, each wrapped to the side card's width — so a neighbour is recognisable by the same name the overview and pickers use, and a title-only task is never an empty box. All three cards vertically center their body the same way via the shared `top_pad(len, height)` helper. **Everything that fits text to a row measures display cells, not characters.** A wide glyph (East Asian, most emoji) takes two cells, so a character count under-measures it. Deep review, round 3, reproduced via `TestBackend`: `code_block_lines` pads content out to a fixed inner width, so measuring a row of wide characters by character count pushed the closing `│` off the row to be clipped — the box rendered visibly open. Prose had the same flaw, worse: `wrap_text`/`wrap_tokens` judged a line of wide characters to fit when it was up to twice the card width, and since card lines are drawn without ratatui wrapping the overflow was clipped and never shown — scrolling didn't help, because the line count agreed it fit. `display_width`/`char_width` (in `ui/mod.rs`; ratatui's own `Span::width`, `unicode-width` underneath, no new dependency) now drive the box padding, `hard_wrap`'s chunking, prose wrapping (`wrap_text`, `wrap_tokens`, which hard-split overlong words through `split_at_width` — at least one glyph per row, so a glyph wider than the row still makes progress), and every truncation (`truncate`, `fit_tab_titles`, the header's `split_width` budgets, the card breadcrumb, the overview's section dividers). Line counts stay exact for scroll clamping because the renderer and `desired_card_height` wrap through the same functions; the renderer writes `card_max_scroll` back into `AppState` each frame. State accent (`state_color`): Done → `palette.done`, Started → `palette.started`, else default — applied to the border and the position status via `accent_color`, which is `state_color` except that an **idle display-only note falls back to `palette.note` (blue)** so its frame (border + ` n/m `) matches its blue note icon and inside-title rather than sitting at the default color; tasks are unaffected (a pending task frame stays default). **Display-only parents reflect their sub-list:** `state_color` takes the parent's aggregate child state (`List::info_parent_state` — `Done` when it has ≥1 descendant checkbox and all are done, `Started` when ≥1 is started-or-done but not all done, else none), so an info parent borrows the same green/yellow accent a task would while its **rounded border keeps saying "information"** — shape encodes kind, color encodes state — and takes the **note blue** when nothing is under way (matching the icon, via `accent_color`). The top-left `header_line` note icon takes the same accent (the note *glyph* is unchanged, only its color, staying `palette.note` blue when nothing is under way); `info_parent_state` never feeds `checkbox_progress`, so `done/total`, the progress bar and completion detection are unaffected. The border is bold on the center card and dim on side cards; the body is dimmed only when Done (a started body stays normal, the code color still shows through). Side cards are always dim.

**Responsive tiers:** measured against the width-capped area, driven by `OVERVIEW_MIN_WIDTH` (60) and `NARROW_THRESHOLD` (80, checked on the *card-area* width left after the overview split). Three tiers result: **narrow** (< 60 cols — single full-width card, no overview), **medium** (overview shown but the card pane is < 80 so still a single card), and **wide** (overview + the three-card stack).

**Title bar:** split into two independent `Layout::horizontal` chunks, `[left(Min 0)] [right(Length)]`. The **left chunk** is purely static identity — a leading space then `{file icon} {document title} │ {filename}` — the title is the first `# H1` in `palette.current` bold, the filename a dim secondary joined by a dim `│` separator; when there's no H1 a title derived from the file stem (`scaffold::derive_title`, the same one `--new` writes) stands in with the same style, filename still shown — a missing H1 is valid Markdown, so nothing error-colored appears here. Nothing dynamic lives here.

**Right-hand cluster:** everything about the file's *current state* — recency, git-sync, progress — reads together on the right rather than trailing the filename on the left (moved here from the left group specifically so the left side could be pure identity and the right side pure status). Built by measuring each present piece's text width up front, then sizing the right chunk to exactly that combined width (tags + ` │ ` separators + the counter) — so it's a variable-width block that grows or shrinks as tags come and go, but the **counter is always its last (rightmost) element**, meaning the counter itself never shifts position on screen even though the tags before it do; only their combined leftward reach changes. a leading space then `{done icon} done/total` is that final, outermost piece. Its color **fades with completion:** `Palette::progress_color(done, total)` returns a two-stop ramp — started-yellow (nothing done) → done-green (complete) — driven by the `done/total` ratio, so progress is glanceable from the counter's hue alone rather than a flat color. It **starts at yellow rather than gray** so the counter is legible even at 0% done (`total == 0` counts as complete/green, preserving the old `done == total` behavior for a doc with no checkboxes). The ramp is resolved per color depth: a smooth 24-bit RGB lerp on TrueColor, the same lerp snapped to the nearest 256-color-cube/gray-ramp index (`rgb_to_256`) on Palette256, and a coarse stepped ramp of named colors (`Yellow` → `Green` → bold `Green`) on Basic, which can't interpolate. This is the **single** `done/total` counter: the overview panel used to carry a copy, but since the title-bar counter is always shown whenever the overview is (the wide layout), that copy was pure duplication and was removed — progress now reads from this counter plus the full-width progress bar below.

Before the counter, in cluster order: the `Updated Ns/Nm ago` tag — relative elapsed time since the content last changed, **either** our own write (toggle/reset) **or** an external reload — is a dim-yellow span, prefixed with the **refresh icon** (`IconSet.update`, `\u{f021}` Nerd / `↻` plain) rather than `[ ]` brackets, since the ` │ ` separator and the dim-yellow style already set it apart; hidden below 80 columns and once ≥2 minutes old. It reads "Updated just now" under 5s, and the seconds are floored to 5s steps so it changes at most every ~5s rather than every render. Then the git-sync section (see below), when active. The title bar itself never carries the list tabs.

**Git-sync section:** appends after the update tag behind its own ` │ ` separator, gated on `AppState.git_sync.active` (set once at startup — see Git Sync, above) rather than on any per-sync state, so it's either fully present for the whole session or fully absent, never flickering in and out as syncs come and go. `{icon} git` is a **persistent** "git-sync is on" indicator, shown from startup regardless of whether anything has synced yet; a relative `· Synced Ns/Nm ago` label **appends** after it, in the same section, only while a completed sync is still recent (`AppState.git_sync.last_at`, set by `record_git_sync()`), and drops away again on its own once stale — leaving just `{icon} git`. The literal word **"git"** is part of the label on purpose, not just the icon: two earlier icon-only attempts (a generic cloud-upload glyph, then a `fa-git` Nerd Font logo) both turned out illegible/unrecognizable on the reporting user's terminal, so the text carries the meaning and the icon (`IconSet.sync`, a plain `⇅` Arrows-block character — deliberately the *same* glyph in both `nerd()` and `unicode()`, since a Nerd Font Private Use Area codepoint was exactly what failed to render) is now just a small visual anchor, not load-bearing on its own. The relative-time half reuses the update tag's mechanism exactly — `relative_label(verb, at, now)` is the one function both tags call (parameterized on the leading verb, `"Updated"`/`"Synced"`), so the wording, the 5s-floored steps, and the 2-minute lifetime are shared, not reimplemented. The whole section shares the update tag's 80-column width gate. Colored `palette.done` (green) rather than the update tag's `palette.started` (yellow), so it reads as its own distinct signal rather than the update tag's neutral "something changed" note. `ui::sync_section` picks the text and style by precedence: `git_sync.problem` set → `{icon} git · not pushed` (or `not synced`/`not tracked`) in `palette.error`, outranking even a running retry; otherwise `git_sync.busy` → `{icon} git · syncing…` in dim `palette.started`; otherwise the green `Synced … ago`/bare form above. The problem state is set and cleared only by `apply_git_sync_outcome` (see Git Sync, above), never by input, so it survives the keypresses that clear the status bar.

**List tabs — dedicated row on narrow:** `render_list_tabs` draws the `[n] Title` strip (current list a black-on-`palette.current` pill, others dim) in **its own full-width row** just below the title bar, and only when the overview is hidden *and* there's more than one list. When the overview is visible (wide) it already lists every list, so no tab row is drawn; a single-list doc gets no row either (no wasted line). Giving the strip the whole row (rather than cramming it into the title bar) leaves room for the titles — **Tab fitting:** `fit_tab_titles` shows every list tab at full length when they fit (now usually the case), truncating proportionally (never below 3 chars each) only when they overflow, and falling back to just the current tab (truncated to 20) when even that won't fit. The above-cards list header still shows the *current* list near the cards in both tiers, mirroring how the overview + list header pair up on wide.

**Progress bar:** `render_progress_bar` draws a one-row completion bar under the title bar from `Document::checkbox_progress() -> (done, started, total)`: `━` in `palette.done` (green) for the done portion, then `━` in `palette.started` (yellow) for started/in-progress tasks, then `─` dim for what remains. Widths are proportional via `progress_fill`, with the started segment clamped so the three never exceed the row width. (`checkbox_stats()` now derives its `(done, total)` from `checkbox_progress`.)

**Icons:** `IconSet` in `model.rs` — Nerd Font glyphs by default (classic Font Awesome range, retained by Nerd Fonts v3), `--no-nerd-font` swaps plain-Unicode symbols (`☑ ☐ ❯ ▪ ≡ • ↻`) for terminals without a patched font. `sync` (`⇅`) is the one exception to both halves of that rule — a plain Arrows-block character in *both* icon sets, paired with a literal "git" text label wherever it's used, rather than a Nerd Font glyph relied on to read as "git" by shape alone (see Git-sync section, below).

**Overview:** a progress view that takes no *keyboard* input, but its rows are **click targets** — click a label to jump to a task, a task's marker to toggle it (see Click-to-copy below). Rows: `{list icon} [n] Title` (current list cyan), a non-selectable `palette.warning` banner row (`{info icon} {banner}`, cut with `…` to the panel width — the full banner is wrapped above the cards) below the title when the list has one, and item rows with markers by precedence `☑` done (`palette.done`) > `◐` started (`palette.started`) > `▪` display-only note > `❯` current > `☐` dim pending — so an item's kind/state stays visible even on the current row (the list's own reversed-highlight already marks "current"). The `❯` current marker is `palette.current` (cyan) at the top level, but a **nested** current row tints it with the item's **own sub-list depth color** (its immediate parent's `sublist_slot`, the same color as its deepest `│` guide) so that under the row's `Modifier::REVERSED` highlight the marker's background matches the colored depth guides on the row instead of clashing with a cyan block. A display-only row's note marker (and, when all its children are done, its label) takes its sub-list's aggregate state color (`info_parent_state` — note blue / started yellow / done green with a dimmed label), matching the card. Items show `Item::label()` — their `header` when present, otherwise `display_text`, prefixed with the ordered-list step number (`ordinal`) if any — cut with `…` (`ui::truncate`) to the width left after the indent, guides and marker so a long label never ends mid-word with no sign of the cut. **Sub-section dividers:** before an item whose `section` path diverges from the previous item's (a common-prefix diff via `new_sub_headings`), the overview inserts a non-selectable `── Text` divider row per newly-active `### H3`+ heading (`section_divider` — a bold label between dim rules, indented by heading level and filled to the panel's inner width), so each group of cards reads under its sub-heading. The label is truncated with an ellipsis when it doesn't fit (`section_divider_line`, via the same `truncate` helper the card-side breadcrumb uses) rather than being hard-clipped by the render area. These rows are `RowClick::None` (like the banner) and don't shift the selection. **Sticky header:** as the rows are built, the renderer records per row its pinnable ancestor context (`row_sticky: Vec<StickyContext>`, aligned with `list_items`): the list's `[n] Title` header row (multi-list only) and the active `### H3`+ path as `(SubHeading, divider row index)` pairs, via a per-list `active_stack` that mirrors each item's `section`. The header is rendered **reserve-space**, not overlay: the panel's block is drawn first, and the sticky rows occupy reserved rows at the *top* of the content area with the scrollable list rendered *below* them (`inner.y + reserved`), so a pinned header never covers a list row. How many rows to reserve depends on the scroll offset, which itself depends on the reserved rows (they shrink the list viewport) — so the renderer iterates to a fixed point (bounded at 4 passes): render the `List` into the content area below `reserved` rows, read back `ListState::offset()`, and recompute the pinnable set for the row now at the top (`list_header_line` / `section_divider_line`, for every ancestor whose own row is `< offset`); it converges immediately while the top row stays within one group, since that group's ancestor chain is constant. The pinned set is always a prefix of the chain (an ancestor's row always precedes its descendants', so a scrolled-off deep level implies its shallower ones scrolled off too), capped so it can't fill the whole panel, and each reserved row is `Clear`ed before its header line is drawn (so nothing from an earlier pass bleeds through). So deep in `Deploy › Pre-flight › Data safety`, all three stay pinned above the still-visible list rather than just the deepest, and no content is hidden. The panel title is just ` Overview ` — it carries **no** `done/total` counter: that count is shown once, in the always-on title-bar counter directly above (a copy here was pure duplication, since the overview is only visible in the wide layout where the title-bar counter is too). **Single-list docs:** when there's only one list the `[1] Title` row is dropped — the number is meaningless, the title already appears above the cards as the list header, and a title-less `(Default)` list would otherwise read `[1] (Default)`. Items (and any banner) then de-indent one level so top-level rows sit flush at the left margin (`item_indent(depth, has_list_header)`); nesting still adds a level per `depth`. Multi-list overviews are unchanged. The panel's block carries `Padding::horizontal(1)` so rows sit a column in from the border, matching the card body's `BODY_PAD`. When the rows overflow, a **scrollbar** on the right border (`render_scrollbar`, driven by the `ListState`'s own scroll offset) shows the position. **Clickable rows:** after rendering, `overview::render` writes each *visible* clickable row's on-screen `Rect` plus an `OverviewTarget` into `state.overview_rows`. Because each row is exactly one line (the `List` truncates rather than wraps), the mapping is `y = inner.y + reserved + (row_index − offset)` for rows inside `[offset, offset + content_viewport)` — the list is rendered below the `reserved` sticky-header rows, reading the final `ListState::offset()` back after the render. The reserved header rows carry no click target (non-interactive, like a divider). A **checkbox item row is split into two zones:** its **marker prefix** (the left edge through the indent + state icon + trailing space, `marker_cells` wide — computed as the prefix's char count, since every `IconSet` glyph and the indent are single display cells) → `OverviewTarget::Toggle(list, item)`, and the **label** to the right → `OverviewTarget::Item(list, item)`; the two tile the row with no gap. A **display-only item row** and a **list-title row** each map their whole width to one target (`Item` / `List`); banner rows are skipped. The field is cleared when the overview isn't shown (narrow terminals), so stale rects can't be clicked. (The renderer builds a per-row `RowClick` — `None` / `Whole(target)` / `TaskItem { .., marker_cells }` — that this loop turns into the rects.)

**Scrollbars:** the cards, the overview, and the help overlay share `render_scrollbar` (`ui/mod.rs`) — a ratatui `Scrollbar` drawn over the right border (a soft `▓` shade thumb with `▲`/`▼` end arrows, the box border showing through as the track) only when the content overflows its viewport. **ratatui gotcha:** its thumb reaches the bottom only when `position == content_length - 1`, but a scroll offset maxes at `total - viewport`; so `content_length` is passed as the number of scroll *positions* (`total - viewport + 1`) so the last item lands the thumb flush at the bottom.

`cards.rs` dispatches on the overlay first (`ConfirmReset`, `ConfirmQuitReset`, `Help`, `ListPicker` replace the cards area), then, with no overlay or under `Search`, on the view: `Checklist` (stack above; a defensive "No checklist items" card if a list is somehow empty), `ListComplete`, `AllComplete`, `ConfirmReset`, and `ConfirmQuitReset` — all four go through `modal_card`, which takes the descriptive lines and the key-prompt lines separately, word-wraps both to the card's inner width (`wrap_modal_lines`, keeping each word's span style), and sizes the centered card to the wrapped rows plus borders, capped at the area. When that still doesn't fit (a short terminal, or an all-complete summary with many lists), `fit_modal_rows` trims the descriptive lines from the bottom and ends them on a dim `…`, so the `Press …` lines are never what disappears. These cards used to be a fixed 40% of the main area, which on an 80×24 terminal cut off every `Press y`/`n`/`Esc` line of both confirmation dialogs (#93). Completion cards use `palette.done` borders, `ConfirmReset` a `palette.started` border, `ConfirmQuitReset` a `palette.done` border, and `Help` a rounded `palette.current` border (`render_help`, sized to its content; when the terminal is too short it scrolls — `help.scroll`, with a scrollbar). All are threaded from `state.palette`. The completion screens lead with a green check heading, a dim rule divider (`completion_rule`), and footer hints; the all-complete screen additionally surfaces `R` to reset the whole checklist, while the per-list screen does not (resetting is a whole-document action). All these block/modal titles are padded a space each side (`┌ Title ──┐`).

**UI convention — border title padding:** every title rendered in a block/box border must be padded one space on each side (` Title `) so the border never butts against the text. This applies to all bordered panels, cards, and modals, current and future — when adding a new bordered widget with a border title, include the surrounding spaces.

Status bar shows `status_message` when set (e.g., "Copied to clipboard", "Reloaded: file changed on disk"), otherwise the keybind legend. A status message too long for one row **wraps** instead of being clipped: `statusbar::height` word-wraps it (via `cards::wrap_text`, hard-splitting an overlong word such as a path) at the content width, and `ui::render` gives the status row that many lines, capped at `MAX_STATUS_ROWS` (6) and a quarter of the terminal height so the checklist keeps most of the screen. The actionable part of the longest messages sits at their end — the write-lock refusal's lock-file path to remove, a git-sync failure's stderr line — and the UI is capped at 120 columns, so a single clipped row would never show it. The search prompt, the armed `o`/`y` digit prompts, the pending-`gg` prompt and the legend stay on one row. Messages auto-expire: **ephemeral** ones — passive confirmations and info (`Copied…`, `Reloaded…`, `Reload skipped…`, `All tasks reset…`), set via `set_status` — clear after `STATUS_TIMEOUT` (4s) of idle or on the next input; **sticky** ones carry no expiry (`status_expiry = None`) and persist until the next input, set via `set_error` for **failure / "nothing happened"** feedback — copy/reload/editor/open failures, `Nothing to copy`, `Not copied: N candidates`, `Not copied: command contains hidden control characters`, `Nothing to reset`, `No matches for "q"`, `n`/`N` with no previous search (`No previous search — press / to search`), a key the `ListComplete`/`AllComplete` screen doesn't bind (`List complete — press l for the next list or h to review` / `All tasks complete — press h to review, R to reset or q to quit`), an unbound `Ctrl`/`Alt` chord (`Ctrl-S is not bound (? lists every key)`), unsupported/absent links, the **file-deletion** notice (`File was deleted — changes cannot be saved until it exists again`), a failed git-sync commit (`Git sync failed: {message}`), a failed git-sync push after a successful commit (`Committed, not pushed: {message} (will keep retrying)`), a failed retry of that push (`Push retry failed: {message} (will keep retrying)`), and a git-sync attempt against an untracked file ("Git sync skipped: file is not tracked in git…"). `set_error` also raises the `status_is_error` flag, and the status bar renders those messages in `palette.error` (red) so failures stand out from passive confirmations (this supersedes the earlier file-deleted-only red; `set_status`/`clear_status` reset the flag). `expire_status(now)` runs each event-loop tick (the loop idle-redraws every 100ms, so it clears within ~100ms of the deadline); the four input handlers clear via `clear_status`. This is separate from the title bar's reload tag, which persists for up to 2 minutes. A failed git-sync is the only git-sync feedback that lives here — the "is git-sync active" indicator itself lives in the title bar (see Git-sync section, above), not the status bar.

## Completion Screens

### View and Overlay State

```rust
pub enum View { Checklist, ListComplete, AllComplete }
pub enum Overlay { ConfirmReset, ConfirmQuitReset, Help, Search, ListPicker }
// AppState { view: View, overlay: Option<Overlay>, .. }
```

The state is split in two: `view` is the base screen, changed by navigation, toggles and reloads, and `overlay` is an optional modal layer over it. Key dispatch is "overlay first, else view": an open overlay takes every key in `handle_key_with_mods`, before the global keys. Closing an overlay is `overlay = None`, which returns to the view it was opened from, so no return slot is needed. Only overlay handling assigns `overlay`: opening one (`/`, `T`, `?`, `R`, quit with all done), its own key handler closing it, `Ctrl-C`, and a reload cancelling a confirmation it made stale (#66). Before this split one `Screen` enum held both kinds, with a shared `screen_before_confirm` return slot, so every view change had to know which overlays might be open and clobbered them; that was the root cause of #24.

`maybe_transition_screen()` fires after every completed toggle:

```rust
fn maybe_transition_screen(&mut self) {
    let all_list_done = /* all Checkbox items in current list completed */;
    if all_list_done {
        let all_done = /* all Checkbox items in every list completed */;
        self.view = if all_done { View::AllComplete } else { View::ListComplete };
    } else {
        self.navigate_next();
    }
}
```

A `—` cell is never silent: any key a completion screen doesn't bind (e.g. `Space`, `/`, `y`) shows a sticky hint naming that screen's keys (`List complete — press l for the next list or h to review`, `All tasks complete — press h to review, R to reset or q to quit`).

`e`, `R`, `u`/`Ctrl-R`, `1`–`9`, `Tab`, `Shift-H`/`Shift-L`, `?`, and `q`/`Esc` are global (handled after the overlay dispatch, before the per-view dispatch). `Ctrl-Z` goes further: it is checked first of all in `handle_key_with_mods`, so it suspends from the overlays and from search input too. `Ctrl-C` is checked right after it (`handle_ctrl_c`): raw mode delivers it as a key rather than `SIGINT`, so, as in vim, it cancels search input, the `T` picker, the help overlay and both confirmation cards exactly like `Esc`, and on the three content screens shows a sticky `Type q to quit` error instead of quitting (it also cancels armed chords). It never quits, so it can't bypass the all-done reset offer. Right after those two, **unbound chords are rejected** (`is_bound_chord`): every handler below matches on `KeyCode` alone, so a key carrying `Ctrl`, `Alt` or any modifier other than `Shift` reaches them only when the current screen explicitly binds it — `Ctrl-E`/`Y`/`D`/`U`/`R` on `Checklist`, `Ctrl-R` on the two completion screens, `Ctrl-E`/`Y`/`D`/`U` in help, `Ctrl-P`/`N`/`D`/`U` in the picker, nothing in search or the confirmation cards, and no `Alt` chord anywhere. Anything else cancels armed chords and shows a sticky `Ctrl-S is not bound (? lists every key)` error, so `Ctrl-S` can't mark a task started, `Ctrl-Q` can't quit and `Ctrl-Y` can't confirm a reset. `Shift` passes through because capitals may arrive as `Char('L')` with `SHIFT` set. `handle_key_with_mods` is itself just an orchestrator over one small handler per concern — `handle_pending_open_link_key`, `handle_confirm_key`, `handle_help_key`, `handle_search_key`, `handle_picker_key`, `handle_checklist_scroll_key`, `handle_global_key`, and one per screen's own bindings (`handle_checklist_key`/`handle_list_complete_key`/`handle_all_complete_key`) — called in the exact front-to-back order described throughout this section; the split is structural only; no dispatch order or behavior changed. `gg`/`G` are `Checklist`-only motions — `gg` via a pending-`g` flag on `AppState` that any other key resets; while it is set the status bar shows `g… press g for the first task · any other key cancels` in the armed-prompt slot (below a status message, above the legend), so a lone `g` is never a silent no-op. `}`/`{` are likewise `Checklist`-only: they jump to the first item of the next/previous `### H3`+ sub-section **within the current list** (`List::sub_section_starts` gives the divider positions), reporting the landed-on sub-section, or an "already at the first/last" / "no sub-sections in this list" notice rather than wrapping or moving silently. They stay off the always-on legend (a navigation nicety, not an essential) and live only in the `?` overlay. The always-on status-bar legend is trimmed to the essentials (`hjkl:nav · space:toggle · /:search · y:copy · ?:help · q:quit`) with `?` as the full reference. `?` opens the `Help` overlay from any non-modal screen, scrolled to the top. Its rows come from `HELP_SECTIONS` (`ui/cards.rs`), one titled group per mode — the checklist/global keys, the `o`/`y` digit prompt, the list-complete screens, search, the picker, the help itself and the reset dialogs — and `app_tests.rs` guards it behaviorally: for each mode it presses every named key, printable character and bound `Ctrl` chord on a fresh state, and any key whose outcome differs from an unbound key's (for the digit prompt, from the same key with no prompt pending) must appear in that mode's key column, so a new binding without a help row fails the suite (#74); when it overflows a short terminal the card scroll keys plus `j`/`k` and the arrows scroll it (`help.scroll`, clamped by `help.max_scroll`/`help.viewport_height` written back by `render_help`), and **any other key** closes it, returning to the view it was opened from (`overlay = None`). **Navigation vs. scrolling:** since the layout stayed **horizontal**, all four home-row/arrow motions navigate between tasks — `h`/`l`/`←`/`→` read as the carousel sliding left/right, `j`/`k`/`↑`/`↓` as walking the list-shaped overview (`j`/`k` are plain aliases of `h`/`l`). Card-body scrolling moved off the plain home row onto vim's viewport keys: `Ctrl-E`/`Ctrl-Y` (line), `Ctrl-D`/`Ctrl-U` (half page), and `PageDown`/`PageUp` (page). Seeing the `Ctrl` modifier requires the real `KeyModifiers`, so `main.rs` calls `handle_key_with_mods(code, modifiers)`; the plain `handle_key(code)` wrapper (unmodified) is kept for headless tests. Half-page/page distances come from `card_viewport_height`, which the cards renderer writes back each frame alongside `card_max_scroll`. The mouse wheel gives an overflowing card body absolute priority; on a card that fits, the wheel navigates like `k`/`j`, crossing into the adjacent list at a list edge. In the `?` overlay the wheel scrolls the help, and in the `T` picker it moves the highlight. Card scroll state (`card_scroll`) resets to 0 on any navigation, list jump, or reload remap.

**Mouse input cancels armed key chords:** `handle_left_click`/`handle_scroll_up`/`handle_scroll_down` call `clear_pending_chords()` (not just `clear_status()`) as their first action, resetting `pending_g` (the `gg` chord), `pending_open_link` (the `o` number prompt), `pending_copy_code` (the `y` number prompt) and `pending_number` (a partly typed number) alongside the status message. Mouse events don't go through `handle_key_with_mods` — the only other place that consumes these flags — so without this, e.g. clicking an overview row to jump to a different card while `o`'s prompt was armed would leave it armed against the *new* card, and a later digit press would be misread as a link-open selection instead of ordinary input.

**Click-to-copy & click-to-navigate:** a left-click is dispatched to `AppState::handle_left_click(col, row)` (`main.rs`). It first hit-tests `overview_rows`: on the content screens (`Checklist`, `ListComplete`, `AllComplete` — *not* the modal overlays, whose overview is still drawn beside them) a click on an overview row acts on its target — `Item` calls `focus_item` with `CursorMove::Navigate`, honouring `--auto-copy` (mirroring the `T` go-to-task picker), `List` calls `jump_to_list` (landing on the list's first not-done item, like the number keys), and `Toggle` (a checkbox row's marker prefix) calls `toggle_item` to flip that task done↔not-done **in place**. `focus_item`/`jump_to_list` drop back to the `Checklist` screen; `toggle_item` leaves the cursor and card view untouched, writes back, reports a `Marked done`/`Marked not done` status, and only *demotes* a now-stale completion screen back to `Checklist` (it never *promotes*, which would steal focus). If no overview row is hit, it hit-tests two things the cards renderer writes back each frame (on the `Checklist` screen only):

- **`code_regions`** — **per-command** hit-testing. `render_current_card` records each copy target as a single-row `Rect` + the *clean, full* copyable text. `body_layout` produces the targets in lockstep with the body lines (`CopyTarget` = column range from the body's left edge + text): a fenced-block row and a trailing-command row are whole-row targets mapping to the block text / the command; on a flowed prose row, each inline-code chip is its own target covering only the chip's columns (`chip_targets`, offset by the same `(width / 2) − (line_width / 2)` ratatui uses to center a line). `wrap_tokens` reports, per span, the code token it came from, so every fragment of a chip hard-split across rows maps to the token's full text rather than the fragment — a click never copies a truncated command, and two chips on one row each copy their own. Row indices are mapped to on-screen rows through the same `top_pad` (centered) / `card_scroll` (overflow) offset used to draw the body, and clipped to the visible area. A click on a target copies *that exact command* (`AppState::copy_specific`, queuing a `CopyKind::Command` copy) — **overriding** the fenced-over-inline priority of `y`, so a multi-command card that `y` refuses as ambiguous is copyable per command.
- **`card_rect`** — the whole-card fallback. A click inside the card but *not* on a copy target (including prose beside an inline chip) calls `copy_current_code()` (the MVP behavior): a one-command card copies, a no-command card shows the same hint as `y`, and a multi-command card arms `y`'s digit prompt. Clicks elsewhere / off the checklist are ignored.

**Advancing:** `Tab` is global and jumps to the next unfinished *task* anywhere in the document (`jump_to_next_incomplete_task`) — after the cursor, wrapping around, `NotStarted`/`Started` both count — announcing a wrap with an ephemeral `Wrapped to the first unfinished task (<list>)` (a wrap jumps backwards across the document, which in a long runbook could pass for "the next step", #87) and reporting a sticky `No unfinished tasks` rather than moving silently when none exist. `Shift-L` is the coarser move: the next *list* with remaining work (`next_incomplete_list_after`), landing on its first not-done item; `Shift-H` mirrors it to the *previous* incomplete list (`prev_incomplete_list_before`). Neither wraps or moves silently when nothing qualifies (matching `jump_sub_section`'s convention): `no_further_incomplete_list_message` distinguishes no list in the document having unfinished work at all (`No lists have unfinished tasks`) from simply being at the last/first incomplete list already (`Already at the last/first incomplete list`). (`n` was dropped in an earlier vim-consistency pass.) `l`/→ (`navigate_forward`) steps within the list and, at the **last** item, crosses into the *immediately-next* list (adjacent, not skipping complete ones); `h`/← (`navigate_backward`) mirrors it — at the **first** item it crosses into the *immediately-previous* list. Both cross-boundary moves go through `jump_to_list`, so they land on the target list's **first not-done item, or its first item if all are done** (they may skip already-done items at the top of the adjacent list). `navigate_next`/`navigate_prev` themselves still clamp, so the toggle-driven advance in `maybe_transition_screen` never crosses a boundary; the mouse wheel goes through `navigate_forward`/`navigate_backward` and does. From `ListComplete`, `l`/`Enter` skip fully-complete lists to the next list with remaining work.

On the `ConfirmReset` screen, only `y` confirms and **any other key (including `Enter`) cancels** (closing the overlay, which returns to the view underneath); `Enter` was dropped because it's too easy to hit by reflex for a whole-file rewrite. This screen is checked before the global `q`/`Esc` handler so `Esc` cancels rather than quits.

On the `ConfirmQuitReset` screen (offered when pressing `q`/`Esc` with every task already done): `y` resets all tasks then quits, `n` quits without resetting, and `Esc`/any other key cancels back to the view underneath. `reset_all` returns whether the reset reached disk, and `y` quits only on success: a refused or failed write keeps markcheck running with the sticky error shown (still on the modal, so `y` retries and `n` quits as-is — or on the checklist, when a file changed on disk forced a reload), so the reason is never lost to an exit. Like `ConfirmReset`, it's handled before the global quit check.

## Incremental search (`/`)

`/` on the `Checklist` view opens `Overlay::Search`, remembering the cursor in `search.origin`. The `Search` branch sits at the very top of `handle_key_with_mods` (right after the other modal checks) so every typed key edits `search.query` instead of firing a command — `q`, `?`, `j`, … are literal text. On each edit (`Char`/`Backspace`), `update_search` re-runs `find_matches` and moves the cursor to `search_target`'s pick — the first match **at or after `search.origin`**, wrapping to the first match overall (vim's forward `/`; it used to jump to the first match in the document, throwing a user at step 40 back to step 3, #61) — **keeping** `Overlay::Search` open so the query keeps showing in the status bar (rendered vim-style as `/query`; the checklist cards stay visible because `cards::render` draws the view under the `Search` overlay). The status bar always gives feedback: it appends the match count (`/query  (N matches)`) or, when a non-empty query hits nothing, a distinct error-colored `/query  (no matches)`. When the query matches nothing (or is backspaced to empty), `update_search` returns the cursor to `search.origin` with a `Quiet` `focus_item`, like vim's incremental search, rather than leaving it on whichever card an earlier prefix matched (#117). `Enter` (`commit_search`) reports that match's real position (`Match 7/12 · n/N to cycle`), stores the query in `search.last`, returns to `Checklist`, and only then fires `maybe_auto_copy` — auto-copy is suppressed during incremental jumping so `--auto-copy` users don't copy on every keystroke. A committed query that matched nothing, or an empty one, skips `maybe_auto_copy` entirely, so the sticky `No matches` error is never replaced by a copy confirmation for a card the user never navigated to (#117). `Esc` (`cancel_search`) restores `search.origin` with a `Quiet` `focus_item`, so cancelling never copies.

After committing, `n` / `N` (`search_cycle`) step forward / backward through `find_matches(search.last)` relative to the cursor, wrapping around, and set an ephemeral `Match i/N` status — with `· wrapped to top` / `· wrapped to bottom` appended when the step wrapped, like vim's `search hit BOTTOM` (#87); `commit_search` reports `Match 1/N` too — with a nudge — a leading space then `· n/N to cycle` — appended when there's more than one match, so the cycling keys are discoverable without opening `?` (they're not on the always-on legend) — and a committed query that matches nothing sets a sticky "No matches". With no previous search, `n`/`N` stay put and show a sticky `No previous search — press / to search` (vim's `E35` equivalent), and they report the sticky "No matches" if the stored query no longer matches anything. Matching (`find_matches` + `smart_case_contains`) is **smart-case** substring containment (case-insensitive unless the query has an uppercase letter) over each item's `Item::search_text` — the card title, body prose/inline code (folded into `display_text`), and any fenced command blocks — so a task is findable by its command, not just its prose. `focus_item(list, item)` is the shared exact-cursor primitive (unlike `jump_to_list`, which lands on the first not-done item); it's reused by the TOC overlay.

## Go-to-task overlay (`T`)

`T` opens `Overlay::ListPicker`, a full-screen overlay (rendered by `render_list_picker` in the cards area, like `Help`, with the overview still beside it) that lists **every** navigable card — checkbox tasks and display-only note cards alike — with its state marker and a dim `— {list} › {sub-section}` context suffix — the list name (only when there are several lists) followed by the item's `### H3`+ sub-section path. When label and suffix don't both fit the row, `ui::split_width` keeps the suffix at least half the row (or its full length, if shorter) and the label takes the rest, each cut with `…`, so a long label can't push off the context that tells same-named tasks apart. Like `Search`, its key branch is at the top of `handle_key_with_mods` so typed keys are filter input. `AppState::picker_matches` returns every item when `picker.query` is empty, otherwise smart-case-matches each item's `picker_match_text` (its `search_text` plus its ordered-list step number and its sub-section path, so "the task under Pre-flight checks" is findable) — the same smart-case predicate shared with search, but over a picker-only source so the section text never leaks into the main `/` search. Because letters are filter input, the selection moves on **arrows and `Ctrl-N`/`Ctrl-P`**, with **`Ctrl-D`/`Ctrl-U`** half-page jumps (matching the card-body scroll keys; the list viewport height is written back by the renderer into `picker.viewport_height`) — not `j`/`k`, which must stay typeable; `picker_move` clamps without wrapping and `picker.selection` resets to 0 on any filter edit. `Enter` (`picker_commit`) calls `focus_item` on the highlighted entry (as a `Navigate` move, so `--auto-copy` applies), or just closes when nothing matched; `Esc` closes it, back to the view underneath. The mouse wheel moves the highlight like the arrows. A left-click on the picker (`picker_click`, dispatched first in `handle_left_click`) hit-tests `picker.rows_area`, which `render_list_picker` writes back each frame along with the `ListState` offset (`picker.scroll_offset`): the clicked row's entry is `scroll_offset + (row − rows_area.y)`; a click on a row other than the highlighted one highlights it, a click on the highlighted row commits it like `Enter`, and clicks off the entry rows are ignored. The overlay always gives feedback (per the UI Feedback rule): the filter text, and a title count that reads ` N items ` unfiltered ("items" rather than "tasks" since the count includes notes), ` N match(es) `, or ` no matches ` (with a centered "No matching items" body). Selection highlight and scrolling come from ratatui's `List`/`ListState`.

## Editor integration (`e`)

`handle_key` queues `Effect::OpenEditor { line }` with the current task's line; the main loop's drain calls `open_in_editor`, which suspends the TUI (disable raw mode + mouse capture, leave the alternate screen), spawns the editor resolved from `$VISUAL` → `$EDITOR` → `vi` (shell-word-split via the `shell-words` crate, so `EDITOR="code --wait"` works and a quoted argument containing spaces — `EDITOR="my-wrapper --arg='value with spaces'"` — stays one token instead of splitting apart) on the file, then always restores the terminal and hands the editor's exit status to `AppState::finish_editor`, which calls `reload_if_changed()` (queuing a git-sync request when it reports a real reload happened and the editor succeeded — see Git Sync, above) and only *then* reports a launch failure or non-zero exit with `set_error`, joined to the reload's own message by a semicolon. Reporting first let the reload's ephemeral `Reloaded: file changed on disk` replace the sticky failure. Unbalanced quotes fail to parse; `resolve_editor` falls back to `vi` and returns a warning (its third tuple element) that `open_in_editor` passes to `finish_editor`, which reports it the same way, after the reload, rather than misparsing silently. **Non-blocking editors:** `open_in_editor` times the editor and passes the elapsed time to `finish_editor`. A successful exit within `EDITOR_RETURNED_AT_ONCE` (1 s) that left the file unchanged is almost always a GUI editor (`code`, `subl`, `gedit` with an instance running, `emacsclient -n`) handing the file to a window and returning; its later save would arrive through the watcher as an external edit, which never queues a sync. So that case adds a sticky `<editor> returned immediately — if it opened a window, make it wait: EDITOR="code --wait" (subl -w, gedit --wait)` to the reported problems instead of staying silent. No wait flag is added automatically. The reload's mtime guard makes the watcher's later events a no-op, so the file is reloaded exactly once and the cursor is remapped to the previously selected item. **Cursor line:** `editor_file_args` builds the editor's file arguments from the program's basename and the selected task's 1-based `line_number`, in the form that editor takes: `+N path` (`vi`/`vim`/`nvim`/`view`/`nano`/`pico`/`emacs`/`emacsclient`/`joe`/`gedit`/`kak`/`micro`), `path:N` (`hx`/`helix`/`subl`) or `--goto path:N` (`code`/`codium`), appended after any arguments from `$VISUAL`/`$EDITOR` so `EDITOR="code --wait"` becomes `code --wait --goto path:N`. Anything unrecognised, or no selected task, gets the bare path and opens at the top of the file.

The full repaint on restore is done with `terminal.resize(current_size)`, **not** `Terminal::clear()`: ratatui's `clear()` issues a DSR cursor-position query (`ESC[6n`) and waits for the terminal to answer, which hangs/errors on terminals that don't reply (bare PTYs, some multiplexers) — surfacing as "The cursor position could not be read within a normal duration". `resize` to the same size clears the screen and resets the back buffer to force a redraw without any query.

## Suspend (`Ctrl-Z`)

Raw mode turns off the terminal's `ISIG`, so Ctrl-Z reaches markcheck as a key rather than as `SIGTSTP`. `handle_key_with_mods` checks for it before anything else (any screen, overlays and search input included), cancels armed chords and queues `Effect::Suspend`; the main loop's drain calls `suspend_to_shell` (`main.rs`). That tears the terminal down exactly as `open_in_editor` does, then `stop_self` runs `kill -TSTP -- <own pid>` — `kill(1)` rather than a libc dependency, as `git_sync`'s timeout already does. The process stops while waiting for `kill`, so the call returns only after the shell's `fg` sends `SIGCONT`. The terminal is then restored with the same resize-based full repaint, and `AppState::finish_suspend` reports the outcome: a failure to run `kill` is a sticky `Couldn't suspend: …` error; otherwise `reload_if_changed()` picks up any edit made from the shell (its own `Reloaded` status), falling back to an ephemeral `Resumed`. No git-sync request is queued for such an edit: like any other external change, it isn't markcheck's to commit. Every thread stops with the process, but a git subprocess already running in its own process group carries on. Under a shell without job control the process group is orphaned, the kernel discards `SIGTSTP`, and markcheck simply repaints with `Resumed`.

## Reset (`R`; quit-reset)

`request_reset` opens the `ConfirmReset` modal, or shows "Nothing to reset" when no task is done or started. The modal states what will change, counting done and started tasks separately (e.g. `This marks 1 done and 2 started tasks (of 5) as not started`), since a reset clears both. `reset_all` flips every checkbox to not-done, writes back once (updating `file_mtime` to suppress a self-reload), and returns to `Checklist`. The cursor is kept. A write failure sets a sticky error (`Write failed — reset not saved to disk`) instead — the screen stays on `ConfirmReset` and the reset status is never shown, since it wasn't actually saved (the checkboxes are rolled back to their pre-reset state via `commit_write`'s failure path, matching `set_current_state`'s behavior — memory never diverges from what's actually on disk).

Quitting with everything already done (`q`/`Esc` when `document.checkbox_stats()` is all-done) opens the `ConfirmQuitReset` modal instead of quitting outright, so a finished checklist can be handed back ready to run again: `y` calls `reset_all` and quits only if the reset was saved, `n` quits without resetting, `Esc`/other cancels. This keeps the "leave it clean for the next run" workflow one keystroke away without ever resetting silently.

## Undo / redo (`u` / `Ctrl-R`)

Every state-changing action — `toggle_current`/`start_current` (via `set_current_state`), the overview-click `toggle_item`, and `reset_all` — is undoable. Each captures a full `StateSnapshot` (`Vec<(line_number, TaskState)>` of every checkbox's *current* state, from `state_snapshot()`) immediately before it mutates and writes. A full snapshot — rather than a per-item delta — makes all four actions uniform and captures `reset_all`'s whole-document change for free; snapshots are a few bytes per task, and `undo_stack` is capped at `UNDO_HISTORY_CAP` (100, oldest dropped). The snapshot is taken only *after* each action's `file_deleted` guard and item validation, so a blocked or no-op action captures nothing (`toggle_item` validates with an immutable borrow, then re-fetches mutably after the snapshot is taken). That pre-mutation snapshot serves double duty: it's what `commit_write` (see above) rolls the document back to if the write fails, and — only once the write has actually succeeded — it's what `push_undo_point` commits onto `undo_stack` (capping it and clearing `redo_stack`, since a fresh change invalidates redo). A failed action therefore never reaches the undo/redo stacks at all: pushing a snapshot for a mutation that was just rolled back would leave a no-op undo entry and wipe out a valid redo stack for nothing.

`u` (`undo`) pops `undo_stack`, snapshots the current state (the redo point), and applies the popped snapshot via `apply_snapshot` — which matches items by `line_number` (a line no longer present is skipped) via a line-number → state map built once up front, not a linear scan per item, and returns the lines that actually changed. `Ctrl-R` (`redo`) is the exact mirror, moving a snapshot back the other way. Both refuse when `file_deleted`, and report a sticky error (`Nothing to undo` / `Nothing to redo`) when their stack is empty. The shared tail `finish_history_apply` writes the restored document back (refreshing the `file_mtime` self-write guard and the `Updated` tag), drops any completion screen to `Checklist`, and gives **change-aware feedback** (per the UI Feedback rule): exactly one item changed → the cursor focuses it (`focus_item` via `locate_line`) and the status reads `Undo: marked done`/`marked started`/`marked not done` from the item's new state; several changed (a reset undo) → `Undo: restored N tasks`. A write failure sets a sticky error (`Undo failed`/`Redo failed — write error, change not saved`) instead: `commit_write` rolls the document back to the pre-undo/redo state, and `undo`/`redo` put the popped snapshot back onto the stack it came from (rather than committing the swap) — so the document, `undo_stack`, and `redo_stack` all end up exactly as if the undo/redo had never been attempted, ready to retry once the file is writable again. The one exception is a write refused because the file changed on disk: that path reloads the file, and the reload clears both stacks (an external edit is a hard boundary), so the popped snapshot — keyed on the old file's line numbers — must not be pushed back onto the fresh history. `reload_from_disk` bumps `history_epoch` whenever it clears the stacks, and `undo`/`redo` re-push only when the epoch is unchanged; after such a refusal the next `u`/`Ctrl-R` reports `Nothing to undo`/`Nothing to redo` instead of replaying a pre-reload snapshot onto the new file. `u`/`Ctrl-R` are global (like `R`/`e`), so they work from the completion screens too; the `u` handler is guarded on `!CONTROL` so it never fires on `Ctrl-U` (card scroll), and redo is `Ctrl-R` so it stays distinct from `R` (reset).

**External reloads are a hard boundary.** A successful `reload_if_changed` (an external edit) clears **both** stacks — the new document can change task state and line numbers underneath the snapshots, so they no longer apply cleanly. Our own writes update `file_mtime` and so never trigger a reload, meaning history survives toggles/resets we make ourselves. (Scope is task state only; in-app editing, if built, would need its own history integration.)

## Clipboard (`src/clipboard.rs`)

`y` copies code content only. Candidates (`clipboard::candidates`) are the item's fenced `code_blocks` if any exist, otherwise its inline `code_spans`. Exactly one candidate → copy it; zero → nothing is copied and the status bar says `Nothing to copy: item has no code`. One candidate is queued as a `CopyKind::Command` copy (see Effects). **Several** → `copy_current_code` arms `pending_copy_code` with no status message, so the status bar shows `press 1–N to copy · esc cancels` (same slot and priority as `o`'s prompt). It mirrors `o`'s link prompt exactly: `handle_pending_copy_code_key` runs at the top of `handle_key_with_mods` next to `handle_pending_open_link_key`, a number (see Open link for how digits are collected) calls `copy_code_number(n)` — which copies candidate `[n]` through `copy_specific` (same outcomes and messages as a click), or reports a sticky `No command [n] on this card` — `Esc` cancels, and any other key soft-cancels and takes its normal action. The card's `[N]` markers (see Card anatomy) are the key for these numbers, and `[10]` and up are reached the same way as links. Without this, a multi-command card could only be copied by mouse, which `--no-mouse` and many multiplexer setups rule out.

Backend order: `arboard` first — verifiable and correct on a local X11/Wayland session — then an OSC 52 escape (`ESC ] 52 ; c ; <base64> BEL`) written to stdout when arboard fails. OSC 52 travels through SSH to the local terminal emulator, which makes copy work on headless servers (markcheck's core use case); it is fire-and-forget — writing the escape to stdout succeeding says nothing about whether the terminal/multiplexer actually accepted or applied it — so the status message says `Sent to clipboard (OSC 52)` rather than `Copied`, distinct from the verifiable `Copied to clipboard` arboard gets. Payloads are capped at 70 KB, comfortably under the ~74 KB tmux is known to truncate at, so a payload this cap rejects is never one tmux would otherwise have silently truncated instead. Bare OSC 52 is emitted — tmux users need `set-clipboard on`; VTE-based terminals (e.g. GNOME Terminal) don't support OSC 52 at all. If both backends fail outright, the status bar says so — copy failures are never silent.

**One arboard instance per session:** `set_via_arboard` lazily creates a single `arboard::Clipboard` in a `static Mutex<Option<Clipboard>>` and reuses it for every copy, rather than creating one per copy. On X11 the owning instance serves the selection to whoever pastes, and arboard's `Drop` for the last instance tries a 100 ms handover to a clipboard manager and then destroys its selection window — so a per-copy instance made `Copied to clipboard` a lie on any X11 session without a clipboard manager. A failed write discards the cached instance so the next copy reconnects. `main` calls `clipboard::release_system_clipboard()` once after the event loop returns, which drops the instance and lets arboard do that handover once, on quit.

**Hidden characters:** `copy_text` — the common path under `clipboard::copy`, so `y`, click-to-copy, auto-copy and the link fallback alike — first refuses any text containing a control character other than `\n`/`\t` (ratatui drops those when drawing, so the card can't show them) or a bidi control (U+061C, U+200E/F, U+202A–U+202E, U+2066–U+2069), returning `CopyOutcome::HiddenCharacters` without touching either backend. Otherwise a checklist could display one command while the clipboard got another — an embedded `ESC [201~` ends a bracketed paste early. The app reports it with the sticky `Not copied: command contains hidden control characters`. pulldown-cmark normalizes CRLF line endings inside code, so CRLF checklists are unaffected.

Outcomes are modeled as a `CopyOutcome` enum; the candidate selection and the OSC 52 sequence builder are pure functions with unit tests. `copy_text_with` takes the system-clipboard write and the OSC 52 output stream as parameters; in test builds `copy_text` routes them to `clipboard::fake`, a per-thread stand-in that records every attempted clipboard write (with its `primary` flag) and every OSC 52 byte, and whose system clipboard is unavailable unless a test turns it on. So no test can overwrite the developer's clipboard or write escapes to the harness's stdout, and tests assert on what was sent where. `set_via_arboard` is not compiled into tests at all; the real arboard path is verified manually. `tests/pty.rs` launches the binary with `DISPLAY`/`WAYLAND_DISPLAY` removed, so its copies fall back to OSC 52 inside the pseudo-terminal.

**PRIMARY selection (`--primary`):** by default only the CLIPBOARD selection is set. With `--primary`, arboard *also* writes the X11 PRIMARY selection (`SetExtLinux::clipboard(LinuxClipboardKind::Primary)`, Linux-only; best-effort — a PRIMARY failure doesn't fail the copy), and the OSC 52 fallback emits a second sequence with selection `p` in addition to `c`. This makes middle-click paste work alongside Ctrl-V. `clipboard::copy`/`copy_text` take a `primary: bool`, carried on each `Effect::Copy` from `AppState.clipboard_primary`.

**Auto-copy (`--auto-copy`):** when set, `AppState.maybe_auto_copy()` runs after every navigation and copies the current item's code if it has exactly one candidate. It shows the same status message as manual `y` on a **successful** copy, but stays silent when the card has no code or an ambiguous set, so passive navigation isn't spammed. The one exception is a hidden-characters refusal, which is always reported (sticky), since it warns about the checklist itself. Reuses the same candidate logic and honors `--primary`.

## Open link (`o`)

`o` opens the current card's link: `AppState::open_current_link` reads `Item::link_urls()` — exactly one **with a safe scheme** → queue `Effect::OpenLink` with that URL (the status is set by the main loop once it knows what happened — see below); exactly one with any other scheme → sticky `Not opened: unsupported link type (<url>)`; zero → sticky `Nothing to open: card has no link`; **several** → arm `pending_open_link` and set **no** status message, so the panel below the card keeps showing the numbered URL list (the user needs it to choose) while the status bar shows a short `press 1–N to open · esc cancels` prompt. The armed key is consumed at the top of `handle_key_with_mods`, before both the global digit→list jump (so a digit selects a link, not a list) and the global q/Esc quit (so Esc cancels rather than quitting): digits are collected by `pick_number_key` into `AppState.pending_number` (shared with `y`'s prompt): a digit (`0` only after another digit) acts at once unless a longer valid number could still follow — i.e. while `n * 10 <= count` it waits, so on a card with nine or fewer links every digit acts immediately, and with twelve `1` waits for `0`–`2` or `Enter` — `Enter` takes the number typed so far, `Backspace` deletes the last digit, and a number past the last link still reaches `open_link_number(n)`, which opens link `[n]` with the same safe-scheme/unsupported/out-of-range (`No link [n] on this card`) outcomes. `Esc` cancels, and any other key is a soft cancel that also takes its normal action (like the `gg` chord), discarding a partial number. While a partial number is pending the status bar shows it: `open [1…] of 1–12 · next digit, or enter for [1] · esc cancels`. The card's dim `[N]` markers (see Card anatomy) are the on-screen key for these numbers. The global `1`–`9` list-jump (`handle_global_key`) keeps a nine-item ceiling.

The safe schemes are `http://`, `https://` and `mailto:` (`SAFE_LINK_SCHEMES`/`is_safe_link` in `app.rs`, matched case-insensitively per RFC 3986) — everything else is refused, including `javascript:`, `data:`, schemeless URLs like `example.com`, and `file://`. `file://` is excluded deliberately: an opener handed a `file://` URL pointing at a `.desktop` file or an executable can *run* it rather than merely display it. The allowlist also closes the **argument-injection** hole: a link like `[x](--some-flag)` would otherwise reach the opener's argv as an option, and a URL constrained to start with an allowed scheme can never start with `-`. This makes an explicit `--` end-of-options separator unnecessary — which matters, because `xdg-open` is a shell script with no standard `--` convention. Validation lives in `app.rs` (pure and unit-tested) rather than `main.rs`, which stays a dumb spawner. A refused link renders no differently from any other — the URL isn't drawn on the card at all, only its underlined text.

**Link panel below the card:** since the URL no longer appears on the card, `cards::render_link_panel_below` draws the current card's link URLs in the empty space **below the card**, one per line and horizontally centered, under a one-row blank spacer. Single link → `→ <url>`; several → a numbered `[1] <url>` / `[2] <url>` … list matching the card's dim `[N]` markers. Crucially the card is positioned by `card_row` against the **full** main area — the panel is painted into the leftover space afterward, never subtracted from the layout — so the card stays put whether or not it has links (no jitter as you navigate). The full URL always lives in `Item.body`, so `link_urls()` and `o` are independent of how (or whether) it is displayed. Known limitation: a URL wider than the content area is clipped rather than wrapped (rare). While a multi-link `o` is armed (`pending_open_link`), the panel keeps listing the URLs and the **status bar** shows `press 1–N to open · esc cancels` (`statusbar.rs`, on the `Checklist` screen when no transient message is active; priority search overlay > status message > armed prompt > legend). On a short terminal with no room below the centered card for the panel itself (`link_panel_fits`), the card falls back to a compact ` → link ` hint in its bottom-right border title (same slot as the scroll indicator, which wins if both apply — see Card anatomy) so `o` is never a blind guess even when the full URL can't be shown.

Like the editor, `app.rs` only queues the effect — the main loop's drain calls `open_link`, which resolves the openers (`launch::resolve_opener`) and spawns them in turn until one starts, with the URL as a **plain argument** (no shell, so a crafted URL can't inject a command). `$BROWSER` follows the convention `xdg-open` and Python's `webbrowser` use: a colon-separated list of commands, each shell-word-split the same way as the editor, with `%s` in an argument replaced by the URL (`%%` is a literal `%`) and the URL appended as the last argument only when no `%s` is present. Empty entries are skipped; an entry with unbalanced quotes is skipped with a warning surfaced via `set_error`, and when no usable entry is left the platform default (`xdg-open`/`open`) is used, the same graceful-degradation contract as the editor. When every candidate fails to spawn, the last failure is surfaced. The TUI is **not** suspended (unlike the editor) — the browser is a separate GUI process; its stdio is sent to `/dev/null` so it can't corrupt the screen, and the child is reaped in a detached thread so we neither block on the browser nor leak a zombie. A spawn failure is surfaced in the status bar.

**Feedback reports what actually happened, not that something started.** A successful spawn sets the ephemeral `Sent to <program>: <url>` (`AppState::report_link_sent`) — worded as an attempt, because a spawn only proves the opener started. The reaper thread times the child and, when `launch::opener_failure_message` says it exited non-zero (or was killed) within `OPENER_FAILURE_WINDOW` (10 s), sends a `Couldn't open link (<program> exited with code N)` message over an `mpsc` channel that the main loop drains each tick into `set_error`, the same pattern as git-sync's outcomes. The window exists because an opener that *is* the browser can run for hours, and its eventual exit status says nothing about the link. **Headless sessions copy instead of opening:** before resolving openers, `launch::no_browser_available` checks for no usable `$BROWSER` entry and, outside macOS, neither `$DISPLAY` nor `$WAYLAND_DISPLAY` set (empty counts as unset). That's the SSH-to-a-server case, where `xdg-open` either fails or picks a terminal browser that can't draw on a raw-mode terminal it doesn't own; `AppState::copy_link_instead` queues a `CopyKind::LinkFallback` copy of the URL, which the same drain runs through the same clipboard path as `y` (OSC 52 reaches the user's local terminal) and says `No browser here — link copied to clipboard`. A user who really wants an opener there sets `$BROWSER`, which bypasses the check. Terminal browsers in `$BROWSER` still aren't given the terminal (no suspend, as `e` does); one that exits at once with an error is now at least reported.

## Terminal Setup (`src/main.rs`)

**Startup errors name the file and the cause.** Before any terminal setup, `main.rs` wraps every way of failing to open the checklist in context that names the path: `cannot resolve path: <file>` (canonicalize), `cannot read <file>` (`parser::parse_document`, which adds a "not valid UTF-8 … convert it with e.g. iconv" layer for `InvalidData`, so a UTF-16 file says what to do), and a zero-task file prints `No checklist items found in <file>.` plus a one-line hint about `- [ ] step` syntax (exit status 0, unchanged). Then, before anything with side effects (git-sync's catch-up push), it refuses to start when stdout is not a terminal (`cannot open <file>: markcheck is interactive and needs a terminal`), instead of letting raw mode fail with a bare `No such device or address`; `enable_raw_mode`/`EnterAlternateScreen` carry context too, for a terminal that fails anyway. clap's `after_help` names the config file path, so `--help` points at it.

`TerminalGuard` with `Drop` ensures the terminal is always restored even on panic — disabling raw mode, releasing mouse capture (when it was enabled), and turning bracketed paste off while leaving the alternate screen:

```rust
struct TerminalGuard { mouse: bool }
impl Drop for TerminalGuard {
    fn drop(&mut self) {
        restore_terminal(self.mouse); // raw mode off, mouse released, paste off, alt screen left
    }
}
```

The guard alone is too late for a panic's *message*, though: the default panic hook prints before unwinding reaches the guard, so the text would land in raw mode on the alternate screen and vanish with it. `install_panic_hook`, called just before `enable_raw_mode`, wraps the previous hook: on the main thread it runs `restore_terminal` first (mouse release unconditionally, since a redundant disable is harmless), then the previous hook, then a one-line "please report this at" pointer to the issue tracker, so the message and location appear on the normal screen with the terminal usable. The guard's later drop repeats the restore harmlessly. Panics on other threads only run the previous hook: git-sync's workers convert theirs into a `Failed` outcome (`run_reporting_panics`) while the TUI keeps running, so restoring the terminal there would wreck a live session. Debug builds read `MARKCHECK_TEST_PANIC` to force a panic right after a frame is drawn; `a_main_thread_panic_prints_its_message_on_the_restored_screen` in `tests/pty.rs` uses it, and release builds compile the trigger out.

CLI via `clap` derive (`Cli` in `cli.rs`): positional `file: Option<PathBuf>` (`required_unless_present = "new"`), plus `--new PATH` (`conflicts_with = "file"`), `--no-nerd-font`/`--nerd-font` (plain-Unicode vs Nerd Font icons), `--no-mouse`/`--mouse` (skip mouse capture, so terminal text selection works without Shift), `--primary`/`--no-primary` (also copy to the X11 PRIMARY selection), `--auto-copy`/`--no-auto-copy` (silently copy an item's code when navigating to it) — each pair `conflicts_with` the other —, `--color auto|truecolor|256|16` (a clap `ValueEnum` on `model::ColorChoice`; see Color palette), and `--git-sync`/`--no-git-sync` (commit+push this file's changes after every write, when it's in a git repo / never, even under a matching `git_sync_paths` entry; also `conflicts_with` each other). `--config PATH`/`--no-config` choose the config file for the run (see Config File, below; they `conflicts_with` each other too). The four boolean flags each have a config-file default (below); a passed flag always wins. The `--primary`/`--auto-copy` flags set the matching `AppState` fields after construction; `--git-sync` instead feeds `GitSync::detect` (see Git Sync, above) since it isn't an `AppState` field at all.

`--new PATH` (`scaffold.rs`) creates a starter checklist and opens it instead of an existing file. `scaffold::create_new_checklist` validates the extension (`.md`, case-insensitive) and a non-empty file stem before touching the filesystem, and resolves `PATH`'s parent directory with `fs::canonicalize` (the file itself can't be canonicalized — it doesn't exist yet). The write itself is atomic in two senses at once: the template is written to a temp file in the same directory first (fsynced, so a write failure never leaves the *final* path holding a truncated template), then `fs::hard_link`ed into place rather than renamed — unlike `rename`, `hard_link` fails with `AlreadyExists` instead of silently replacing an existing target, so the existence check and the placement stay one atomic operation with no separate exists-then-write race, the same guarantee `OpenOptions::create_new(true)` gave directly before this. Some filesystems have no hard links at all (FAT32/exFAT, many SMB/CIFS mounts, some FUSE filesystems, Android shared storage), and they report it with a spread of error codes (`EPERM`, `EOPNOTSUPP`, `ENOSYS`, a Windows `ERROR_INVALID_FUNCTION`); so any link failure other than `AlreadyExists` falls back to writing the final path directly with `create_new(true)` (`write_new_file`, shared with `write_temp`), which keeps the never-overwrite guarantee and removes the file again if the write itself fails. Falling back on every such error rather than a list of codes is safe because `create_new` refuses an existing file on its own, and a genuine failure (a full disk, say) simply fails again in the fallback with its own error. The link step is injected (`create_new_checklist_with`) so tests can simulate a filesystem without hard links. The temp name is removed either way (on success it and the final path are the same inode, so nothing is lost by removing it), and its parent directory is fsynced on Unix afterward (`writer::sync_parent_dir`, made `pub(crate)` for this reuse) so the new directory entry itself survives a crash, mirroring `write_back`'s own durability guarantee. This still isn't `writer::write_back`'s temp-file-then-*rename* dance verbatim: that path also reads the *source* file's permissions first and errors on `NotFound` by design (a deleted file must never be silently recreated), which doesn't apply to creating a brand-new file — there's no source permissions to preserve, so the temp file gets ordinary default (umask-masked) permissions, not `write_back`'s deliberately-restrictive-then-restored 0600. The template title is derived from the filename (`derive_title`: split on `-`/`_`, title-case each word, e.g. `meeting-notes.md` → `# Meeting Notes`, falling back to `# Untitled` for a stem with no words), followed by two blank tasks — blank checkbox items are already a supported, tested parser case. `main.rs` then feeds the created path into the same `parser::parse_document`/`AppState::new` flow as a normal invocation, and shows `"Created new checklist"` via `AppState::set_status` (made `pub` for this cross-module call) as the first frame's confirmation. `launch::startup_message` combines it with any startup warning (hard links, foreign owner, git-sync off) into one message, which is then sticky and error-coloured via `set_error` rather than letting one message overwrite the other.

`--version`/`-V` (clap's built-in flag, wired via `#[command(version = VERSION)]`) prints `<CARGO_PKG_VERSION> (<git short sha>)`, e.g. `1.0.0 (da90ddd)`. `build.rs` shells out to `git rev-parse --short HEAD` at compile time and exports it as the `MARKCHECK_GIT_SHA` build-time env var (`cargo:rustc-env`), falling back to `unknown` when not in a git checkout (e.g. a source tarball); `cli.rs`'s `VERSION` const stitches it together with `env!("CARGO_PKG_VERSION")` via `concat!`. `cargo:rerun-if-changed` keeps the SHA current: `build.rs` watches `HEAD` (branch switches, detached checkouts), `packed-refs` (a tip that moves while staying packed), and the **directory** the current branch's loose ref lives in rather than the ref file itself — in a packed repository the loose file doesn't exist at build time, and the next commit *creates* it, which a watch on the file would miss. Only paths that exist are emitted, since a missing `rerun-if-changed` path makes cargo rebuild unconditionally; outside a git checkout nothing is emitted at all.

Mouse capture is enabled by default (`EnableMouseCapture` at startup); `TerminalGuard { mouse }` disables it again on drop, before leaving the alternate screen. The event loop polls at 100ms but **redraws only when something may have changed**: a dirty flag is set by any event `ui::event_needs_redraw` accepts (everything but key releases and `MouseEventKind::Moved` — crossterm's mouse capture reports every pointer motion), a reload check that changed something (`ReloadTrigger::check`), a finished git sync, an expired status message (`AppState::expire_status` returns whether it cleared one), the editor/suspend/link round trips, and the deadline `ui::next_label_change` computes for the title bar's relative "Updated/Synced … ago" labels; an idle session does no layout work between those. It dispatches `Event::Key` presses to `handle_key`, `Event::Mouse` wheel events to `handle_scroll_up/down`, and left-clicks (`MouseButton::Left` down) to `handle_left_click` for click-to-copy; `Event::Resize` is handled automatically by ratatui. Bracketed paste is always on (`EnableBracketedPaste` with the alternate screen, off again in `TerminalGuard::drop` and around `open_in_editor`), so a paste arrives as one `Event::Paste` instead of a keystroke per character — otherwise a command pasted into the wrong pane would run each letter as a binding (spaces toggle, `R`+`y` resets, `q` quits). `AppState::handle_paste` clears pending chords, then appends the text to the query on `Search`/`ListPicker` as one line (line breaks and tabs become spaces, trailing whitespace and other control characters are dropped) and on every other screen ignores it with a sticky `Paste ignored` error. File reload is watch-driven with a 2-second recheck behind it — see "Reload From Disk" above.

**Platform support:** Linux and macOS only (see README's Installation section). `default_opener` (`o` link-opening) hard-codes `open` on macOS and `xdg-open` everywhere else, and `resolve_editor`'s no-`$VISUAL`/`$EDITOR` fallback is `vi` — neither exists on Windows. The code assumes Unix throughout (file modes, `fchown`, process groups, `kill`) with no fallbacks, and `main.rs` opens with a `#[cfg(not(unix))] compile_error!`, so a non-Unix build fails at once with that message instead of compiling stand-ins that no build ever tested.

## Config File (`src/config.rs`)

Sets defaults for the 4 boolean CLI flags so they don't need to be passed on every invocation, at `$XDG_CONFIG_HOME/markcheck/config.toml` (falling back to `$HOME/.config/markcheck/config.toml`). TOML keys use each flag's positive sense — `nerd_font`, `mouse`, `primary`, `auto_copy` — even though `no_nerd_font`/`no_mouse` are negations on the CLI; the two are merged in `cli.rs` (`Settings::resolve`), not in `config.rs`:

```rust
pub struct Config {
    pub nerd_font: Option<bool>,
    pub mouse: Option<bool>,
    pub primary: Option<bool>,
    pub auto_copy: Option<bool>,
    pub color: Option<ColorChoice>,    // "auto" | "truecolor" | "256" | "16"
    pub git_sync_paths: Option<Vec<PathBuf>>,
}
```

Precedence, per flag: **CLI flag (if passed) > config value > built-in default.** Each of the four settings has a flag in *both* directions — `--nerd-font`/`--no-nerd-font`, `--mouse`/`--no-mouse`, `--primary`/`--no-primary`, `--auto-copy`/`--no-auto-copy` — so any config value can be overridden for a single run, either way. All four resolve through one `resolve_flag(cli_on, cli_off, config, default)`: an explicitly passed flag wins (positive → `true`, negative → `false`), else the config value, else the built-in default. clap's `conflicts_with` on each pair rules out both being passed at once, so `resolve_flag` never has to define that case. `color` is not a boolean and resolves as `cli.color.or(config.color).unwrap_or_default()` in the same `Settings::resolve`.

This took two rounds to get right, both times through the *call sites* rather than `resolve_flag` itself. Round 2: `primary`/`auto_copy` were `cli.x || config.x`, which can only ever turn a setting on, so `auto_copy = true` in the config couldn't be disabled for one run; that added `--no-primary`/`--no-auto-copy` and routed all four through `resolve_flag`. Deep review, round 3: it only added flags for *two* of the four, while README and CHANGELOG were updated to claim all four had both directions — `nerd_font`/`mouse` default to `true`, had only their negative flag, and passed a hardcoded `false` for `cli_on`, so `nerd_font = false` in the config still couldn't be overridden. This paragraph documented that older state as settled design (“there's no CLI way to force it back off”) and was itself left unupdated by round 2's commit, so all three documents disagreed with the code and with each other. `--nerd-font`/`--mouse` close it.

Because both regressions were wiring, not logic, `Settings::resolve` now owns the whole CLI+config → four-booleans mapping in one place, and `Settings`' tests drive it through **real argv** (`Cli::parse_from`) rather than calling `resolve_flag` directly — a test of the pure function passes just as happily with a hardcoded `false` at the call site, which is exactly how round 3's half of this survived round 2's fix.

`git_sync_paths` is the odd field out — a list, not a single default for a single flag. It holds path prefixes: a file whose canonical path starts with one of them auto-activates git-sync, the same as passing `--git-sync` for that one invocation. `launch::git_sync_request` ORs the two together (`cli_flag || any entry matches`) rather than the CLI-overrides-config precedence the other four fields use, since `--git-sync` is a blanket "yes, definitely" rather than a default for this same key. `--no-git-sync` is the blanket "no" and beats both (`requested && !cli_off`), so a covered file can still be opened for one run without committing or pushing; the entries are still checked, so an unresolved one is reported regardless. Each entry first has a leading `~` expanded against `$HOME` (`launch::expand_tilde`) — the config file never passes through a shell, and `~/checklists` is the natural way to write one. `git_sync_path_matches` then canonicalizes the prefix before comparing — `file_path` is already canonical, and an as-written relative or symlink-containing prefix would otherwise never match a file it should cover, since only one side of the comparison would be resolved. An entry that doesn't exist can never match, so `git_sync_request` returns it in `unresolved` (every entry is checked, even after one matches) and `main.rs` shows `git_sync_paths: <entry> does not exist — ignored` as a sticky startup message: the same "surface a typo, don't hide it" stance as the hard error for an unknown key, but a warning rather than a refusal to start, since a directory that only exists on some machines is a legitimate config shared between them. The comparison itself is `Path::starts_with`, which matches path *components*, not string bytes — a configured `/foo/bar` never matches `/foo/barn/file.md`. **An entry covers its own repository, not ones nested inside it (#124).** A repository copied or unpacked into a configured tree carries its own `.git/config` and hooks, which git trusts because the files belong to the user (`safe.directory` checks only ownership), so syncing it on a prefix match alone ran another party's `remote.<name>.uploadpack`, `core.sshCommand`, `core.fsmonitor` and hooks just by opening a checklist. `git_sync_request` therefore also returns the entries that cover the file (`CoveringEntry`: as written, the canonical prefix, and whether it ended in `/**`, split off by `split_nested`) and whether `--git-sync` was passed, and `main.rs` runs `launch::git_sync_scope` against `GitSync::repo_root()` right after `detect`, which has run only `rev-parse` (no hooks, no helpers), and before the catch-up, the leftovers sweep or any sync. A plain entry is accepted only when the canonical root is the prefix itself or one of its ancestors; a `/**` entry or `--git-sync` accepts any root. A refusal becomes the detect error, shown as `Git sync off: the checklist's repository (...) is nested inside git_sync_paths entry ...; end the entry with /** ...`. `a_plain_git_sync_paths_entry_never_runs_git_in_a_nested_repository` (PTY) plants a hostile `uploadpack` and hook in a nested repository and checks neither runs.

A **missing** config file is not an error (`load_config` returns `Loaded::default()`, all `None`) — most installs have no file. An **existing but malformed** one *is* a hard error that aborts startup before the TUI opens, with `anyhow` context naming the file and the `--no-config` way out: the user asked for these defaults, so silently falling back would hide a mistake rather than surface it (this is the same startup-error style as an unresolvable file path). That covers bad TOML and a known key with the wrong type.

An **unknown key** is only a warning (issue #112). It used to be a hard error via `deny_unknown_fields`, to surface a typo'd key (e.g. `nerdfont`) that serde would otherwise ignore silently — but the same rule rejected keys a *newer* release understands, so a config shared between machines (dotfiles, the multi-host setup git-sync serves) locked every machine still on an older release out of every checklist once one setting was added. `load_config` now parses the file twice — once as a `toml::Table` to list its top-level keys, once into `Config` (which ignores unknown fields; both parses keep `toml`'s line/column errors) — and returns a `Loaded { config, unknown_keys }`, where `unknown_keys` is every top-level key not in `KNOWN_KEYS`, sorted. `main.rs` passes them to `config::unknown_keys_warning`, which joins the sticky startup message alongside the other startup warnings (`launch::startup_message`). `KNOWN_KEYS` duplicates the field list, so two tests pin it to `Config`: setting every field must report no unknown keys, and giving each `KNOWN_KEYS` entry a wrong-typed value must fail (an entry naming no real field would accept anything).

`config::load_for_run` picks the file for the run: `--no-config` returns the defaults without reading anything, so a broken config can be bypassed without editing it; `--config PATH` reads `PATH` instead of the default location, and a missing `PATH` *is* an error (`config file not found`), since the user named it; otherwise `config_path` decides, as below.

`config_path(xdg_config_home, home)` takes the two environment values as parameters rather than reading the environment itself, so it's pure and testable without mutating global process state — the same pattern `resolve_editor`/`resolve_opener` (`launch.rs`) already use for `$EDITOR`/`$VISUAL`/`$BROWSER`. `main.rs` is the only caller that reads the real environment. Test isolation follows from the same design: every process `tests/cli.rs` and `tests/pty.rs` spawn gets `common::isolated_env`, whose `HOME` and `XDG_CONFIG_HOME` are a freshly created, empty per-test directory, so the suite never picks up a real config file on the machine running it, nor one anyone could plant in the shared, world-writable temp directory (pinning `XDG_CONFIG_HOME` to `std::env::temp_dir()` itself, as an earlier version did, allowed exactly that); a test that wants to exercise config behavior overrides it with its own isolated directory.

## Testing

Unit tests live in a `<module>_tests.rs` file beside each module, attached with `#[cfg(test)] #[path = "<module>_tests.rs"] mod tests;` so they still see the module's private items; UI rendering is tested via ratatui's `TestBackend` (content assertions, not styling). `tests/pty.rs` drives the compiled binary under a pseudo-terminal (`portable-pty`, a dev-dependency) to cover `main.rs`'s terminal wiring — the event loop, key dispatch, editor suspend/restore, and reset — which can't be reached headless; assertions are behavioral (clean exit, resulting file contents) rather than screen-scraping, except where a message on screen is the only observable effect. Each test drives a `Session`: it spawns the binary, drains the PTY output on a background thread, and waits for the alternate screen to be entered (raw mode is on by then, so keys reach the event loop) before sending anything. Scripted interactions are a sequence of `Step`s: `Step::Key` paces plain keys with a short fixed delay (input pacing only, so an `Esc` is never read together with the next key as an Alt-chord), `Step::WaitForFile` polls the target markdown file for a condition a preceding key is expected to have caused — mirroring `watcher.rs`'s own `wait_until` test helper — and `Step::WaitForScreen` polls for text on the screen, replaying the output's cursor moves onto a grid (ratatui only redraws changed cells, so a message is rarely one contiguous run in the byte stream). These are used before any step (notably quitting) that depends on that condition already holding, e.g. an edit having landed, a toggle having been written back, or an external write having been reloaded. No test synchronizes on a fixed sleep: guessed delays could be too short under CI load or needlessly long otherwise, and were the source of CI flakiness. Every wait has a deadline, including the child's exit, which is polled and the child killed and the test failed if it doesn't quit, so a hung binary can't hang CI. Each `Session` holds a file-wide lock while its binary runs, serializing the PTY tests (concurrent PTY-spawning tests starved git-sync's background thread on shared CI runners) while the unit tests keep full parallelism. `tests/cli.rs` covers the `main.rs` startup paths that exit *before* any terminal setup — an unresolvable file path, an unreadable one (not UTF-8, a directory), a valid file with zero checklist items, and a run whose stdout is not a terminal — plus the `--help` text naming the config file, with plain `Command::output()` subprocess runs, no pseudo-terminal needed; `tests/pty.rs` additionally covers `open_in_editor`'s spawn-failure and non-zero-exit branches (a nonexistent/failing `$EDITOR`), asserting the app survives and exits cleanly with the file untouched. Coverage: `cargo llvm-cov` (see CLAUDE.md); the headline figure measures production code only. It excludes the `*_tests.rs` files and both `test_support.rs` files, because test code is executed by definition and would otherwise pull the percentage up (with tests inline, the gate read about 98% while production code was below 97%). It also excludes `main.rs`, though the PTY (and now CLI) tests do cover most of it in practice. That exclusion is only sound while `main.rs` stays wiring: anything with branches of its own — flag precedence, command resolution, outcome-to-message mapping, the post-editor reload — lives in a covered module (`cli.rs`, `launch.rs`, `git_sync`, `AppState`) instead, so the 97% gate measures it.

**Prerequisites.** `cargo test` needs `git` and `sh` on `PATH` (the git-sync fixtures and the stub commands run real subprocesses), and `cargo build` first for the PTY and CLI binaries. Two tests depend on the machine and skip with a `skipped:` note on stderr instead of failing where it can't support them: the scaffold test that makes its directory read-only to force the temp write to fail skips when the directory stays writable (running as root, the default in most container images), and the lock tests that need a real liveness probe skip when there is no `ps` (Debian/Ubuntu `-slim` images, including the official `rust:*-slim` ones, ship without `procps`) and, for the recovery test, no `/proc` either. A run as a non-root user with `ps` installed exercises everything.

**Temp files clean themselves up.** Every test path under the temp directory comes from `test_support::unique_temp_path` (or `tests/common`'s copy for the integration binaries), which records the path in a thread-local list whose `Drop` removes each file or whole directory. libtest runs each test on its own thread, so cleanup happens when the test ends, pass or panic, without each call site holding a guard; a full `cargo test` leaves nothing `markcheck-*` behind in the temp directory.

`git_sync/`'s own tests build real throwaway git repos under `std::env::temp_dir()` (a bare "remote" plus a working clone, mirroring `watcher.rs`'s temp-file convention) and run actual `git` subprocesses — no mocking, since the whole point is verifying real `git` behavior (e.g. that a temporary-index commit never picks up an unrelated staged file, or that an untracked checklist is reported rather than added). Those subprocesses are hermetic, so the results don't depend on the machine or on how the suite was started: fixture commands go through `test_support::git()` (`tests/pty.rs` has its own `git(dir)`), and under `cfg(test)` `git_command` applies the same `isolate_git`, so the commits markcheck itself makes in a fixture are covered too. Both strip the repository-redirecting variables (a pre-commit or pre-push hook that runs the suite exports `GIT_DIR`/`GIT_INDEX_FILE`, which would otherwise send `git add` into the outer repository — defect class 8, inside the tests) plus `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT`, set `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` (a developer's `commit.gpgsign`, `core.hooksPath` or `init.templateDir` would otherwise change fixture behavior), and point `HOME`/`XDG_CONFIG_HOME` at an empty directory so no global ignore or attributes file applies either. Most tests call the free `run_sync` function directly, synchronously, rather than going through `GitSync::request`/`poll`'s background thread, to keep them deterministic; the couple that do exercise the thread (`request`/`poll` round-trip, and coalescing a second request that arrives while busy) write every file change *before* either `request` call, so there's no race between the background thread's `git status` check and a concurrent write on the test thread — an earlier draft that wrote the file *between* two `request` calls was genuinely flaky (which of two concurrently-racing filesystem operations wins is not deterministic), not just a wrong assertion. `tests/pty.rs`'s `git_sync_flag_commits_and_pushes_after_toggle` covers the same feature end-to-end through the compiled binary (flag parsing, `GitSync::detect`, and the main-loop poll/request wiring) that `git_sync/`'s unit tests can't reach, using the same bare-remote-plus-clone setup; its checklist file needs **two** items, not one, since completing the *only* item would swap `q` for the reset-before-quit confirmation prompt instead of exiting.

## Verification Checklist

- `h`/`l`/`j`/`k` (and `←`/`→`/`↓`/`↑`) all navigate prev/next and, at a list edge, cross into the adjacent list landing on its first not-done item; the mouse wheel and toggle-advance clamp instead
- `Ctrl-E`/`Ctrl-Y`, `Ctrl-D`/`Ctrl-U`, and `PageDown`/`PageUp` scroll an overflowing card body (line / half-page / page) and clamp; on a card that fits they do nothing
- mouse wheel scrolls an overflowing card, otherwise navigates prev/next
- `Space`/`Enter` toggles; file updated immediately (`grep -n '\[x\]' <file>`)
- Duplicate items with identical text: toggling one updates only its line
- Completing last item in list → `ListComplete` screen appears
- `l`/`Enter` from `ListComplete` → jumps to next list; `h` returns to last item
- Completing all lists → `AllComplete` screen with correct per-list counts
- `y` on a single-code item → copies it; on 0 or several candidates → status-bar alert, nothing copied
- `e` → suspends TUI, opens `$EDITOR` (on the selected task's line for editors with a known line syntax), restores and reloads with the cursor kept
- `Ctrl-Z` → suspends to the shell with the terminal restored; `fg` repaints and loads any edit made meanwhile
- `Ctrl-C` → on a content screen shows `Type q to quit` without quitting; in search, the `T` picker, help or a confirmation it cancels like `Esc`
- `R` → confirmation card; only `y` resets all tasks to not-done, any other key (including `Enter`) cancels
- `u` undoes the last toggle/start/reset (restoring state and focusing the changed task); `Ctrl-R` redoes it; empty history / a deleted file report a sticky message; an external reload clears the history
- Card body shows no `[ ]`/`[x]` prefix; done cards read green
- A leading bold-only bullet renders as the list's warning banner (not a navigable card); a later bold-only bullet, or a leading one carrying inline or fenced code, renders as a display-only card whose command `y` copies
- `### H3`+ under an H2 → an overview `── divider` above its group and a dim ` › ` breadcrumb above the card; deeper H4+ nest; an item-less sub-heading shows nothing; the heading isn't a cursor target, but `}`/`{` jump between sub-sections
- List with no checklist items is dropped (no tab, not navigable)
- Terminal resize → layout reflows without panic (incl. the narrow single-card fallbacks)
- `q` → terminal fully restored (cursor visible, no raw mode, mouse capture released)
- Title bar `done/total` counter updates live as items are toggled
- Editing the open file externally → TUI reloads within the same tick, title bar shows `↻ Updated Ns ago` (refresh icon, stepping in 5s increments), cursor stays on the same list/item where possible; toggling a task yourself updates the same tag
- Toggling a checkbox ourselves never produces a spurious "Reloaded" status message
- Update tag disappears from the title bar 2 minutes after the last change
- Wiping the file to zero lists externally → reload is skipped (status bar shows `Reload skipped: file has no checklist items`), last good document stays in memory
